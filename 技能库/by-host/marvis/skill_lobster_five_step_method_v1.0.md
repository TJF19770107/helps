### Step 1 — DEFINE 定义问题

> **核心问题**：我们到底在解决什么问题？边界在哪里？

**操作要点**：
1. 用一句话描述问题（≤30字，含主语+动词+结果）
2. 区分**症状**（表象，可观察）和**根因**（本质，待挖掘）
3. 确认问题**可测量**（有明确成功标准，避免主观判断）
4. 圈定**边界**（范围内 vs 范围外，防止范围蔓延）

**问题定义模板**：
```
问题陈述: <一句话，≤30字>
症状表现: <观察到的现象列表>
根因假设: <可能的深层原因（可多个）>
成功标准: <完成时如何验证，要可量化>
边界定义:
  包含: <xxx>
  不包含: <xxx>
```

**典型场景示例**：

| 场景 | 错误定义 | 正确定义 |
|------|---------|---------|
| 策略回测 | "策略不好" | "BTC趋势策略近30天最大回撤>15%，目标降至<8%" |
| 系统部署 | "系统崩了" | "Hermes服务(8642)启动后30秒内自动退出，错误码1" |
| 信号质量 | "信号不准" | "RSI超买信号次日涨幅<0%的比例达68%，目标<40%" |

**常见陷阱**：
- ❌ 把解决方案当问题（"问题是没有用Redis"）
- ❌ 问题太宽泛（"系统性能差"）
- ❌ 成功标准主观（"跑起来就行"）

### Step 2 — COLLECT 收集信息

> **核心问题**：我们有什么？缺什么？信息可靠吗？

**信息四象限分类**：
```
┌─────────────────────────────────────────────────┐
│ Category A: 已知且确认  → 直接使用                 │
│ Category B: 已知但存疑  → 验证后使用               │
│ Category C: 未知可获取  → 立即收集                 │
│ Category D: 未知难获取  → 标记风险，制定假设         │
└─────────────────────────────────────────────────┘
```

**信息收集工具优先级**（从快到慢）：
```
P1. 本地文件/代码库     → 最快，最可控，直接Read
P2. mem_gstack记忆检索  → 历史沉淀，经验复用
P3. 数据库查询          → 结构化精确数据
P4. WebSearch/WebFetch → 实时外部信息
P5. 用户询问            → 最后手段，减少打扰
```

**信息质量评估**：

| 质量指标 | 说明 | 低质量的处理 |
|---------|------|------------|
| 时效性 | 数据是否过期 | 标注时间戳，核实更新时间 |
| 来源可靠性 | 数据来源是否权威 | 标注来源，优先官方/一手 |
| 完整性 | 关键字段是否缺失 | 标注缺失项，补充默认值 |
| 一致性 | 多源数据是否矛盾 | 以最新/最权威源为准 |

**信息收集报告格式**：
```
已获取:
  ✅ <信息项>: <来源> (<时效>)

待验证:
  ⚠️ <信息项>: <当前值> → 需要 <验证方式>

缺失:
  ❌ <信息项> → 影响: <对后续步骤的影响> → 方案: <如何获取/假设>
```

### Step 3 — GENERATE 生成方案

> **核心问题**：有哪些解决路径？哪个最优？

**方案生成规则**：
- 至少生成 **2个**方案（避免单一路径陷阱）
- 每个方案必须是**可执行的**（不是方向，是具体步骤）
- 明确标注每个方案的**假设前提**

**方案评估矩阵**（3维评分，1-5分）：

```
| 方案 | 可行性(F) | 成本(C，低=好) | 风险(R，低=好) | 综合分=F×2-C-R |
|-----|----------|--------------|--------------|---------------|
| A   |    4     |      2       |      2       |    4×2-2-2=4  |
| B   |    3     |      1       |      3       |    3×2-1-3=2  |
| C   |    5     |      4       |      1       |    5×2-4-1=5  |
```

**推荐规则**：
- 选综合分最高且风险可控（R≤3）的方案为**主推方案**
- 保留综合分第二的方案为**Plan B**
- 风险R≥4的方案需额外列出风险缓解措施

**方案描述格式**：
```
方案 A: <一句话描述>
  前提假设: <列出依赖条件>
  执行步骤: Step1 → Step2 → Step3
  预期产出: <具体描述>
  评分: F=X, C=X, R=X, 综合=X
  适用场景: <什么情况下选择此方案>
```

**量化策略迭代专用评估维度**：

| 维度 | 说明 |
|------|------|
| 历史收益 | Sharpe Ratio / 年化收益率 |
| 风险控制 | 最大回撤 / 波动率 |
| 实现复杂度 | 代码行数 / 依赖服务数 |
| 实盘稳定性 | 信号频率 / 延迟要求 |

### Step 4 — EXECUTE & VERIFY 执行与验证

> **核心问题**：做了什么？结果对不对？

**执行四原则**：

| 原则 | 说明 | 反例 |
|------|------|------|
| 小步快跑 | 每步执行后立即验证 | 10步执行完才检查 |
| 可回滚 | 高风险操作前建检查点 | 直接覆盖生产配置 |
| 留痕迹 | 关键操作记录日志 | 执行成功但不知道做了什么 |
| 闭环确认 | 执行完 ≠ 任务完成 | 工具没报错就认为成功 |

**验证三问（每步执行后必问）**：
```
Q1: 产出是否符合预期格式？（文件/JSON/数值/状态码）
Q2: 结果是否在合理范围内？（数值范围/文件大小/记录数）
Q3: 是否有意外副作用？（影响了预期外的系统/文件/服务）
```

**量化策略回测验证清单**：
```
□ 回测时间范围覆盖牛熊市场
□ 手续费和滑点已纳入计算
□ 没有使用未来数据（前视偏差检查）
□ 样本内 vs 样本外表现对比（过拟合检查）
□ 最大回撤在可接受范围内
□ 交易频率符合实盘执行能力
```

**常见执行陷阱**：
- ❌ 跳过中间验证直接执行到底
- ❌ 把工具没报错当成执行成功
- ❌ 忘记验证边界条件（空数据、异常输入、0值）
- ❌ 回测胜率高≠实盘可用（忽略流动性和滑点）

---

### Step 5 — SOLIDIFY 固化传承

> **核心问题**：这次解决了，下次怎么更快？经验如何传承？

**固化三要素**：
```
1. 做了什么 → 任务记录（今日日志）
2. 为什么这样做 → 决策依据（MEMORY.md）
3. 踩过哪些坑 → 经验教训（技能文件/MEMORY.md）
```

**固化工具选择**：

| 内容类型 | 存储位置 | 工具 | 优先级 |
|---------|---------|------|--------|
| 可复用完整流程 | SKILL.md | SkillManage(create) | ⭐⭐⭐⭐⭐ |
| 踩坑经验/决策依据 | MEMORY.md | 追加写入 | ⭐⭐⭐⭐ |
| 配置参数/路径 | MEMORY.md | in-place更新 | ⭐⭐⭐⭐ |
| 当日任务记录 | YYYY-MM-DD.md | 追加写入 | ⭐⭐⭐ |
| 重要文件备份 | archive/ 目录 | cp/robocopy | ⭐⭐⭐ |

**传承质量标准**（6个月后的自己能直接用）：
```
✅ 包含完整执行步骤（不是方向）
✅ 包含所需工具和依赖版本
✅ 包含已知问题和解决方案
✅ 包含成功验证方法
❌ 不包含一次性的绝对路径
❌ 不包含临时Token和密码
❌ 不包含仅当时有效的数据
```

### 五步法适用场景

**强烈推荐使用**（复杂度中等及以上）：
- 量化策略迭代优化（L3/L4级任务）
- 系统架构设计和重构
- 新工具链集成和配置
- 跨多天的长期任务
- 涉及多个外部依赖的任务
- 有明确决策分叉的分析任务

**可简化执行**（快速任务，仅用1-2步）：
- 单一文件读写修改
- 明确的API信息查询
- 简单的代码片段生成
