## Step 1-5 核心五步法（继承自 v1.0）

> **注**：Step 1-5 完全继承自 `lobster_five_step_method_v1.0`，此处仅作简要回顾。

### 快速回顾

| 步骤 | 核心问题 | 关键产出 | 质量检查点 |
|------|----------|----------|------------|
| S1 DEFINE | 我们到底在解决什么问题？ | 问题陈述 + 成功标准 | 问题可测量、边界清晰 |
| S2 COLLECT | 我们有什么？缺什么？ | 信息四象限盘点 | 信息可靠、完整 |
| S3 GENERATE | 有哪些解决路径？哪个最优？ | ≥3方案 + 评估矩阵 | 方案可执行、风险可控 |
| S4 EXECUTE | 做了什么？结果对不对？ | 执行日志 + 验证结果 | 小步快跑、可回滚 |
| S5 SOLIDIFY | 经验如何传承？ | Skill/MEMORY/日志 | 6个月后自己能直接用 |

## Step 6 — ITERATE 迭代反馈闭环

> **核心问题**：如何持续改进？反馈如何闭环？

### 6.1 迭代三循环模型

```
┌──────────────────────────────────────────────────────────────────────────────────┐
│                   迭代三循环 — Triple Loop                                        │
├──────────────────────────────────────────────────────────────────────────────────┤
│  内循环（执行层）: S4 EXECUTE → 验证 → 调整执行                                    │
│  中循环（方案层）: S3 GENERATE → S4验证 → 优化方案                                 │
│  外循环（问题层）: S1 DEFINE → S5固化 → 重新定义问题                               │
└──────────────────────────────────────────────────────────────────────────────────┘
```

### 6.2 反馈收集矩阵

| 反馈来源 | 收集方式 | 处理优先级 | 反馈闭环时间 |
|----------|----------|------------|--------------|
| 执行结果 | 自动监控（工具返回） | P0（立即） | ≤5分钟 |
| 用户反馈 | 主动询问/被动接收 | P1（高） | ≤1小时 |
| 系统监控 | 性能/错误日志 | P2（中） | ≤4小时 |
| 外部环境 | 市场/技术变化 | P3（低） | ≤24小时 |
| 历史经验 | claude-mem 检索 | P1（高） | ≤30分钟 |

### 6.3 迭代决策流程

```
开始迭代
├─ 收集反馈（多源）
├─ 分析反馈类型
│   ├─ 执行错误 → 修复执行（内循环）
│   ├─ 方案缺陷 → 优化方案（中循环）
│   ├─ 问题偏差 → 重新定义（外循环）
│   └─ 环境变化 → 适应调整（外循环）
├─ 制定改进措施
├─ 执行改进
└─ 验证改进效果 → 记录到 claude-mem
```

### 6.4 迭代质量指标

| 指标 | 目标值 | 测量方法 | 改进触发条件 |
|------|--------|----------|--------------|
| 错误率 | ≤5% | 错误次数/总操作数 | >10% |
| 用户满意度 | ≥4/5 | 主观评分 | <3/5 |
| 执行效率 | 提升≥10% | 耗时对比 | 下降>20% |
| 方案优化度 | ≥2次/周 | 方案改进次数 | 连续2周无改进 |
| 问题解决率 | ≥90% | 成功解决问题数/总数 | <80% |

### 6.5 迭代工具化

1. **反馈收集工具**
   - 用户反馈: `ask_user`（确认/评分）
   - 执行监控: 工具返回码/日志分析
   - 性能监控: `lobster_codex_benchmark_v1.0`
   - 历史检索: `claude-mem` + `gstack`

2. **分析决策工具**
   - 根因分析: 五步法 S1 DEFINE
   - 方案优化: 五步法 S3 GENERATE
   - 优先级排序: 四象限法（紧急/重要）

3. **改进执行工具**
   - 快速修复: 原工具重试/参数调整
   - 方案重构: 重新执行 S3-S4
   - 问题重定义: 重新执行 S1-S5

## Step 7 — ARCHIVE 跨平台归档与版本管理

> **核心问题**：成果如何跨平台共享？版本如何管理？

### 7.1 归档四层结构

```
┌──────────────────────────────────────────────────────────────────────────────────┐
│                   归档四层结构 — 4-Layer Archive                                   │
├──────────────────────────────────────────────────────────────────────────────────┤
│  L1: 原始产出物    — 文件/代码/数据（不可修改）                                     │
│  L2: 过程文档      — 执行日志/决策记录/会议纪要                                     │
│  L3: 经验总结      — 成功模式/失败教训/最佳实践                                     │
│  L4: 技能封装      — SKILL.md/MEMORY.md/工作流模板                                  │
└──────────────────────────────────────────────────────────────────────────────────┘
```

### 7.2 跨平台归档规范

| 平台 | 归档位置 | 格式要求 | 同步机制 |
|------|----------|----------|----------|
| Marvis (Windows) | `E:\龙虾AI主控中心\归档库\` | 原始格式 + Markdown | WebDAV 自动同步 |
| Claude Code | `~/lobster-archive/` | POSIX路径 + 软链接 | Git 同步 |
| TRAE (Cloud) | `/archive/` 项目空间 | 云存储格式 | API 自动上传 |
| CC Switch | `.cc-switch/skills/` | SKILL.md 标准 | 技能管理器同步 |
| Hermes | `/app/data/archive/` | 容器内路径 | 卷挂载同步 |

### 7.3 版本管理策略

1. **语义化版本控制**
   ```
   主版本.次版本.修订版本
   v1.2.3
   │ │ └─ 修订版本：Bug修复，向后兼容
   │ └─── 次版本：功能增强，向后兼容
   └───── 主版本：架构变更，可能不兼容
   ```

2. **版本标签规范**
   - `stable`: 生产环境稳定版
   - `beta`: 测试环境测试版
   - `dev`: 开发环境开发版
   - `archive`: 历史归档版（只读）

3. **版本发布流程**
   ```
   开发 → 测试 → 预发布 → 生产 → 归档
   dev   beta   rc     stable archive
   ```

### 7.4 归档质量检查清单

| 检查项 | 标准 | 检查工具 |
|--------|------|----------|
| 文件完整性 | 无损坏、可正常打开 | 文件校验和 |
| 元数据完整 | 包含创建时间、作者、版本 | 元数据提取 |
| 依赖明确 | 列出所有依赖项和版本 | 依赖分析 |
| 可复现性 | 提供完整复现步骤 | 复现测试脚本 |
| 安全性 | 不包含敏感信息 | 敏感信息扫描 |
| 跨平台兼容 | 在所有目标平台可访问 | 平台兼容性测试 |

### 7.5 归档工具链

1. **本地归档工具**
   - 文件打包: `tar/zip/7z`
   - 版本管理: `git tag`
   - 元数据管理: `yaml/json` 配置文件

2. **跨平台同步工具**
   - WebDAV: `rclone/webdav-client`
   - Git: `git push/pull`
   - 云存储API: 各平台SDK

3. **归档验证工具**
   - 完整性验证: `md5sum/sha256sum`
   - 兼容性测试: 多平台测试脚本
   - 安全性扫描: 敏感信息检测脚本

## 第3章：多Agent协作编排矩阵

### 3.1 Agent角色定义

| Agent | 核心能力 | 适用场景 | 协作接口 |
|-------|----------|----------|----------|
| **Marvis** | Windows桌面自动化、文件操作、GUI控制 | 本地文件处理、桌面应用操作、Windows系统管理 | MCP文件工具、shell_executor |
| **TRAE** | 云端计算、Web搜索、API集成 | 网络信息收集、云端数据处理、Web服务调用 | REST API、WebSocket |
| **Claude Code** | 代码分析、开发调试、技术架构 | 代码审查、技术方案设计、系统架构 | 代码编辑器集成、终端工具 |
| **CC Switch** | 技能管理、工作流编排、任务分发 | 技能调用编排、跨Agent任务分发、工作流管理 | 技能调用API、任务队列 |
| **Hermes** | 容器化AI服务、模型推理、批量处理 | AI模型服务、批量数据处理、隔离环境执行 | Docker API、gRPC |

### 3.2 协作模式矩阵

| 协作模式 | 主导Agent | 辅助Agent | 通信协议 | 适用任务类型 |
|----------|-----------|-----------|----------|--------------|
| **主从模式** | Marvis | TRAE/Claude Code | MCP + API | 本地为主，云端为辅 |
| **并行模式** | CC Switch | 所有Agent | 消息队列 | 任务分解并行执行 |
| **接力模式** | Agent A → B → C | 顺序传递 | 文件/数据传递 | 多阶段流水线 |
| **协同模式** | 多Agent平等 | 实时协作 | WebSocket | 复杂决策分析 |
| **监督模式** | Hermes | Marvis/TRAE | 监控API | 长期任务监控 |

### 3.3 协作协议规范

1. **任务分发协议**
   ```json
   {
     "task_id": "uuid",
     "task_type": "file_processing|code_analysis|web_search",
     "priority": "P0|P1|P2|P3",
     "timeout": 300,
     "requirements": {
       "target_agent": "Marvis|TRAE|ClaudeCode",
       "skills_required": ["skill1", "skill2"],
       "input_format": "file_path|url|code_snippet",
       "output_format": "json|file|text"
     }
   }
   ```

2. **结果返回协议**
   ```json
   {
     "task_id": "uuid",
     "status": "success|partial|failed",
     "result": {
       "data": "...",
       "files": ["path1", "path2"],
       "metrics": {"time_cost": 120, "accuracy": 0.95}
     },
     "next_steps": [
       {"agent": "ClaudeCode", "action": "code_review"},
       {"agent": "Marvis", "action": "file_cleanup"}
     ]
   }
   ```

3. **错误处理协议**
   ```json
   {
     "error_type": "agent_unavailable|skill_missing|timeout",
     "error_message": "详细错误描述",
     "suggested_fallback": {
       "alternative_agent": "TRAE",
       "alternative_skill": "backup_skill",
       "degraded_mode": true
     },
     "retry_policy": {
       "max_retries": 3,
       "retry_delay": 30,
       "exponential_backoff": true
     }
   }
   ```

### 3.4 协作冲突消解规则

1. **资源冲突**（文件/端口/内存）
   - 原则: 先到先得，后到等待
   - 超时: 等待超时后尝试替代方案
   - 优先级: P0 > P1 > P2 > P3

2. **结果冲突**（不同Agent结果不一致）
   - 原则: 多数一致 + 权威源优先
   - 权威排序: Claude Code > TRAE > Marvis > Hermes
   - 验证机制: 第三方验证或人工仲裁

3. **流程冲突**（任务依赖关系冲突）
   - 原则: 依赖优先，无依赖并行
   - 检测: 依赖图分析
   - 调整: 动态重排执行顺序

4. **权限冲突**（不同Agent权限不同）
   - 原则: 最小权限 + 权限提升申请
   - 提升流程: 低权限 → 申请 → 高权限执行
   - 记录: 权限提升日志

### 3.5 协作性能优化

1. **负载均衡策略**
   - 基于Agent当前负载分配任务
   - 基于任务类型匹配Agent专长
   - 基于历史性能数据预测耗时

2. **缓存共享机制**
   - 跨Agent结果缓存（避免重复计算）
   - 文件共享缓存（避免重复传输）
   - 配置共享缓存（统一配置管理）

3. **连接池管理**
   - Agent连接池（减少连接建立开销）
   - 数据库连接池
   - HTTP连接池

   - 项目准时率: 按时交付项目数/总项目数
   - 客户满意度: 客户评分平均值（1-5分）
   - 缺陷密度: 缺陷数/千行代码（或功能点）

3. **持续改进机制**
   - 每月质量评审会议
   - 季度质量报告分析
   - 年度质量目标设定
   - 质量改进项目跟踪
