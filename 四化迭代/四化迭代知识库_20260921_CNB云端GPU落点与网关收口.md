## 三、★ 本轮三个新坑（都是实测逼出来的，不是推理的）

### 形态 #21 · 高优先级环境变量注入窄凭据 → 宽凭据被静默遮蔽 → **假性能力缺失**

**这是本轮最有价值的发现，直接改写了「能力判定」的方法论。**

- **现场**：`cnb` CLI 的所有 API 模块（`users` / `repositories` / `workspace` / `charge`）一律回
  `403 Missing required scopes: account-engage:r`。按经验，这看起来就是「令牌 scope 不够」。
- **真因**：宿主往环境里注入了一个 **27 位的 git 专用窄令牌**到 `CNB_TOKEN`。而 CLI 源码写着：

  ```js
  // @cnbcool/cnb-cli/dist/index.js · resolveApiDomain
  let e = process.env.CNB_API_ENDPOINT || "https://api.cnb.cool";
  if (process.env.CNB_TOKEN_FOR_CODEBUDDY || process.env.CNB_TOKEN) return e;  // ← 一旦存在就短路
  let t = loadToken();   // 只有前面都不成立，才去读 ~/.cnb/token
  ```

  **它一旦存在就直接返回，连 `~/.cnb/token` 里那个 94 位宽 scope OAuth 令牌都不读。**
- **误判代价**：我差点写下「令牌 scope 不够，请去补授权」的错误指引 —— **归因完全错**。
- **验证**：摘掉 `CNB_TOKEN` 后跑同样三条探针 → **全部 200**：
  `get-user-info` 拿到「汤嘉锋」· `get-repos` total=**19** · `list-workspaces` total=**65**。
- **判据**：**报错信息指向的对象 ≠ 真正出问题的对象**。当「权限类报错」出现时，先做**凭据来源分层**
  （env var → 本地文件 → 默认值），逐个摘除法验证，**不要直接接受报错文本的归因**。
- **沉淀**：`cnb_env_up.py` 默认主动摘掉窄令牌，并提供 `--use-env-token` 反向开关。

### 形态 #22 · 异步受理被读成失败 → **假失败**

- `start-workspace` 受理成功时平台回：`status: 200` + `sn: cnb-ruq-…` + `message: "cnb received, but didn't finish build yet"`。
- 我最初的判据是 `if "status:" in blob → 失败`，**把成功读成了失败**。
- **正确判据**：`status: 200` **且** 拿到 `sn` = 受理成功（异步）；终态必须另查 `build get-build-status`。

### 形态 #23 · `.cnb.yml` 配置正确 ≠ 环境能起 —— 配额前置校验会先拦

- 现象：`Pipeline prepare error: Root Group's workspaces GPU core-hours are insufficient for pre-freezing (5.00 min ≈ 1.33 core-hours)`。
- **极易误判成「.cnb.yml 写错了」**。但同一次构建日志证明前面全绿：
  `Runner runs on cnb:arch:amd64:gpu` / `GPU: L40` / `cpus 16` / `memory 128` / 4 个 service 全 started。
- **判据**：CNB 的失败有**分层** —— `配置解析` → `runner 分配` → `services 启动` → **`配额预冻结`** → `stages 执行`。
  看日志要**按这五层逐层定位**，别一出错就改配置。
