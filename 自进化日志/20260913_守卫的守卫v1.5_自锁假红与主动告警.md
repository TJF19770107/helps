## 二、核心发现：267009 不是崩溃，是 Windows 在说「它正在跑」

### 现象

```
[红] Lobster_GuardHealthAudit
     判定: 审计器上次执行失败（退出码 267009，未捕获异常）
```

但同一时刻，**结果码同为 267009** 的另外三个任务全都活得好好的：

| 任务 | LastResult | 数据面真相 |
|---|---|---|
| Lobster_HKTunnel | 267009 | 端口 1081 LISTENING ✅ |
| Lobster_HTTP2Socks_7897 | 267009 | 端口 7897 LISTENING ✅ |
| Lobster_ObsidianLaunch | 267009 | GUI 启动器，免检 |
| **Lobster_GuardHealthAudit** | **267009** | **被判「未捕获异常」** ❌ |

同样的码，三个判绿一个判红 —— 判据本身有问题。

### 根因（两层）

**第一层：语义。** `267009 = 0x41301 = SCHED_S_TASK_RUNNING`。
这不是脚本退出码，是**调度器在描述状态**：「这个实例正在运行」。

**第二层：代码结构。** `classify()` 里——

- 自指例外（只放行 `res in (0, 1)`）排在**第 227 行**
- 语义表 `SCHED_S`（含 0x41301=RUNNING）排在**第 267 行**

**自指分支先命中，把状态码吞成了脚本失败。**

### 为什么手动跑永远复现不出来

这是本次最值钱的一条。审计器**被调度器拉起时**，它查询 `schtasks` 的那一刻
**它自己还在运行** → 调度器如实回答 `0x41301`；等它退出（exit 1）后，
落库的结果码才变成 `1`。

所以：

- 手动执行 → 读到 `1` → 走「已报告红项」分支 → 绿，**永远看不到 bug**
- 计划任务执行 → 读到 `267009` → 判自己红 → **自锁**

典型的**时序型假故障**：bug 只在特定观察时点显形，且观察者就是被观察者。

### 修法：语义表做「减刑器」，不做「抢答器」

直觉修法是把语义表提到最前面先返回。**这是错的**——
`Lobster_HKTunnel` 会因此退化成用**弱证据**（状态码）判绿，丢掉更强的端口探针。

正解：预取语义，只在证据链判红时兜底**降级为黄**并留证：

```python
sched = SCHED_S.get(res) if res is not None else None   # 预取，不抢答
sched_ok = bool(sched and sched[1] == "OK")

def soften(level, reason, e=None):
    if level == "RED" and sched_ok:   # 证据链判红，但 Windows 说这不是失败
        return ("YELLOW", f"{reason}；但结果码 {res} = 调度器状态 {sched[0]}", e)
    return (level, reason, e)
```

> **通用教训**：凡是「状态码 → 结论」的映射，一旦被特例分支绕过，映射形同虚设。

## 三、假安全 / 假故障形态新增两条

| # | 形态 | 表现 | 防线 |
|---|---|---|---|
| 6 | **假红（语义被特例吞掉）** | 调度器状态码被自指例外判成崩溃 → 审计器自锁永久红，淹没真实红项 | 语义表做减刑器，且置于所有特例之上 |
| 7 | **假告警（记账与送达脱钩）** | 去重记账写在 `--push` 分支 → 不推送就永不记账 → 冷却期失效 | 记账绑定「是否已送达」，不绑定「用哪条通道送」 |

第 7 条是实测抓出来的：第一版告警器连跑两次，两次都报「新增待报 1」。
因为记账写在推送分支里，不推就不记 —— 去重等于没做。
