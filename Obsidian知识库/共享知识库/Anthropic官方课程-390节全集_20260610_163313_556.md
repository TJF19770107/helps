## 第三部分：Claude Code 子代理（Subagents）体系

### 3.1 子代理核心概念

子代理是专用的 AI 助手，在自己的上下文窗口中执行，具有自定义系统提示、特定工具访问和独立权限。

**三大核心价值**：
1. **上下文保护** — 将探索和实现隔离在主对话之外，防止噪音污染
2. **强制约束** — 限制子代理可使用的工具，按领域隔离
3. **成本控制** — 将任务路由到更快/更便宜的模型（如 Haiku）

### 3.2 子代理定义格式

```yaml
---
name: code-reviewer
description: Expert code reviewer. Use proactively after code changes.
tools: Read, Glob, Grep
model: sonnet
maxTurns: 8
permissionMode: acceptEdits
skills:
  - code-style
hooks:
  PostToolUse:
    - command: "pnpm lint-staged"
---
You are a senior code reviewer. Focus on code quality, security, and best practices.
When invoked, analyze the code and provide specific, actionable feedback.
```

### 3.3 完整 frontmatter 字段表

| 字段 | 必填 | 说明 |
|------|------|------|
| name | ✅ | 唯一标识，小写字母+连字符 |
| description | ✅ | 何时委派任务给此子代理 |
| tools | ❌ | 允许使用的工具列表，省略则继承全部 |
| disallowedTools | ❌ | 禁止使用的工具列表 |
| model | ❌ | sonnet/opus/haiku/inherit/完整模型ID。默认 inherit |
| permissionMode | ❌ | default/acceptEdits/auto/dontAsk/bypassPermissions/plan |
| maxTurns | ❌ | 最大Agent循环次数 |
| skills | ❌ | 预加载的 Skills 列表（完整内容注入，子代理不从父会话继承Skills） |
| mcpServers | ❌ | 可用的 MCP 服务器（支持引用已配置服务器名或内联完整定义） |
| hooks | ❌ | 生命周期钩子，作用域限定此子代理 |
| memory | ❌ | 持久记忆范围：user/project/local |
| background | ❌ | true 时始终作为后台任务运行 |
| effort | ❌ | low/medium/high/xhigh/max |
| isolation | ❌ | worktree 时在临时 git worktree 中运行 |
| color | ❌ | 显示颜色：red/blue/green/yellow/purple/orange/pink/cyan |
| initialPrompt | ❌ | 作为主会话Agent时自动提交的第一个用户轮次 |

### 3.4 内建子代理

| 子代理 | 功能 | 特点 |
|--------|------|------|
| Explore | 代码库探索与研究 | 跳过CLAUDE.md和git status，快速经济 |
| Plan | 任务规划 | 跳过CLAUDE.md和git status |
| general-purpose | 通用任务处理 | 继承父对话权限 |

### 3.5 配置作用域优先级

```
Managed (组织管理员) > Project (.claude/agents/) > User (~/.claude/agents/)
```

### 3.6 多Agent协作判断框架

**单Agent优先** — Anthropic 明确建议大多数情况下单Agent就足够了。

**三种值得上多Agent的信号**：

| 信号 | 场景 | 做法 |
|------|------|------|
| 上下文被噪音淹没 | 子任务产生大量中间信息，主对话只需摘要 | 子Agent独立处理，主Agent只拿可控长度摘要 |
| 搜索空间太大 | 竞品研究、事故根因、替代方案评估 | 多子Agent并行扫互不重叠的方向，汇总交叉验证 |
| 工具太多行为打架 | 20+工具跨领域，注意力分散 | 按领域拆专家子Agent，各自只拿自己那套工具 |

### 3.7 Agent SDK 子代理编排（Python）

```python
import asyncio
import claude_agent_sdk as sdk

code_reviewer = sdk.AgentDefinition(
    description="Python code quality and design review specialist",
    prompt="You're a Python senior engineer with 10 years of experience...",
    tools=["Read", "Grep"],
    model="sonnet",
    maxTurns=8,
)

security_scanner = sdk.AgentDefinition(
    description="Security vulnerability scanner",
    prompt="You're a security engineer. Find injection risks, hardcoded secrets...",
    tools=["Read", "Grep", "Bash"],
    model="sonnet",
    maxTurns=6,
)

doc_writer = sdk.AgentDefinition(
    description="Docstring and README writer",
    prompt="You're a technical writer...",
    tools=["Read", "Write", "Edit"],
    model="haiku",
    maxTurns=5,
)

opts = sdk.ClaudeAgentOptions(
    system_prompt=(
        "You're a PR review orchestrator. "
        "Call code-reviewer, security-scanner, and doc-writer in parallel..."
    ),
    allowed_tools=["Agent", "Read"],
    agents={
        "code-reviewer": code_reviewer,
        "security-scanner": security_scanner,
        "doc-writer": doc_writer,
    },
    task_budget=sdk.TaskBudget(total=100000),
    permission_mode="bypassPermissions",
)

async def review_pr(pr_diff: str):
    async for message in sdk.query(
        prompt=f"Review this PR diff:\n\n{pr_diff}\n\nRun all three agents in parallel...",
        options=opts,
    ):
        if isinstance(message, sdk.ResultMessage):
            print(f"Total cost: ${message.total_cost_usd:.4f}")
```

### 3.8 TaskBudget 成本控制

```python
class TaskBudget(TypedDict):
    total: int  # Token预算上限

# 两级安全网
# L1: TaskBudget(total=100000) — 全局Token上限
# L2: AgentDefinition.maxTurns=6 — 子代理级别最大循环数
```

### 3.9 子代理生命周期钩子

```python
def on_agent_start(hook_input: sdk.SubagentStartHookInput) -> None:
    print(f"▶ {hook_input.agent_type} started (id: {hook_input.agent_id[:8]})")

def on_agent_stop(hook_input: sdk.SubagentStopHookInput) -> None:
    print(f"■ {hook_input.agent_type} done")
    # hook_input.agent_transcript_path 含完整子代理对话日志

opts = sdk.ClaudeAgentOptions(
    hooks={
        "SubagentStart": [sdk.HookMatcher(hook_callback=on_agent_start)],
        "SubagentStop": [sdk.HookMatcher(hook_callback=on_agent_stop)],
    },
)
```

## 第四部分：Agent Skills 开放标准

### 4.1 Skills 架构总览

Agent Skills 是 Anthropic 于 2025年12月发布的开放标准，已被 33+ Agent 产品采纳（Claude Code / OpenAI Codex / GitHub Copilot / VS Code / Cursor / Gemini CLI 等）。

**核心设计**：Skill 是一个**文件夹**，不是单个 Markdown 文件。

```
skill-name/
├── SKILL.md          # 必需：YAML元数据 + Markdown指令（约500行以内）
├── scripts/          # 可选：可执行脚本（Python/Bash/JS）
├── references/       # 可选：按需加载的参考文档
└── assets/           # 可选：模板、图片等静态资源
```

### 4.2 三层渐进式加载机制

| 层级 | 内容 | 加载时机 | Token成本 |
|------|------|----------|-----------|
| L1 | YAML frontmatter (name + description) | 会话启动时始终加载 | ~100 tokens/skill |
| L2 | SKILL.md body 正文 | 任务匹配description时 | ~500行以内 |
| L3 | references/ + assets/ | SKILL.md指令引用时按需 | 按需 |

**关键价值**：即使安装 50 个 Skill，初始加载仅 ~5000 tokens。相比单体式提示词，上下文使用量减少约 90%。

### 4.3 SKILL.md 格式规范

```yaml
---
name: pdf-processing              # 必填: 1-64字符，小写字母+连字符
description: >                    # 必填: 1-1024字符，含触发关键词
  Extract text and tables from PDF files, fill PDF forms,
  and merge multiple PDFs. Use when working with PDF documents
  or when the user mentions PDFs, forms, or document extraction.
license: Apache-2.0               # 可选
metadata:                         # 可选
  author: example-org
  version: "1.0"
disable-model-invocation: false   # 可选: true时隐藏Skill，仅手动触发
---
# PDF Processing

## When to use this skill
Use this skill when the user needs to work with PDF files...

## How to extract text
1. Use pdfplumber for text extraction...
2. When API returns non-200, read references/api-errors.md
```

**name 命名规则**：
- ✅ `pdf-processing`, `data-analysis`, `code-review`
- ❌ `PDF-Processing`（大写）, `-pdf`（连字符开头）, `pdf--processing`（连续连字符）

### 4.4 description 写作要点

Description 是**路由规则**，不是功能介绍。模型通过它判断何时加载 Skill。

**好的示例**：
```
Analyze CSV and tabular data files — compute summary statistics,
add derived columns, generate charts, and clean messy data. Use this
skill when the user has a CSV, TSV, or Excel file and wants to
explore, transform, or visualize the data, even if they don't
explicitly mention "CSV" or "analysis."
```

**差的示例**：
```
Helps with PDFs.
```

**检查方法**：写完 Description 后删掉整个 Skill 只保留这一行，看模型能否判断何时加载。

### 4.5 Anthropic 九类 Skill 分类体系

| 类别 | 定义 | 典型例子 |
|------|------|----------|
| 库和API参考 | 教Agent正确使用内部库/CLI/SDK | billing-lib, internal-platform-cli |
| 产品验证 ★ | 教Agent怎么测试/验证代码是否工作 | signup-flow-driver, checkout-verifier |
| 数据获取与分析 | 连接数据栈，提供查询路径 | funnel-query, datadog |
| 业务流程自动化 | 把重复工作流压成一条命令 | standup-post, weekly-recap |
| 代码脚手架 | 生成框架模板和样板代码 | new-migration, create-app |
| 代码质量与审查 | 强制代码风格、审查流程 | adversarial-review, code-style |
| CI/CD与部署 | 推代码、部署、监控 | babysit-pr, deploy |
| 运维手册 | 拿症状→多工具排查→结构化报告 | oncall-runner, log-correlator |
| 基础设施操作 | 日常维护，带破坏性操作护栏 | orphans, cost-investigation |

> ★ **产品验证类 Skill 回报最大** — Anthropic 内部经验表明，验证类 Skill 对输出质量的影响最可衡量、最显著。

### 4.6 写 Skill 的核心原则

1. **不要写模型已经知道的废话** — 高质量 Skill 补充模型默认不知道的信息（内部约定、常见错误、特定系统真实行为、工具链限制、团队判断标准）
2. **一定要有 Gotchas（踩坑记录）** — 每一条都有血有肉的具体记录，Agent 哪里犯错就加一条
3. **使用渐进式披露** — 不把所有内容塞进 SKILL.md，详细 API/长示例/模板放 references/
4. **不要把 Claude 绑得太死** — 给信息和边界，不规定每一步机械执行
5. **尽量用脚本** — 重复动作做成 scripts/，让模型调用而非每次重新生成

### 4.7 Instructions vs Scripts

| 维度 | Instructions（指令） | Scripts（脚本） |
|------|----------------------|-----------------|
| 提供什么 | 经验和判断 | 能力和执行 |
| 例子 | "Stripe返回200不意味支付成功，需检查payment_events表" | `check_payment_events()` 函数 |
| 为什么需要 | 模型知道该查什么 | 模型知道怎么查 |
| 依赖 | 判断力 | 执行精度 |

> 两者缺一不可：只有Script，模型知道怎么查但不知为什么查。只有Instructions，每次都得重新实现。

## 第五部分：MCP（Model Context Protocol）

### 5.1 MCP 核心定位

**MCP 是专业厨房，Skills 是菜谱。** 厨房有工具/食材/设备（MCP提供能力），菜谱告诉你如何组合成一道菜（Skills定义流程）。

### 5.2 USB-C 比喻

MCP 之前：N个Agent × M个工具 = N×M 种集成方式  
MCP 之后：N + M（每个工具实现MCP协议一次，所有Agent通用）

### 5.3 配置示例

```json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"]
    },
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres", "postgresql://localhost:5432/mydb"]
    },
    "slack": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-slack"]
    }
  }
}
```

### 5.4 常用 MCP Servers

| MCP Server | 功能 | 使用场景 |
|------------|------|----------|
| github | PR操作、Issue管理、代码搜索 | 自动化代码审查、项目管理 |
| slack | 发送消息、读取频道 | 团队通知、状态更新 |
| postgres | 数据库查询 | 数据分析、生成报告 |
| filesystem | 高级文件操作 | 批量文件处理 |
| puppeteer | 浏览器自动化 | Web抓取、UI测试 |
| google-drive | 文件上传下载 | 文档管理 |

### 5.5 MCP 注意事项

- ✅ 按需接入，不要一次连 20 个 Server（占用上下文）
- ✅ 权限最小化，只给 Agent 必要的访问权限
- ✅ 优先使用官方或社区维护的 MCP Server
- ❌ 不要让 Agent 跑 shell 命令操作外部服务（不安全、不可控）

### 5.6 Agent 四层架构（Agent Loop + Runtime + MCP + Skills）

```
┌─────────────────────────────────────────┐
│           Agent Loop（推理层）            │
│       "模型决定做什么"                     │
├─────────────────────────────────────────┤
│           Runtime（执行层）               │
│       "执行环境怎么跑"                     │
├─────────────────────────────────────────┤
│      MCP（连接层）    │  Skills（方法论层） │
│    "能访问什么"        │  "怎么做才对"      │
└─────────────────────────────────────────┘
```

**核心约束**：
- 推理层不要塞具体流程 → 流程进 Skill
- 连接逻辑不要写在提示词里 → 连接进 MCP

## 第六部分：CLAUDE.md 与 Hooks

### 6.1 四件套全景图

| 组件 | 类比 | 解决问题 | 形式 | 加载方式 | 执行方式 |
|------|------|----------|------|----------|----------|
| CLAUDE.md | 员工手册 | "这是什么项目" | Markdown | 自动加载 | LLM推理 |
| Skills | SOP流程 | "遇到X怎么做" | 文件夹 | 按需触发 | LLM推理 |
| MCP | 工具箱接口 | "能用什么工具" | Server服务 | 按需连接 | LLM推理 |
| Hooks | 流水线钩子 | "自动执行任务" | Shell脚本 | 事件触发 | 确定性脚本 |

### 6.2 CLAUDE.md 编写框架（WHY/WHAT/HOW）

```markdown
# CLAUDE.md

## 项目概览（WHY）
这是一个面向 B2C 的电商项目，支持多语言、多币种。

## 技术栈与目录结构（WHAT）
Next.js + TypeScript + Tailwind CSS

## 开发规范（HOW）
- 使用 pnpm 作为包管理器
- 提交前运行 pnpm lint && pnpm test
- API Key 绝对不能提交到代码里
```

**核心原则**：
- 控制在 300-500 行以内
- 只放全局通用信息
- 不把工作流写进 CLAUDE.md（用 Skills）
- 指向而非复制（引用文件路径而非粘贴代码）

### 6.3 三层级配置

```
~/.claude/CLAUDE.md          ← 全局：所有项目通用偏好
项目根目录/CLAUDE.md          ← 项目级：团队共享规范
项目子目录/CLAUDE.md          ← 模块级：特定目录规则
```

### 6.4 Hooks 事件与场景

| 事件 | 触发时机 | 典型场景 |
|------|----------|----------|
| PreToolUse | 工具执行前 | 验证、权限检查 |
| PostToolUse | 工具执行后 | 格式化、测试、通知 |
| SessionStart | 会话开始 | 环境初始化 |
| Compact | 上下文压缩时 | 保存重要信息 |

**Hooks 配置示例**：
```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{"type": "command", "command": "pnpm lint-staged"}]
      }
    ]
  }
}
```

### 6.5 四件套协作完整流程

```
会话开始 → 自动读取 CLAUDE.md → 理解项目上下文
用户下达任务 → 触发对应 Skill → Agent 按流程执行
执行过程中 → 需要操作外部工具 → 通过 MCP 调用
特定事件触发 → Hooks 自动执行 → 完成自动化任务
```

## 第七部分：Agent 工程化最佳实践

### 7.1 从0到上线的落地清单

**1）先把单 Agent 做到可控**
- 写清楚完成定义：格式、必含字段、边界提示、失败条件
- 固定输出格式：小标题、表格、JSON
- 加最小评估集：10-30个真实样本

**2）出现信号再上多Agent**
- 只在这三类情况优先考虑：上下文噪音/搜索空间大/工具冲突
- 按信息流切分，不按任务类型切分

**3）把流程写成 Skill，别写进 Prompt**

**4）外部系统统一走 MCP**

**5）最后再谈"聪明"**

### 7.2 常见 6 坑自查

| # | 问题 | 正确做法 |
|---|------|----------|
| 1 | 把团队流程写进 System Prompt | 进 Skill，用 Git 管 |
| 2 | 工具越接越多但没有先后顺序 | Skill 定义流程骨架 |
| 3 | 有连接但没权限边界 | MCP 权限管理不是可选项 |
| 4 | 输出没有格式标准 | Skill 里定义固定输出格式 |
| 5 | 上来就多 Agent | 先把单 Agent 做到位 |
| 6 | 没有评估集 | 哪怕 10 个样本也比没有强 |

### 7.3 会议准备 Skill 模板（最简起步）

```yaml
---
name: meeting-prep
description: 为会议生成可复用材料。Use when preparing meeting materials or generating agendas.
---
## 触发条件
用户说"准备会议/写会议材料/生成议程"

## 输入
- 会议主题
- 参会人（可选）
- 项目名或Notion链接（可选）

## 工作流程（严格按顺序）
1. 通过MCP搜索项目主页与最近2次会议纪要
2. 提取现状、未决问题、关键指标
3. 生成议程（含每项目标与预计时长）
4. 生成"需要对齐的问题清单"（按优先级排列）
5. 输出一页版会议材料

## 输出格式（固定）
- 📋 背景（一段话，≤100字）
- 📊 现状（3条，每条一句话）
- 🎯 本次要决策的1-3件事
- ⚠️ 风险与依赖（最多5条）
- ➡️ 下一步（负责人/截止时间/交付物）
```

### 7.5 核心结论

> **Agent 的竞争力不在于模型有多聪明，而在于你能把多少"人的经验"系统化地喂给它。Skills 是经验的载体，MCP 是能力的通道，两者缺一不可。**
>
> **未来很长一段时间，你的竞争力不是"会不会用模型"，而是"能不能把工作拆成可验证、可复用、可规模化的流程"。**

## 第八部分：中文社区深度解读精华

### 8.1 CLAUDE.md / Skills / MCP / Hooks 实战（popring.cn）

**核心区别**：
- CLAUDE.md + Skills = **知识层**（告诉Agent怎么思考）
- MCP + Hooks = **能力层**（让Agent能动手）

**实战场景：自动化PR审查+团队通知**
1. CLAUDE.md 提供项目上下文（代码规范、审查重点）
2. Skill 定义审查流程（逐文件检查→分级报告→PR留言）
3. MCP 提供执行能力（GitHub PR操作 + Slack通知）
4. Hooks 自动格式化（编辑后运行 lint-staged）

### 8.2 2026 Agent 正确姿势（53ai.com，基于Anthropic四篇博客）

**五条核心结论**：
1. 从单 Agent 开始，多 Agent 是"更贵+更难控"
2. 多 Agent 最常见价值就三种：上下文保护、并行化搜索空间、专业化分工
3. 模型缺的不是 IQ，是积累的流程与标准
4. Skills 解决"教它怎么做"，MCP 解决"让它能访问什么"
5. 最稳组合：Agent Loop + Runtime + MCP + Skills

### 8.3 Anthropic 内部 Skill 方法论精髓

1. **Skill 不是提示词工程，是上下文工程** — 本质是沉淀组织隐性知识
2. **Gotchas 是 Skill 含金量最高的部分** — 每一条都有血有肉
3. **尽量用脚本** — 不让模型把有限上下文浪费在重复劳动上
4. **Description 是路由规则** — 描述用户意图，不是罗列功能
5. **渐进式披露** — 文件夹结构本身就是上下文优化的设计模式

### Subagent 完整生命周期

```
定义 → 加载(会话启动) → 匹配(description路由) →

```

### Claude Code 权限模式

| 模式 | 行为 | 适用场景 |
|------|------|----------|
| default | 标准权限弹窗 | 日常开发 |
| acceptEdits | 自动接受编辑 | 信任的子代理 |
| auto | 自动批准全部 | 沙盒环境 |
| dontAsk | 拒绝需确认操作 | 只读分析 |
| bypassPermissions | 绕过所有权限 | 完全信任场景 |
| plan | 仅规划不执行 | 方案评估 |

### SDK 关键类

| 类名 | 用途 |
|------|------|
| AgentDefinition | 子代理配置数据类（description/prompt/tools/model/skills/hooks等） |
| ClaudeAgentOptions | 完整编排选项（system_prompt/agents/task_budget/permissions） |
| TaskBudget | Token预算控制（total字段） |
| SubagentStartHookInput | 子代理启动事件数据 |
| SubagentStopHookInput | 子代理停止事件数据（含agent_transcript_path） |
