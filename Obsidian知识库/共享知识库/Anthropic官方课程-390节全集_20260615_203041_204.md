## <a id="ch1"></a>第1章：构建有效的 AI Agent

> 原文：[Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents) (2024.12)

### 1.1 核心定义

Anthropic 将所有变体统称为 **Agentic Systems（智能体系统）**，并区分两个架构层级：

| 类型 | 定义 | 特点 |
|------|------|------|
| **Workflows（工作流）** | LLM + 工具通过预定义代码路径编排 | 可预测、一致性强 |
| **Agents（智能体）** | LLM 动态指导自身流程和工具使用 | 灵活、自主决策 |

### 1.2 何时使用 Agent

**三原则**（按优先级排序）：

1. **简单性优先**: 先找最简单的方案，仅在需要时增加复杂度
2. **透明度**: 显式展示 Agent 的规划步骤
3. **ACI 设计**: 像设计 HCI 一样精心设计 Agent-Computer Interface（工具文档与测试）

**权衡判断**:
- Agentic 系统用延迟和成本换取更好的任务表现
- 对很多应用来说，增强单次 LLM 调用（检索 + 上下文示例）通常已足够

### 1.3 六大 Agentic 模式

#### 模式1: Augmented LLM（增强型LLM）
基础构建模块，LLM 增强以下能力：
- **检索（Retrieval）**: 搜索外部知识
- **工具（Tools）**: 调用 API、执行代码
- **记忆（Memory）**: 跨会话保持状态

#### 模式2: Prompt Chaining（提示链）
```
步骤1 → 步骤2 → 步骤3 → 输出
        ↑Gate    ↑Gate
```
- 将任务分解为固定子任务序列
- 适合可清晰分解的任务
- 示例: 生成营销文案→翻译为多语言

#### 模式3: Routing（路由）
```
输入 → [分类器] → 路由到专项处理器A/B/C
```
- 输入分类后定向到专项下游任务
- 关注点分离，构建更专业化的 Prompt
- 示例: 简单问题→Haiku，复杂问题→Sonnet

#### 模式4: Parallelization（并行化）
**两种变体**:
- **Sectioning（分区）**: 拆分独立子任务并行执行
- **Voting（投票）**: 同一任务运行多次获取多样输出

- 示例: 一个模型处理用户查询，另一个筛查不当内容

#### 模式5: Orchestrator-Workers（编排者-工人）
```
中央编排LLM → 动态分解 → Worker A/Worker B/Worker C → 汇总
```
- 中央 LLM 动态分解任务，分配给 Worker LLM
- 关键区别: 子任务不是预定义的，而是编排者根据输入动态确定
- 示例: 编码产品对多文件进行复杂变更

#### 模式6: Evaluator-Optimizer（评估器-优化器）
```
生成LLM → 输出 → 评估LLM → 反馈 → 生成LLM（循环）
```
- 一个 LLM 生成响应，另一个提供评估和反馈
- 适合有明确评估标准的任务
- 示例: 文学翻译（评估器捕捉微妙差异）

### 1.4 框架使用指南

建议路径: **先用 LLM API 直接构建 → 理解底层原理 → 再考虑框架**

常用框架:
- Claude Agent SDK
- AWS Strands Agents SDK
- Rivet (拖拽式 LLM 工作流)
- Vellum (构建测试复杂工作流)

**警告**: 框架增加抽象层，可能掩盖底层 Prompt 和响应，使调试困难。

## <a id="ch2"></a>第2章：上下文工程

> 原文：[Effective Context Engineering for AI Agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) (2025.09)

### 2.1 核心概念

从 **Prompt Engineering（提示工程）** 到 **Context Engineering（上下文工程）** 的范式转变：

> "Building with language models is becoming less about finding the right words and phrases for your prompts, and more about answering the broader question of 'what configuration of context is most likely to generate our model's desired behavior?'"

**上下文** = 从 LLM 采样时包含的 token 集合
**工程问题** = 优化这些 token 的效用，以一致地达成期望结果

### 2.2 上下文工程的 5 个关键维度

| 维度 | 描述 | 关键实践 |
|------|------|----------|
| **选择** | 哪些 token 进入上下文？ | 相关性排序、去噪、优先级分层 |
| **结构化** | token 如何组织？ | 格式一致性、层级标题、代码块 |
| **排序** | token 的呈现顺序？ | 最重要信息放首位/末位 |
| **压缩** | 如何减少 token 总量？ | 摘要、缓存、渐进式加载 |
| **时机** | token 何时注入？ | 静态预加载 vs 动态按需检索 |

### 2.3 六大破裂模式

Agent 设计中常见的六类上下文管理失效：

1. **上下文污染**: 无关信息淹没关键指令
2. **上下文漂移**: 长对话中 Agent 逐渐偏离原始目标
3. **上下文遗忘**: 关键信息被截断或逐出窗口
4. **上下文过载**: 窗口塞满导致模型忽略一半指令
5. **格式崩溃**: 结构化输出退化
6. **注意力稀释**: 多任务指令导致各任务表现下降

### 2.4 上下文工程最佳实践

- **CLAUDE.md ≤ 200 行**: 臃肿的 CLAUDE.md 不会让 Claude 遵守更多规则，只会让重要的规则淹没在噪音中
- **渐进式信息披露**: 元数据→全文→引用文件→代码，逐层按需加载
- **Prompt 缓存**: 共享的系统 Prompt 复用缓存，降成本
- **子代理隔离**: 父代理保持简洁编排，子代理独立上下文窗口

## <a id="ch3"></a>第3章：Agent Skills

> 原文：[Equipping Agents for the Real World with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) (2025.10)
> 开源标准：agentskills.io (2025.12.18)

### 3.1 什么是 Skills

Skills 是有组织的文件夹，包含指令、脚本和资源，Agent 可以动态发现和加载。**Skill 之于 Agent，如同入职指南之于新员工。**

```
skill-name/
├── SKILL.md          # 核心指令文件（YAML frontmatter + Markdown 正文）
├── reference.md      # 细分参考文件
├── forms.md          # 特定场景文件
└── scripts/          # 可执行脚本
```

### 3.2 三层渐进式信息披露（Progressive Disclosure）

| 层级 | 内容 | 加载时机 | Token 成本 |
|------|------|----------|-----------|
| **第1层** | name + description (frontmatter) | 启动时预加载到 system prompt | 极低 |
| **第2层** | SKILL.md 正文 | 任务匹配时由 Agent 主动读取 | 中等 |
| **第3层+** | 捆绑的引用文件、代码文件 | 按需由 Agent 导航发现 | 按使用付费 |

### 3.3 Skills 设计最佳实践

1. **从评估开始**: 在代表性任务上运行 Agent，观察瓶颈，增量构建 Skill
2. **为规模化设计**: SKILL.md > 500 行时拆分到独立文件
3. **以 Claude 视角思考**: 监控 Claude 在实际场景中如何使用 Skill，观察非预期轨迹
4. **与 Claude 共同迭代**: 让 Claude 捕获成功方法和常见错误，转化为可复用的 Skill 内容

### 3.4 Skills 安全注意事项

- 仅从可信来源安装 Skills
- 安装前彻底审计内容（特别是代码依赖和外部网络连接）
- 恶意 Skills 可能引入环境漏洞或指示 Agent 泄露数据

## <a id="ch4"></a>第4章：Claude Agent SDK 五大子代理模式

> 原文：[Claude Agent SDK: 5 Subagent Patterns That Cut Cost & Raise Quality (2026)](https://claudeguide.io/claude-agent-subagents-pattern)

### 4.0 为什么需要子代理

单 Agent 循环的两大失败模式：

1. **上下文膨胀（Context Bloat）**: 每步推理、每次重试都堆积到同一上下文窗口。30 轮后，150K token 的成本是 $0.45/轮（仅输入）
2. **角色漂移（Drift）**: "你是代码审查员、翻译、测试编写者" = 三个 Prompt 混在一起，模型在所有角色之间折中

**子代理修复两者**: 父代理保持小而编排化。每个子代理获得紧凑的 Prompt、全新的上下文、仅其需要的工具。

### 4.1 模式一：分而治之（Divide-and-Conquer）

**形态**: 父代理分解任务为 N 个独立子任务 → 扇出每个子代理 → 汇总结果

**胜出场景**: 真正可并行的工作（如转换 50 个文件、总结 20 个 PDF）
**反模式**: 子任务有隐藏依赖关系

**成本**: 20 文件摘要 → 单 Agent $0.85 vs 子代理 $0.12（节省 86%）

### 4.2 模式二：专家路由（Specialist Routing）

**形态**: 父代理检查输入任务 → 分类 → 路由到定制子代理（code-reviewer / translator / tester / sql-writer）

**胜出场景**: 产品处理固定的任务分类。路由器 Prompt 仅 200 token，避免 8K token 的条件判断

每个专家获得:
- 聚焦的系统 Prompt (300-800 token)
- 狭窄的工具允许列表（翻译员不需要 Bash）
- 匹配任务的模型选择（翻译用 Haiku，代码审查用 Sonnet）

### 4.3 模式三：并行研究（Parallel Research）

**形态**: 派生 N 个子代理从不同角度研究同一问题 → 父代理合并

**技巧**: 角度差异化。4 个子代理 = 怀疑者、乐观者、历史学家、对立者。每个都有不同的立场

**成本**: 50 页研究报告 → 单 Agent $2.40 vs 子代理 $0.55（节省 77%）

### 4.4 模式四：评判-迭代（Judge-and-Iterate）

**形态**: 子代理 A 起草 → 子代理 B 按评分标准评判 → A 修订 → 循环直到 B 批准或达到最大迭代次数

**胜出场景**: 质量敏感输出且有明确评分标准（营销文案 vs 品牌声音、SQL vs 风格指南）
**失败场景**: 开放式创意工作（没有评分标准时，评判者反复摇摆）

**硬规则**: 
- 强制上限迭代次数（3 是最佳点）
- 设置硬性 wall-clock 超时
- 无限 judge-revise 循环是多 Agent 系统最昂贵的 bug

### 4.5 模式五：错误恢复（Error Recovery）

**形态**: 父代理捕获工具错误 → 派生"调试器"子代理 → 将诊断结果应用

**核心思想**: 父代理**不在自己的循环中调试**。将失败隔离到新上下文，调试类工作丢进一次性子代理

**为什么重要**: 一次工具失败就能污染父代理上下文 50 轮试错推理，然后降级后续每一个决策

### 4.6 成本数学

| 场景 | 单 Agent (Sonnet) | 子代理 (Haiku子+Sonnet父) | 节省 |
|------|-------------------|---------------------------|------|
| 20文件摘要 | ~$0.85 | ~$0.12 | **86%** |
| 单次Q&A(2K tokens) | ~$0.012 | ~$0.018 | **-50% (更差)** |
| 50页研究报告 | ~$2.40 | ~$0.55 | **77%** |
| 翻译一段 | ~$0.004 | ~$0.006 | **-50% (更差)** |
| 30轮编码循环 | ~$1.90 | ~$0.70 | **63%** |

**规律**: 子代理在**规模与复杂性**上胜出，在**单次简单任务**上输掉。

### 4.7 何时不使用子代理

- 延迟敏感 UX（聊天回复 < 1.5s）
- 单次任务无分解机会
- 无明确专业化（每个子代理需要独立的系统 Prompt）
- 微小上下文窗口（编排开销超过节省）

### 4.8 常见陷阱

1. **上下文泄漏**: 子代理返回完整转录而非摘要 → 强制返回 schema: `{result, citations, confidence}`
2. **无限循环**: 始终设置最大迭代次数 + wall-clock 超时
3. **输出格式不匹配**: 使用 `responseFormat: "json"` 或 schema 验证
4. **工具过度授权**: 摘要器不需要 bash，翻译器不需要 web_search
5. **忽略缓存**: 共享系统 Prompt 的子代理应复用缓存

## <a id="ch5"></a>第5章：长期运行 Agent 的有效驾驭

> 原文：[Effective Harnesses for Long-Running Agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) (2025.11)

### 5.1 核心挑战

Agent 必须在离散会话中工作，每个新会话开始时没有之前工作的记忆。**就像每班工程师换岗时完全失忆。**

### 5.2 双重解决方案

**初始化 Agent（Initializer Agent）**:
- 写 `feature_list.json`（200+ 功能点，初始全部标记为 failing）
- 写 `init.sh`（一键启动开发环境）
- 初始 git commit

**编码 Agent（Coding Agent）**:
- 每次会话只做**一个功能**
- 结束时提交 git + 写 progress 文件
- 开始时读 git log + 进度文件了解状态

### 5.3 四大失败模式与对策

| 失败模式 | 对策 |
|----------|------|
| 过早宣布完成整个项目 | 功能清单文件，每次只选一个功能 |
| 环境留有 Bug 或未记录进度 | 开始读进度+git，结束写提交+进度 |
| 未充分测试就标记完成 | 显式要求端到端测试（如 Puppeteer MCP） |
| 每次都要重新摸索如何运行 App | `init.sh` 脚本标准化启动流程 |

### 5.4 典型会话启动序列

```
1. pwd → 确认工作目录
2. 读 claude-progress.txt → 了解最近进展
3. 读 feature_list.json → 选最高优先级未完成功能
4. 运行 init.sh → 启动开发服务器
5. Puppeteer MCP 做基础端到端测试 → 确认未卡死
6. 开始新功能开发
```

### 5.5 开放问题

- 单通用 Agent 还是多专用 Agent 架构更好？（测试 Agent / QA Agent / 清理 Agent）
- 如何从 Web 应用开发推广到其他领域（科研、金融建模）？

## <a id="ch6"></a>第6章：Claude Code 五大工程机制

> 来源：Anthropic 官方文档 Claude Code Advanced Patterns (2026.03)

### 6.1 CLAUDE.md — 项目级上下文注入

**本质**: 静态指令，加载到每次对话中

**层级化**:
```
项目根/CLAUDE.md → 子目录/.claude/CLAUDE.md → .claude/rules/*.md
```
Claude Code 向上遍历目录树，自动发现并加载沿途的 CLAUDE.md

**约束**: 保持 ≤ 200 行。超过后移至 Skills 或路径特定规则

### 6.2 Hooks — 生命周期自动化

**本质**: 确定性自动化（完全绕过模型判断）

**触发时机**:
- `PreToolUse` — 工具调用前验证/阻止
- `PostToolUse` — 工具调用后反应（如 linting）
- `UserPromptSubmit` — 拦截发送内容
- `SessionStart` — 每会话加载一次

**典型场景**: 保存时自动格式化、编辑后运行测试、完成时发通知、纠正行为偏差

### 6.3 MCP — 外部系统接入

**本质**: 让 Claude 访问外部系统的标准协议

**适用场景**: 需要**推理外部状态**的操作（查询数据库、访问 GitHub、发 Slack 消息）

### 6.4 Octet-Stream / Agents — 子代理

**配置方式**:
```yaml
---
name: code-reviewer
description: Expert code review specialist. Use PROACTIVELY after code changes.
tools: read, grep, glob  # 可选，省略则继承全部
model: claude-haiku-4-5  # 可选
---
```

**管理**: `/agents` 命令提供交互式管理界面

**自动调用条件**: description 中使用 "use PROACTIVELY" 或 "MUST BE USED"

### 6.5 Skills — 任务特定指令包

已在前述第3章详述。

### 6.6 五大机制决策矩阵

| 维度 | CLAUDE.md | Skills | Subagents | Hooks | MCP |
|------|-----------|--------|-----------|-------|-----|
| **触发方式** | 每次会话注入 | 按需发现加载 | 父代理派生 | 确定性事件 | 按需调用 |
| **本质** | 静态指令 | 领域知识 | 委派工作 | 确定性自动化 | 外部工具访问 |
| **典型用例** | "用pnpm不用npm" | PR评审清单 | 隔离繁琐工作 | 保存时自动格式化 | 查询数据库 |
| **绕过模型** | 否 | 否 | 否 | **是（唯一）** | 否 |

## <a id="ch7"></a>第7章：Agent 评估方法

> 原文：[Demystifying Evals for AI Agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) (2026.01)

### 7.1 评估结构

**评估（Eval）= 输入 + 预期行为 + 评分规则**

### 7.2 Agent 评估的特殊挑战

| 维度 | 简单 LLM 调用 | Agent 系统 |
|------|-------------|-----------|
| 评估范围 | 单次响应 | 多轮交互序列 |
| 正确性判断 | 输出匹配 | 过程+结果 |
| 状态影响 | 无 | 可能修改环境状态 |
| 工具使用 | N/A | 需要评估工具选择的合理性 |

### 7.3 评估分类体系

1. **功能评估**: 特定输入的正确输出
2. **行为评估**: 复杂任务中的过程质量
3. **回归评估**: 新版本不破坏已有功能
4. **安全评估**: 边界条件和恶意输入

## <a id="ch10"></a>第10章：全域 Agent 设计原则总结

### 10.1 复杂度阶梯（Complexity Ladder）

```
单次 LLM 调用
    ↓ 需要检索时
增强型 LLM（检索+工具+记忆）
    ↓ 需要多步骤时
工作流（链式/路由/并行）
    ↓ 需要动态规划时
编排者-工人模式
    ↓ 需要迭代优化时
评估器-优化器模式
    ↓ 需要长期自主时
自主 Agent（多子代理 + 长运行驾驭）
```

**核心原则**: 仅在更简单的方案确实不足时才增加复杂度。

### 10.2 模式选择决策树

```
任务是否可清晰分解为固定步骤？
├─ 是 → Prompt Chaining
│   └─ 步骤可并行？ → Parallelization
├─ 否 → 是否有明确的任务分类？
│   ├─ 是 → Routing
│   └─ 否 → 是否需要动态分解？
│       ├─ 是 → Orchestrator-Workers
│       │   └─ 需要迭代质量改进？ → Judge-and-Iterate
│       └─ 否 → 需要长期自主？→ Agent + Long-Running Harness
```

### 10.3 韧性设计（Resilience Design）

1. **错误隔离**: 子代理失败不污染父代理上下文 → Error Recovery 模式
2. **状态恢复**: git + progress 文件实现跨会话状态接力
3. **护栏优先**: Hooks 强制执行关键约束（模型可忽略 CLAUDE.md，但离不开 Hook）
4. **可观测性**: 五维评估（完成率/效率/正确性/可靠性/安全性）
5. **渐进式授权**: 读写权限分离、从模拟到生产

### 10.4 上下文优化核心公式

```
有效上下文 = 相关 token / 总 token
```

优化策略:
- **提升分子**: 相关 token 精炼（CLAUDE.md ≤ 200行）
- **降低分母**: 无关 token 移除（子代理隔离、Progressive Disclosure）
- **降低成本**: Prompt 缓存复用
