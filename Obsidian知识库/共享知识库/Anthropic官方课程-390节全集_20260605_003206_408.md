## 一、Claude Code 扩展体系全景

### 1.1 扩展层架构

Claude Code 提供 7 层扩展机制，从持久上下文到团队协作：

| 扩展层 | 作用 | 加载时机 | 典型用例 |
|--------|------|----------|----------|
| **CLAUDE.md** | 持久项目上下文 | 每次会话始终加载 | 技术栈、架构约定、"始终用 pnpm 而非 npm" |
| **Skills** | 可复用知识+可调用工作流 | 按需加载 | `/deploy` 部署清单、API 文档模式 |
| **Sub-agents** | 隔离上下文执行，返回摘要 | 需要时派生 | 研究任务（读大量文件但只返回关键发现） |
| **Agent Teams** | 协调多个独立 Claude Code 会话 | 需要并行时创建 | 并行审查（安全/性能/测试同时进行） |
| **Code Intelligence** | 语言服务器导航+诊断 | 持续运行 | 类型语言、大型代码库的符号跳转 |
| **MCP** | 连接外部服务 | 配置后常驻 | 查询数据库、发送 Slack、控制浏览器 |
| **Hooks** | 生命周期事件触发脚本/HTTP/提示/子代理 | 匹配事件时触发 | 每次文件编辑后运行 ESLint |

### 1.2 扩展选型决策矩阵

```
新需求 →
  只需项目规则？ → CLAUDE.md
  需要可复用工作流？ → Skills
  需要隔离上下文执行？ → Sub-agents
  需要多个会话并行协作？ → Agent Teams
  需要外部服务连接？ → MCP
  需要自动化触发？ → Hooks
```

## 二、Sub-Agents 子代理架构

### 2.1 核心原理

**Sub-Agent Protocol** 是 Anthropic 的底层协议。原生子代理支持**隔离上下文堆 (isolated context heaps)**，确保不同子代理之间上下文不互相污染。

### 2.2 编排流程

```
用户请求: "将新登录页部署到 Staging"
    │
    ▼
[主编排器] ── 分析请求
    │
    ├──► [前端代理]: "构建登录组件"
    │       └──► 返回: 已创建文件
    │
    └──► [运维代理]: "准备 Staging 环境"
            └──► 返回: 环境 URL
    │
    ▼
主编排器聚合结果 → "已成功部署到 staging.acme.com"
```

### 2.3 Sub-Agent 配置示例

```yaml
# ~/.claude/agents/my-swarm.yml
version: "1.0"
agents:
  - name: "frontend-architect"
    description: "React 19、Tailwind、Framer Motion 专家"
    model: "claude-3-5-sonnet-20241022"
    tools: ["read_file", "write_file", "browser_tool"]
    system_prompt: |
      你是前端架构师。
      - 聚焦：UX、可访问性、性能
      - 绝不编写后端逻辑
      - 组件始终使用 'tsx'

  - name: "backend-engineer"
    description: "Node.js、Prisma、PostgreSQL 专家"
    model: "claude-3-5-haiku-20241022"  # 速度优先
    tools: ["read_file", "write_file", "terminal_cmd"]
    system_prompt: |
      你是后端工程师。
      - 聚焦：安全、可扩展性、清洁 API
      - 始终使用 Zod 验证输入
```

### 2.4 Sub-Agent 调度

```bash
# 主编排器使用 swarm
$ claude "使用 @frontend-architect 重新设计 Hero 区域，@backend-engineer 创建认证 API"
```

主 Claude 实例解析路由，创建两个隔离上下文窗口，并行执行。

### 2.5 Sub-Agent vs Agent Teams

| | Sub-Agents | Agent Teams |
|---|---|---|
| **上下文** | 自有上下文窗口；结果返回调用者 | 自有上下文窗口；完全独立 |
| **通信** | 仅向主代理报告结果 | 队友之间直接通信 |
| **协调** | 主代理管理所有工作 | 共享任务列表+自协调 |
| **适用** | 只需要结果的聚焦任务 | 需要讨论和协作的复杂工作 |
| **Token 成本** | 较低：结果摘要回主上下文 | 较高：每个队友是独立 Claude 实例 |

## 三、Skills 技能系统

### 3.1 CLAUDE.md vs Skills

| 机制 | 加载方式 | 适用场景 |
|------|----------|----------|
| **CLAUDE.md** | 每次对话**始终加载** | 通用项目信息：技术栈、架构、约定 |
| **Skills** | **按需加载**（名称+描述始终在上下文中） | 特定工作流：添加命令、生成测试、代码审查 |

**核心原则**：仅在特定任务需要时放在 Skill 中，节省日常对话的上下文空间。

### 3.2 Skills 目录结构

```
.claude/skills/
├── adding-cli-command/
│   └── SKILL.md
├── generating-cli-tests/
│   └── SKILL.md
└── reviewing-cli-command/
    └── SKILL.md
```

三个存放位置（启动时自动扫描）：
- 项目级：`.claude/skills/`
- 用户级：`~/.claude/skills/`
- 插件级：Plugin 内的 `skills/`

### 3.3 SKILL.md Frontmatter 字段

| 字段 | 说明 |
|------|------|
| `name` | Skill 名称 |
| `description` | 描述（用于自动匹配） |
| `allowed-tools` | 预批准的工具列表 |
| `model` | 指定使用的模型 |
| `disable-model-invocation` | 禁止模型自动触发 |
| `user-invocable` | 是否允许用户手动触发 |
| `argument-hint` | 参数提示 |
| `context` | `fork` 表示在 Subagent 中运行 |
| `agent` | 指定运行的 Subagent |

### 3.4 两种 Skills + Sub-Agents 模式

**模式一：自定义 Sub-Agent + Skills**

在 Sub-Agent 定义中指定 `skills` 字段，Skill 同时对主 Agent 和 Sub-Agent 可用。

**模式二：Skill 自带 Sub-Agent（context: fork）**

```yaml
---
name: deep-research
description: 深入研究某主题
context: fork
agent: Explore
---
```

`context: fork` 让 Skill 始终在隔离的 Sub-Agent 中运行。

### 3.5 Skills 触发方式

| 方式 | 说明 |
|------|------|
| **Model-invoked** | Claude 根据用户请求自动匹配 Skill 描述并加载 |
| **User-invoked** | 用户输入 `/skill-name` 手动触发 |

可通过 frontmatter 控制：
- `disable-model-invocation: true` → 禁止自动触发
- `user-invocable: false` → 禁止手动触发

### 3.6 三种互补 Skill 类型

1. **生成型 (Adding)**：定义创建/添加新内容的完整工作流
2. **测试型 (Testing)**：定义测试生成和运行的工作流
3. **审查型 (Reviewing)**：验证型 Skill，像评估工具一样检查其他产出

### 3.7 Sub-Agents 与 Skills 关键区别

- **Sub-Agents 不继承 Skills**：必须在 Sub-Agent 定义中显式指定 `skills` 字段
- **SKILL.md 完整加载**：Sub-Agent 被调度时加载完整 SKILL.md，不是渐进式披露
- **可以给一个 Sub-Agent 多个 Skills**：`skills: reviewing-cli-command, reviewing-sql-queries`

## 四、Agent Teams 智能体团队

### 4.1 概述

Agent Teams 协调多个 Claude Code 实例作为一个团队协同工作。一位会话作为团队 Leader，协调工作、分配任务、综合结果。队友独立工作，各自拥有独立上下文窗口，可直接相互通信。

**要求**：Claude Code v2.1.32+，需启用 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`

### 4.2 适用场景

- **研究与审查**：多个队友同时调查问题不同方面，分享并挑战彼此的发现
- **新模块/功能**：每个队友独立负责一个部分
- **竞争假设调试**：队友并行测试不同理论，更快收敛到答案
- **跨层协调**：前端、后端、测试各由一个队友负责

### 4.3 团队架构

| 组件 | 角色 |
|------|------|
| **Team Lead** | 创建团队、派生队友、协调工作的主会话 |
| **Teammates** | 独立 Claude Code 实例，各自处理分配的任务 |
| **Task List** | 共享工作项列表，队友认领并完成 |
| **Mailbox** | 智能体间通信的消息系统 |

### 4.4 显示模式

- **In-process**：所有队友在主终端内运行。Shift+Down 循环切换队友
- **Split panes**：每个队友有自己的窗格（需要 tmux 或 iTerm2）

### 4.5 规则工具：Hooks 在 Agent Teams 中的应用

| Hook 事件 | 触发时机 |
|-----------|----------|
| `TeammateIdle` | 队友即将进入空闲状态时触发 |
| `TaskCreated` | 任务被创建时触发 |
| `TaskCompleted` | 任务被标记完成时触发 |

### 4.6 最佳实践

- **给队友足够上下文**：队友不继承 Leader 的对话历史，需在 spawn prompt 中包含任务细节
- **选择合适团队规模**：3-5 个队友是大多数工作流的最佳平衡点
- **任务粒度适中**：每个队友 5-6 个任务是合理的负载
- **避免文件冲突**：确保每个队友操作不同的文件集
- **从研究和审查开始**：新手从有清晰边界、不需要写代码的任务入手

### 4.7 Sub-Agent 定义复用为 Teammates

可通过名称引用已定义的 Sub-Agent 类型来派生队友：

```
Spawn a teammate using the security-reviewer agent type to audit the auth module.
```

队友会继承该定义的 `tools` 白名单和 `model`。团队协调工具（SendMessage 和任务管理）始终可用。

## 五、Hooks 生命周期钩子

### 5.1 概述

Hooks 是用户定义的 shell 命令、HTTP 端点或 LLM 提示，在 Claude Code 生命周期的特定点自动执行。

### 5.2 生命周期事件

**会话级（一次）**：`SessionStart`、`SessionEnd`

**轮次级（每次对话轮次）**：`UserPromptSubmit`、`Stop`、`StopFailure`

**工具级（每次工具调用）**：`PreToolUse`、`PostToolUse`、`PostToolUseFailure`、`PostToolBatch`、`PermissionRequest`、`PermissionDenied`

**Agent Team 级**：`TeammateIdle`、`TaskCreated`、`TaskCompleted`、`SubagentStart`、`SubagentStop`

### 5.3 Hook 类型

| 类型 | 说明 |
|------|------|
| **Command** (`type: "command"`) | 执行 shell 命令，通过 stdin/stdout 通信 |
| **HTTP** (`type: "http"`) | 发送 HTTP POST 请求 |
| **MCP Tool** (`type: "mcp_tool"`) | 调用已连接 MCP 服务器的工具 |
| **Prompt** (`type: "prompt"`) | 发送提示到 Claude 模型进行单轮评估，返回 yes/no |
| **Agent** (`type: "agent"`) | 派生子代理验证条件后返回决策（实验性） |

### 5.4 配置示例：阻止危险命令

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "if": "Bash(rm *)",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-rm.sh"
          }
        ]
      }
    ]
  }
}
```

### 5.5 Hook 存放位置

| 位置 | 范围 | 可共享 |
|------|------|--------|
| `~/.claude/settings.json` | 所有项目 | 否 |
| `.claude/settings.json` | 单项目 | 是（可提交到仓库） |
| `.claude/settings.local.json` | 单项目 | 否（gitignored） |
| 管理策略设置 | 组织范围 | 管理员控制 |
| Plugin `hooks/hooks.json` | 插件启用时 | 是（与插件捆绑） |
| Skill 或 Agent frontmatter | 组件活跃时 | 是（在组件文件中定义） |

### 5.6 Matcher 匹配模式

- `"*"` 或省略 → 匹配所有事件
- 仅字母/数字/下划线 → 精确匹配（支持 `|` 分隔）
- 包含其他字符 → JavaScript 正则表达式
- MCP 工具：`mcp__<server>__<tool>` 格式

### 5.7 两种命令形式

**Exec form** (args 存在)：直接派生可执行文件，无 shell 解释
**Shell form** (args 缺失)：通过 shell 执行，支持管道、`&&`、重定向

## 七、Multi-Agent API 模式

### 7.1 何时使用多智能体

**使用单智能体时**：
- 任务在一个上下文窗口内完成
- 任务是顺序的，无并行机会
- 延迟至关重要（每个额外智能体增加 ~2-30s）

**使用多智能体时**：
- 子任务可并行执行（10x 吞吐量提升）
- 不同子任务需要不同专业化或上下文
- 需要独立验证（Agent A 生产，Agent B 审查）
- 总工作量超出单个上下文窗口
- 需要处理大量独立项目（fan-out 模式）

### 7.2 Pattern 1：并行扇出 (Parallel Fan-Out)

同时处理 N 个独立项目。使用 `claude-haiku-4-5` 处理单项（便宜快速），`claude-opus-4-6` 做最终综合。

### 7.3 Pattern 2：层次化编排 (Hierarchical Orchestration)

编排器分解任务 → 派生工作代理 → 收集并综合结果。每个子任务包含置信度评分。

### 7.4 Pattern 3：检查/验证代理 (Checker/Verifier)

Agent A 生成 → Agent B 独立验证。特别适用于代码生成和需要精确度的金融计算。

生成-验证-重新生成循环，最多尝试 N 次，每次将验证反馈注入下一次生成。

### 7.5 Pattern 4：共享上下文通信 (Shared Context)

顺序代理管道，每个代理构建在前一个代理的输出之上。维护共享历史和状态对象。

```
原始数据分析 → 趋势解读 → 执行摘要撰写 → 准确性审查
```

### 7.6 错误恢复与韧性

多智能体工作流比单次调用更容易失败：

- 指数退避重试
- 主模型过载时自动降级到备用模型
- 区分可重试错误（RateLimitError、529 Overloaded）和不可重试错误

### 7.7 成本估算

| 模型 | 输入/百万tokens | 输出/百万tokens |
|------|----------------|-----------------|
| claude-opus-4-6 | $15.0 | $75.0 |
| claude-sonnet-4-6 | $3.0 | $15.0 |
| claude-haiku-4-5 | $1.0 | $5.0 |

按步骤、模型、并行度和预估 token 数估算每运行成本。

## 八、企业级部署 (3P Cowork)

### 8.1 三层扩展模型（优先级从高到低）

| 层 | 配置者 | 分发方式 |
|----|--------|----------|
| **Managed MCP servers** | 管理员 | `managedMcpServers` 配置键 |
| **Organization plugins** | 管理员 | 每台设备的系统目录 |
| **User extensions** | 最终用户 | 应用内 UI |

### 8.2 管理配置控制

| 键 | 效果 |
|----|------|
| `isLocalDevMcpEnabled: false` | 禁止用户添加本地 MCP 服务器 |
| `isDesktopExtensionEnabled: false` | 禁止安装本地 `.mcpb` 桌面扩展 |
| `isDesktopExtensionSignatureRequired: true` | 拒绝未签名的 `.mcpb` 扩展 |

### 8.3 推荐 MCP 服务器

**生产力套件**：Microsoft 365 (Outlook/OneDrive/SharePoint/Teams)

**协作与知识工作**：Atlassian (Jira/Confluence) · Notion · Linear · Asana · Box · GitHub · Salesforce · Stripe

**金融服务**：FactSet · LSEG · Moody's · Morningstar · PitchBook · CB Insights · Brex · EdgarTools

### 8.4 企业级安全

- MCP 服务器支持 OAuth 和 headers-helper
- 工具策略锁（allow / ask / blocked）
- 插件签名验证
- `allowManagedHooksOnly` 阻止用户/项目/插件 hooks

## 九、Claude Code 框架对比

### 9.1 三大框架（2025年12月）

| 指标 | SuperClaude v2.0.1 | Claude Flow v2.7 | BMAD Method |
|------|-------------------|------------------|-------------|
| **最适合** | 独立黑客/高级用户 | 企业团队/SaaS | 敏捷开发团队 |
| **架构** | 本地配置包装器 | Hive-Mind 集群(服务器) | 方法论+工具 |
| **核心特性** | @include 上下文系统 | SQLite 记忆+神经网络角色路由 | 强制 Plan→Architect→Implement→Review |
| **复杂度** | 低（单脚本） | 高（基础设施） | 中（流程） |
| **记忆** | 无持久化 | SQLite 持久记忆 | 流程级记忆 |

### 9.2 是否需要框架？

**使用框架的场景**：
- 代码库超过 50 个文件
- 频繁重复相同上下文（"我们用 Next.js 14 而非 12"）
- 需要持久化项目记忆

**坚持原生 claude 的场景**：
- 构建原型或脚本
- 更喜欢对提示的完全控制
- 需要最低延迟（框架增加约 500ms 开销）

## 十、最佳实践与反模式

### 10.1 Claude Code 项目组织

```
项目根/
├── CLAUDE.md              # 始终加载：技术栈、架构、约定
├── .claude/
│   ├── settings.json      # 项目级配置
│   ├── settings.local.json # 本地覆盖（gitignored）
│   ├── skills/            # 项目级 Skills
│   │   ├── deploy/
│   │   │   └── SKILL.md
│   │   └── code-review/
│   │       └── SKILL.md
│   ├── agents/            # 自定义 Sub-Agents
│   │   └── security-reviewer.md
│   └── hooks/             # Hook 脚本
│       └── block-rm.sh
└── .mcp.json              # MCP 服务器配置
```

### 10.2 核心设计原则

1. **CLAUDE.md 放通用，Skills 放特定**：不浪费日常上下文
2. **Sub-Agent 需显式指定 Skills**：不会自动继承
3. **Agent Teams 适合并行探索**：不适合顺序任务
4. **先研究再审查再实现**：Agent Teams 新手从审查和研究开始
5. **每个队友 5-6 个任务**：避免上下文切换过度
6. **避免文件冲突**：确保每个 Agent 操作独立文件集
7. **Hook 用于强制规则**：如每次文件编辑后运行 lint
8. **MCP 连接外部数据**：不将外部数据导入上下文窗口

### 10.3 反模式

| 反模式 | 正确做法 |
|--------|----------|
| CLAUDE.md 包含所有 Skill 内容 | 拆分到 Skills，按需加载 |
| 10+ 个 Agent Team 队友处理简单任务 | 3-5 个队友，从研究型任务开始 |
| 两个队友编辑同一文件 | 划分清晰的代码所有权 |
| 让 Agent Team 无人值守长时间运行 | 定期检查进度，及时调整方向 |
| Sub-Agent 定义中遗漏 `tools` 白名单 | 明确列出所需工具，最小权限原则 |

### 10.4 模型选择指南

| 场景 | 推荐模型 | 理由 |
|------|----------|------|
| 编排器/综合器 | claude-opus-4-6 | 最强推理能力 |
| 工作代理（一般） | claude-sonnet-4-6 | 性能与成本平衡 |
| 工作代理（大量并行） | claude-haiku-4-5 | ~15x 更便宜，显著更快 |
| 代码审查/验证 | claude-opus-4-6 | 关键任务需最高精度 |
