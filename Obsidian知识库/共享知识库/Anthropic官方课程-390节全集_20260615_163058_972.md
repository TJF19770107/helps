## 第一篇：Claude Code 子代理（Sub-agents）深度解析

### 1.1 Sub-agents 概述

Sub-agents 是 Anthropic 官方设计用于处理特定类型任务的专门 AI 助手。当辅助任务会用搜索结果、日志或文件内容充斥主对话上下文时，子代理在自己的上下文中完成工作，仅返回摘要。

**核心价值**：
- **保留上下文**：将探索和实现保持在主对话之外，避免上下文窗口污染
- **强制执行约束**：通过限制子代理可用的工具集实现安全边界
- **跨项目重用**：用户级子代理可在所有项目间共享
- **专门化行为**：为特定领域使用专注的系统提示
- **控制成本**：将任务路由到更快、更便宜的模型（如 Haiku）

### 1.2 内置子代理类型

| 子代理 | 模型 | 工具 | 用途 |
|--------|------|------|------|
| **Explore** | Haiku（快速低延迟） | 只读（Read/Grep/Glob） | 文件发现、代码搜索、代码库探索 |
| **Plan** | 继承主对话 | 只读（Read/Grep/Glob） | Plan Mode 下的研究规划 |
| **General-purpose** | 继承主对话 | 所有工具 | 复杂多步骤操作、代码修改 |
| statusline-setup | Sonnet | - | 配置状态行 |
| claude-code-guide | Haiku | - | 回答 Claude Code 功能问题 |

**Explore 子代理的彻底程度级别**：
- `quick`：针对性查找
- `medium`：平衡探索
- `very thorough`：全面分析

### 1.3 自定义 Sub-agent 配置

#### YAML Frontmatter 完整字段

| 字段 | 必需 | 说明 |
|------|------|------|
| `name` | ✅ | 小写字母+连字符唯一标识符 |
| `description` | ✅ | Claude 何时应委托至此子代理 |
| `tools` | ❌ | 允许的工具列表（省略则继承全部） |
| `disallowedTools` | ❌ | 禁止的工具列表（从继承/指定中删除） |
| `model` | ❌ | `sonnet`/`opus`/`haiku`/完整模型ID/`inherit` |
| `permissionMode` | ❌ | `default`/`acceptEdits`/`auto`/`dontAsk`/`bypassPermissions`/`plan` |
| `maxTurns` | ❌ | 最大代理轮数限制 |
| `skills` | ❌ | 启动时预加载的技能（注入完整内容） |
| `mcpServers` | ❌ | 限定于此代理的 MCP 服务器（内联定义或引用） |
| `hooks` | ❌ | 限定于此代理的生命周期 Hooks |
| `memory` | ❌ | 持久记忆范围：`user`/`project`/`local` |
| `background` | ❌ | `true` 以始终作为后台任务运行 |
| `effort` | ❌ | 努力级别：`low`/`medium`/`high`/`xhigh`/`max` |
| `isolation` | ❌ | `worktree` 以在隔离的 git worktree 中运行 |
| `color` | ❌ | 显示颜色：`red`/`blue`/`green`/`yellow`/`purple`/`orange`/`pink`/`cyan` |
| `initialPrompt` | ❌ | 作为主会话代理时自动提交的首个用户轮次 |

#### 子代理存储位置优先级

| 位置 | 范围 | 优先级 |
|------|------|--------|
| 托管设置 (`managed-settings.d/`) | 组织范围 | 1（最高） |
| `--agents` CLI 标志 | 当前会话 | 2 |
| `.claude/agents/` | 当前项目 | 3 |
| `~/.claude/agents/` | 所有项目 | 4 |
| Plugin 的 `agents/` 目录 | 启用插件的位置 | 5（最低） |

#### 模板示例

```yaml
---
name: code-reviewer
description: Reviews code for quality and best practices
tools: Read, Glob, Grep
model: sonnet
permissionMode: acceptEdits
memory: project
---

You are a code reviewer. When invoked, analyze the code and provide
specific, actionable feedback on quality, security, and best practices.
```

#### 工具限定的子代理生成语法

```yaml
# 限制 coordinator 只能生成 worker 和 researcher 子代理
---
name: coordinator
description: Coordinates work across specialized agents
tools: Agent(worker, researcher), Read, Bash
---
```

2. 每次调用的 `model` 参数
3. 子代理定义的 `model` frontmatter
4. 主对话的模型

### 1.5 MCP 服务器限定于子代理

## 第二篇：Agent Teams（多Agent协作）

### 2.1 核心概念

Agent Teams 是 Claude Code 的实验性功能，使多个 Claude 代理能够同时运行、共享状态并自主协作。

**启用方式**：
```bash
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=true
```

### 2.2 Agent Teams vs Sub-agents 对比

| 维度 | Sub-agents | Agent Teams |
|------|-----------|-------------|
| **并行性** | 串行执行（主代理等待子代理结果） | 多代理并行同时工作 |
| **通信** | 单向：子代理 → 主代理 | 双向：队友间可直接通信 |
| **任务分配** | 顺序委托 | 共享任务列表动态抢占 |
| **状态共享** | 无共享（仅返回结果） | 共享任务列表 + 消息通道 |
| **适用场景** | 搜索/研究/专门化子任务 | 并行化大型重构/搜索/PR审查 |
| **UI** | 嵌入主对话 | tmux/iTerm2 分窗模式 |

### 2.3 Agent Teams 工作流

1. **任务分解**：主代理将大型任务分解为原子子任务
2. **并行委派**：多个队友同时从共享任务列表领取工作
3. **队友间通信**：队友可直接 ping 其他队友协调依赖
4. **结果整合**：主代理收集中间结果并合成最终输出

### 2.4 四大用例场景

1. **大型重构**：5+ 文件同时修改，并行化减少总耗时
2. **并行搜索**：多个搜索维度的并行探索，汇总后合成
3. **PR 审查**：多角度审查（安全、性能、风格）并行运行
4. **迁移项目**：多模块同时迁移，保持一致性

### 2.5 最佳实践

- **原子化任务分解**：每个队友处理一个独立原子任务
- **明确完成标准**：任务列表中的每个条目有清晰的定义
- **避免共享冲突**：确保并行任务编辑的文件集不相交
- **统一规范**：所有队友加载相同的 CLAUDE.md 确保一致性
- **适度并行**：建议 3-5 个队友，过多增加协调开销

### 2.6 使用 Sub-agent 定义作为队友

Agent Teams 中的队友可以引用 sub-agent 类型的定义：
- 队友继承 sub-agent 的 `tools` 和 `model` 配置
- sub-agent 定义中的 markdown 正文作为额外指令附加到队友的系统提示

## 第三篇：Skills 系统深度解析

### 3.1 Skills 的核心定位

Skills 是 Claude Code 的知识传递层——定义 Claude "会什么"。每个 Skill 是一个包含 YAML frontmatter 和 Markdown 指令的 `.md` 文件。

**与四件套的关系**：
- **Skills**：知识传递层（会什么）
- **Hooks**：规则执行层（何时自动做）
- **MCP**：工具连接层（能连到什么）
- **Plugins**：生态分发层（如何分享）

### 3.2 Skill 的 Frontmatter 字段

```yaml
---
name: api-conventions
description: Team API design conventions and patterns
paths: ["src/api/**", "lib/api/**"]  # 限定激活范围
disable-model-invocation: false       # 控制谁可以调用此技能
---
```

### 3.3 技能加载生命周期

1. **启动时**：项目级 `./claude/skills/` + 用户级 `~/.claude/skills/` + 插件技能
2. **内容压缩时**：技能内容遵循压缩策略（保留优先）
3. **子代理预加载**：通过 `skills` frontmatter 字段注入完整内容

### 3.4 Skills 内容可包含

- 代码库树形可视化（完整 Python 实现）
- 领域知识编码（API 约定、错误处理模式）
- 工作流模板（PR 审查清单、部署流程）
- 工具配置（MCP 连接参数）

## 第四篇：Hooks 系统深度解析

### 4.1 Hooks 核心架构

Hooks 是用户定义的 shell 命令、HTTP 端点或 LLM 提示，在 Claude Code 生命周期的特定时间点自动执行。

### 4.2 完整 Hook 生命周期事件（24个）

| 事件 | 触发时机 |
|------|---------|
| `SessionStart` | 会话开始或恢复时 |
| `Setup` | `--init-only`/`--init`/`--maintenance` 模式启动时 |
| `UserPromptSubmit` | 用户提交提示前，Claude 处理前 |
| `UserPromptExpansion` | 用户命令展开为提示时 |
| `PreToolUse` | 工具调用执行前（可阻止） |
| `PermissionRequest` | 权限对话框出现时 |
| `PermissionDenied` | Auto Mode 分类器拒绝工具调用时 |
| `PostToolUse` | 工具调用成功后 |
| `PostToolUseFailure` | 工具调用失败后 |
| `PostToolBatch` | 完整批并行工具调用解析后 |
| `Notification` | Claude Code 发送通知时 |
| `MessageDisplay` | 助手消息文本显示时 |
| `SubagentStart` | 子代理生成时 |
| `SubagentStop` | 子代理完成时 |
| `TaskCreated` | 任务创建时 |
| `TaskCompleted` | 任务标记为完成时 |
| `Stop` | Claude 完成响应时 |
| `StopFailure` | 因 API 错误结束轮次时 |
| `TeammateIdle` | Agent Teams 队友即将空闲时 |
| `InstructionsLoaded` | CLAUDE.md 文件加载到上下文时 |
| `ConfigChange` | 配置文件在会话中更改时 |
| `CwdChanged` | 工作目录改变时 |
| `FileChanged` | 被监视的文件在磁盘上改变时 |
| `WorktreeCreate/Remove` | Worktree 创建/删除时 |
| `PreCompact/PostCompact` | 上下文压缩前后 |
| `Elicitation/ElicitationResult` | MCP 服务器请求/响应用户输入时 |
| `SessionEnd` | 会话终止时 |

### 4.3 Hook 执行流程

```
事件触发 → 匹配器过滤 → if 条件检查 → 处理程序运行 → 返回决定
```

### 4.4 五种 Hook 类型

| 类型 | 说明 | 用途 |
|------|------|------|
| `command` | Shell 命令（exec/shell 两种形式） | 本地脚本执行 |
| `http` | HTTP POST 端点 | 远程服务集成 |
| `mcp_tool` | MCP 工具调用 | 已有 MCP 服务复用 |
| `prompt` | LLM 提示评估（单轮） | AI 判断条件 |
| `agent` | 子代理验证条件（实验性） | 复杂条件判断 |

### 4.5 Hook Exit Code 设计

| 退出码 | 含义 |
|--------|------|
| `exit 0` | 无决定，继续正常流程 |
| `exit 1` | 非阻止错误（记录但不中断） |
| `exit 2` + `asyncRewake` | 后台 hook 完成，唤醒 Claude |

### 4.6 Hook 配置示例：阻止危险命令

```json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{
        "type": "command",
        "if": "Bash(rm *)",
        "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-rm.sh"
      }]
    }]
  }
}
```

### 4.7 MCP 工具 Hook 匹配模式

```
mcp__memory__.*       → 匹配 memory 服务器的所有工具
mcp__.*__write.*      → 匹配任何服务器的 write 开头工具
mcp__github__.*       → 匹配 GitHub 服务器的所有工具
```

## 第五篇：MCP 协议深度集成

### 5.1 MCP 核心概念

MCP (Model Context Protocol) 是 Anthropic 定义的标准化工具连接协议，使 Claude 能通过统一接口连接外部服务和数据源。

### 5.2 MCP 服务器类型

| 类型 | 传输方式 | 适用场景 |
|------|---------|---------|
| `stdio` | 标准输入输出 | 本地命令行工具 |
| `http` | HTTP REST | 远程服务 |
| `sse` | Server-Sent Events | 实时流式服务 |
| `ws` | WebSocket | 双向通信服务 |

### 5.3 MCP 与四件套的协同

```
Skills（知识层）→ 告诉 Claude 何时使用哪些工具
Hooks（规则层）→ 自动触发 MCP 工具调用
MCP（连接层）→ 实际执行外部操作
Plugins（分发层）→ 打包和分发 Skills + MCP 配置
```

### 5.4 2026 年 MCP 新特性

- **Elicitation 协议**：交互式工具提示，允许 MCP 工具在执行中向用户请求输入
- **按工具结果大小上限**：控制上下文预算管理
- **OAuth 集成**：安全认证流程支持

## 第七篇：多Agent编排实战模式

### 7.1 Orchestrator-Subagent 模式（TypeScript 实现）

基于 aiforanything.io 的完整生产级实现：

```
编排器(Orchestrator) → 创建子任务 → 并行子代理(Sub-agents) → 整合器(Integrator)
```

**核心代码模式**：

```typescript
// 阶段1：编排器分解任务
const subtasks = await orchestrator.decompose(complexTask);

// 阶段2：并行子代理执行
const results = await Promise.all(
  subtasks.map(task => subagentPool.execute(task))
);

// 阶段3：整合器合成输出
const finalOutput = await integrator.synthesize(results);
```

**架构特点**：
- **分层模型策略**：Orchestrator 用 Sonnet（推理质量），Sub-agents 可用 Haiku（成本效率）
- **并发控制**：p-limit 限流（建议 3-5 并发）
- **指数退避重试**：处理 API 限制和临时故障
- **成本模型**：典型编排约 $0.019/次
- **CCA 认证考点覆盖**：Mapping 到 CCA Domain 1/2/5

### 7.2 四位一体扩展架构

```
┌──────────────────────────────────────────────┐
│              Claude Code 核心                 │
├────────────┬──────────┬───────────┬──────────┤

│  知识层    │  规则层  │  连接层   │  分发层  │
├────────────┼──────────┼───────────┼──────────┤
│ "会什么"   │"何时做"  │ "能连什么" │ "如何分享" │
└────────────┴──────────┴───────────┴──────────┘
```

### 7.3 四问判断法决策树

遇到任务时，依次问：

1. **Skills**：Claude 知道怎么处理吗？（知识）
2. **Hooks**：需要在特定时机自动触发吗？（自动化）
3. **MCP**：需要连接外部工具/服务吗？（连接）
4. **Sub-agents**：需要拆分为专门化的子任务吗？（分工）

### 7.4 Cursor/Copilot 对比矩阵

| 维度 | Claude Code | Cursor | GitHub Copilot |

## 第八篇：CCA 官方认证体系

### 8.1 考试概览（2026年3月12日上线）

| 项目 | 详情 |
|------|------|
| **考试名称** | Claude Certified Architect — Foundations (CCA) |

## 第十篇：核心技能提炼——最佳实践速查

### 10.1 子代理设计原则

1. **单一职责**：每个子代理只处理一种类型任务
2. **明确的描述**：description 字段决定 Claude 何时委托
3. **最小权限**：只给子代理完成工作必需的工具
4. **合理模型选择**：简单搜索用 Haiku，复杂推理用 Sonnet/Opus
5. **隔离性考量**：需要修改代码的用 `isolation: worktree`

### 10.2 Hooks 设计原则

1. **优先使用 if 过滤**：减少不必要的进程生成
2. **timeout 合理设置**：PreToolUse 不宜过长（<30s）
3. **异步优先**：非关键路径 hook 使用 async
4. **退出码约定**：0=无决定，1=非阻止错误，2=唤醒 Claude
5. **MCP 匹配模式**：使用 `.*` 通配符覆盖服务器所有工具

### 10.3 多Agent协作原则

1. **原子化分解**：确保并行任务编辑的文件集不相交
2. **统一 CLAUDE.md**：所有队友加载相同规范
3. **适度并行**：3-5 队友最优，过多增加协调开销
4. **明确完成标准**：任务列表每个条目有清晰定义
5. **继承 sub-agent 定义**：复用工具和模型配置

### 10.4 安全管理原则

1. **最少权限**：Auto Mode 下谨慎配置允许/阻止规则
2. **托管设置强制**：企业环境使用 managed-settings.d/ 不可覆盖
3. **PreToolUse Hook 把关**：阻止危险命令（rm -rf / sudo）
4. **audit 日志**：使用 PostToolUse + PermissionDenied 记录操作
5. **按应用审批**：Computer Use 下逐应用授权桌面应用访问
