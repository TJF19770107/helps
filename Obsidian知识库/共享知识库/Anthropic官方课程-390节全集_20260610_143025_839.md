## 二、Claude Code 五大核心原语

Claude Code 的本质是**可编程的 AI 开发环境**。核心由五个脚手架原语构成：

### 2.1 子代理 (Subagents)

> 独立执行者，拥有自己的上下文窗口、工具权限、模型配置。

```
目录：.claude/agents/<name>.md
```

**核心能力**：
- 独立上下文窗口，不污染主对话
- 可配置模型、工具权限、记忆范围
- 支持后台运行、git worktree 隔离
- 三种记忆范围：user（跨项目）/ project（团队共享）/ local（个人）

**最佳实践**：
- 使用功能特定的子代理，而非通用的"QA 代理"
- 搭配技能实现渐进式披露
- 多个代理在不同分支并行开发，互不干扰
- "测试时计算"概念：同一模型不同上下文窗口可发现彼此遗漏的问题

**推荐的子代理类型**：
- 代码审查代理（只读工具，聚焦审查）
- 测试生成代理（写测试，不动生产代码）
- 搜索代理（web 工具，汇总结果）

### 2.2 命令 (Commands)

> 用户手动触发的入口点。纯用户驱动，不会被 AI 自动调用。

```
目录：.claude/commands/<name>.md
触发：/命令名
```

**核心能力**：
- 斜杠命令手动触发
- 支持参数传递（ARGUMENTS、$0、$1...）
- 团队共享（提交到 git）
- 内容只在触发时注入上下文

**最佳实践**：
- 对每天多次做的"内循环"工作流使用命令
- 适合部署、发布、测试等确定性流程
- 命令是纯用户触发入口，不占用上下文空间

### 2.3 技能 (Skills)

> AI 可根据意图自动发现和调用的知识模块。

```
目录：.claude/skills/<name>/SKILL.md
子目录：references/ / scripts/ / examples/
```

**核心能力**：
- 描述字段是触发条件（给模型看，不是给人看）
- 渐进式披露（按需加载子目录）
- context: fork 隔离运行（主对话只看最终结果）
- 子代理可预加载技能

**9条技能设计原则（Thariq）**：
1. 技能是文件夹，不是文件（渐进式披露）
2. 构建 Gotchas 部分（最高信号密度）
3. 描述是触发器，不是摘要
4. 不陈述显而易见的东西
5. 不要限制 Claude，给目标和约束
6. 包含脚本和库（scripts/ 目录）
7. 用按需钩子保护关键操作（/careful + /freeze）
8. 衡量技能使用情况
9. 投资产品验证技能

**技能描述写法示例**：
- 错误："本技能帮助用户进行代码审查"
- 正确："当用户请求代码审查、PR review、或要求检查代码质量时使用"

### 2.4 钩子 (Hooks)

> 运行在代理循环之外，确定性执行的安全机制。

```
目录：.claude/hooks/
事件类型：PreToolUse / PostToolUse / Stop / Notification
```

**关键钩子**：
- `PostToolUse`：文件编辑后自动格式化代码
- `Stop`：回合结束时推动继续工作或验证输出
- `PreToolUse`：拦截破坏性命令
- `/careful`：阻止危险操作（rm -rf / DROP TABLE / force-push）
- `/freeze`：阻止目录外的编辑

**核心洞察**：Hook 执行率 100%，指令遵从率仅 20%。确定性的事情交给钩子，创造性的事情交给模型。

### 2.5 记忆 (Memory)

> 通过 CLAUDE.md 和 .claude/rules/ 持久化。

```
项目级：CLAUDE.md（自动加载到每次对话）
个人级：~/.claude/CLAUDE.md（跨项目生效）
规则文件：.claude/rules/（paths: frontmatter 延迟加载）
代理记忆：子代理独立知识存储
```

**最佳实践**：
- CLAUDE.md 控制在 200 行以内（HumanLayer 测试 60 行效果最好）
- 用 `<important if="...">` 标签包裹领域特定规则
- 对工具强制执行的行为用 settings.json 而非 CLAUDE.md
- 代理记忆 vs 自动记忆 vs CLAUDE.md 各有归宿

## 三、Command → Agent → Skill 编排模式

五大原语经典编排：

```
用户输入 /命令名        # 命令作为入口点编排工作流
    ↓
命令调用代理            # 代理在独立上下文自主执行
    ↓
代理使用预加载技能      # 获得更精准的上下文
    ↓
命令调用技能（内联）    # 生成最终输出
```

## 四、Boris Cherny 八条核心原则

| # | 原则 | 关键洞察 |
|---|------|---------|
| 1 | 总是从计划模式开始 | Plan模式避免80%返工；计划用Opus，编码用Sonnet |
| 2 | 用子代理为问题投入更多计算 | 独立上下文窗口，并行工作 |
| 3 | 保持 PR 小而专注 | 141 PR/天，中位数118行，每个PR一个功能 |
| 4 | CLAUDE.md 控制在 200 行以内 | 超长会被忽略，60行最佳 |
| 5 | 不要微观管理 bug 修复 | 给自由度，Claude常想出更好的方案 |
| 6 | 用 PostToolUse 钩子自动格式化 | 确定性细节交给钩子 |
| 7 | 用 @claude 自动化代码审查 | 多代理独立审查相同代码 |
| 8 | 每天更新 Claude Code 并阅读更新日志 | 迭代极快，几乎每天发版 |

## 六、多Agent会话架构

### Managed Agents Multi-Agent (platform.claude.com)

**核心架构**：
- 所有代理共享同一容器和文件系统
- 每个代理运行在独立 Session Thread（上下文隔离的事件流）
- 协调器在主线程报告活动，子线程按需生成
- 线程持久化：协调器可向之前的代理发送后续指令，代理保留之前的所有对话

**委托场景**：
- 代码审查：审查代理 + 聚焦系统提示 + 只读工具
- 测试生成：测试代理写测试不动生产代码
- 研究搜索：搜索代理 + web工具汇总结果

### Agent Teams

- 多个 Claude Code 会话并行工作，共享任务协调
- In-process / Split panes 两种模式
- git worktrees 隔离分支开发

## 八、脚手架 > 提示词（架构级洞察）

**核心论点**：提示词质量决定原子任务，但真实代码库工作中，脚手架在做无声的重活。

| 能力 | 提示词 | 脚手架 |
|------|--------|--------|
| 上下文隔离 | 无 | N个并行子代理 = N倍有效上下文 |
| 工具限制 | 建议性（可忽略） | 强制性（无法绕过） |
| 延迟加载 | 静态 | 按需动态加载 |
| 钩子执行 | 无法拦截工具调用 | 代理循环外确定性执行 |
| 模型路由 | 无 | 智能分流 |
| 跨会话持久性 | 无 | Agent记忆系统 |
| 权限分类 | 无 | 安全粒度控制 |

## 九、87条实战技巧精华摘要

### 提示工程
- 挑战 Claude：严格审查，不给创建 PR 直到通过测试
- 平庸修复后说"丢弃这个，实现优雅方案"→ 第二次代码明显更好
- 粘贴错误信息说"修复"即可，不要教学

### 规划
- 分阶段门控计划，每阶段多测试验证
- 启动第二个 Claude 作为资深工程师审查计划
- 原型优先于 PRD：构建 20-30 个版本而不是写规格

### Git/PR
- 一天141 PR，45K行变更，PR中位数118行
- 总是压缩合并，每个功能一个提交
- @claude 自动生成针对重复审查反馈的 lint 规则

### 实用
- 终端运行优于 IDE 集成
- /statusline 实时感知上下文使用量
- 沙箱模式减少 84% 权限提示
- 代理搜索（glob+grep）战胜 RAG

| 范围 | 目录 | 用途 |
|------|------|------|
| user | ~/.claude/agents/<name>/memory/ | 跨项目共享 |

## 十一、多Agent协作最佳实践（2026 最新）

### Managed Agents Multi-Agent（Anthropic 官方）
```
协调器 (Coordinator) → 审查代理 (Reviewer) + 测试代理 (Tester) + 搜索代理 (Searcher)
```
- 共享文件系统 + 独立上下文
- 线程持久化，支持跨轮次调用
- 每个代理独立模型/工具/MCP配置

### Claude Code Agent Teams
- 多会话并行 + git worktrees
- 共享任务协调
- 减少上下文污染

### Code Review 多代理模式
- 多个子代理独立审查相同代码
- 不同角度（逻辑/安全/性能）
- 组合效果远超单代理
