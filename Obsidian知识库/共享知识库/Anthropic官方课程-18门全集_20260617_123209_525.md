## 三、开发者核心课程深度提炼

### 3.1 Claude Code 101

| 维度 | 内容 |
|------|------|
| **课程概述** | 从零开始掌握Claude Code——Anthropic的Agentic编程工具。学会让AI读取代码库、编辑文件、运行命令，建立AI辅助开发工作流。 |
| **前置要求** | 熟悉终端机与代码编辑器，需要Claude Pro/Max/Enterprise账号或API key |
| **适合人群** | 刚进入软件开发领域的新手 / 有经验但未用过AI编程工具的工程师 |

**核心知识点**：

| 知识域 | 关键内容 |
|--------|---------|
| **Agentic Loop** | Claude Code 的底层运行机制：感知→规划→执行→反馈循环。模型自主决定使用什么工具、何时停下来询问用户。 |
| **上下文窗口管理** | 通过 `/compact`、`/clear`、`/context` 命令精确控制上下文。上下文窗口是Agent的"工作记忆"，管理不好=Agent失忆。 |
| **Explore→Plan→Code→Commit 工作流** | 先探索代码库（Explore）→ 制定方案（Plan）→ 实现代码（Code）→ 提交（Commit），四阶段标准化流程。 |
| **CLAUDE.md 配置** | 用 Markdown 文件定义项目级/用户级规则，让Claude记住项目偏好、编码规范、常用命令。 |
| **Subagents（子代理）** | 把任务分派给独立的上下文窗口执行，保持主对话清晰专注。内置 Explore/Plan/General-purpose 三种子代理。 |
| **MCP Server 整合** | 通过 Model Context Protocol 连接外部工具和数据源，扩展Claude Code的能力边界。 |
| **Hooks** | 在特定事件触发确定性的自动化操作——格式化代码、阻止危险指令、发送通知。 |

**关键技能清单**：
- [ ] 安装和配置 Claude Code
- [ ] 使用 `/init` 初始化项目 CLAUDE.md
- [ ] 熟练运用 Explore→Plan→Code→Commit 工作流
- [ ] 使用 `/compact` 管理上下文窗口
- [ ] 创建自定义 Subagents
- [ ] 连接 MCP Server
- [ ] 编写 Hooks 做确定性控制
- [ ] 理解工具权限系统

**最佳实践**：
- 每个项目都写 CLAUDE.md，记录项目结构、技术栈、编码规范
- 善用 Plan Mode 先规划再执行，避免盲目修改
- 利用 `/compact` 在长对话中保持上下文高效
- 内置 Explore 子代理做代码库探索，不污染主对话

**Anti-Patterns（反模式）**：
- ❌ 不写 CLAUDE.md 直接开工 → Claude 不理解项目上下文
- ❌ 在单一对话中处理所有任务不压缩 → 上下文溢出导致质量下降
- ❌ 错误理解 `/compact` 会丢失重要上下文 → 实际上 `/compact` 生成摘要保留关键信息

### 3.2 Claude Code in Action（⭐ Featured Course）

| 维度 | 内容 |
|------|------|
| **课程概述** | Claude Code 的进阶实战课，重心在"整合"而非"入门"——如何把Claude Code接入现有开发流程，而非另起炉灶。这是官方当前主推的两门Featured Course之一。 |
| **前置要求** | 熟悉 CLI 与 Git 基础 |
| **课时** | 15堂课，约1小时视频 |

**核心知识点**：

| 知识域 | 关键内容 |
|--------|---------|
| **视觉输入工作流** | 截图直接描述UI修改需求，Claude理解视觉内容后生成代码修改。跨越"文字描述→视觉理解"的鸿沟。 |
| **自定义指令自动化** | 创建自定义命令（Custom Commands）自动化重复任务，减少手动输入。 |
| **MCP Server 整合（浏览器自动化）** | 将 MCP Server 接入 Claude Code，实现浏览器自动化等高级场景。 |
| **GitHub 整合** | 自动化 PR 审查、代码提交管理。Claude Code 直接对接 GitHub 工作流。 |
| **Hooks 进阶** | Hooks 与 Claude Code SDK 的进阶应用——事件驱动的自动化控制。 |
| **Thinking Mode vs Planning Mode 判断框架** | 课程提供的核心判断力：什么任务用 Thinking Mode（深度推理）、什么任务用 Planning Mode（先规划再执行）、两者适用的任务复杂度边界。 |

**Thinking Mode vs Planning Mode 判断框架**：

| 维度 | Thinking Mode | Planning Mode |
|------|--------------|---------------|
| 适用任务 | 需要深度推理的复杂算法/架构决策 | 需要分步执行、可验证中间结果的任务 |
| 上下文消耗 | 高（思考过程占用大量token） | 中（规划输出简洁） |
| 用户介入 | 少（模型自主推理） | 多（用户审核计划后执行） |
| 典型场景 | 算法优化、安全漏洞分析、架构重构 | 多文件修改、功能开发、重构分步执行 |
| 复杂度边界 | 推理密集型 | 执行密集型 |

**关键技能清单**：
- [ ] 掌握视觉输入→代码修改的完整工作流
- [ ] 创建自定义命令自动化日常任务
- [ ] 整合 MCP Server 扩展能力（浏览器自动化等）
- [ ] 配置 GitHub 工作流整合
- [ ] 编写 Hooks 做事件驱动自动化
- [ ] 准确判断何时用 Thinking Mode / Planning Mode

**最佳实践**：
- 视觉输入+截图是最高效的UI修改方式，不需要文字描述布局细节
- 自定义命令按项目/团队标准化，形成共享的自动化脚本库
- GitHub PR审查交给Claude Code，人类只做最终确认

**Anti-Patterns**：
- ❌ 所有任务都用 Thinking Mode → 简单任务浪费token
- ❌ 所有任务都用 Planning Mode → 复杂推理场景模型受限
- ❌ 自定义命令不维护 → 团队依赖过时的自动化脚本

### 3.3 Introduction to Agent Skills

| 维度 | 内容 |
|------|------|
| **课程概述** | Skills 是 Anthropic 力推的"可复用 AI 指令"标准。通过 Markdown 文件（SKILL.md）扩展 Claude Code 行为——"教一次"，自动套用。课程从创建第一个 Skill 开始，到团队分发和企业部署。 |
| **关键价值** | 清晰说明了 Skills 与 CLAUDE.md、Hooks、Subagents 的差异——帮开发者判断每个情境该用哪个工具。 |

**核心知识点**：

| 知识域 | 关键内容 |
|--------|---------|
| **SKILL.md 格式** | Markdown + YAML frontmatter。frontmatter 包含 name、description（触发判断依据）、allowed-tools 等字段。 |
| **Frontmatter 设计** | Description 是 Skill 能否被正确触发的关键——必须写得具体且有区分度，不是泛泛的关键词堆砌。 |
| **Progressive Disclosure（渐进式披露）** | 用目录结构控制上下文窗口消耗。Claude 先加载 frontmatter（轻量），只在匹配时才加载完整指令（重量）。 |
| **目录结构** | `skill-name/SKILL.md` → frontmatter 摘要层；`skill-name/instructions/` → 详细指令层；`skill-name/scripts/` → 脚本层（不消耗 context 执行）。 |
| **工具存取限制** | allowed-tools 字段限制 Skill 能使用的工具范围——最小权限原则。 |
| **脚本不消耗上下文** | 将脚本放在 skills 目录下，通过 shell 工具调用，脚本内容不占据上下文窗口。 |
| **团队共享** | Skills 可以 commit 到 repo 供团队使用。CLAUDE.md 引用 skills/ 目录。 |
| **Plugins 分发** | 通过 plugins 机制更广泛散布 Skills。 |
| **企业级部署** | 统一部署方式——托管 Skills（Managed Settings）。 |

**Skills vs CLAUDE.md vs Hooks vs Subagents 差异表**：

| 维度 | Skills | CLAUDE.md | Hooks | Subagents |
|------|--------|-----------|-------|-----------|
| **本质** | 可复用的任务指令 | 项目/用户规则 | 事件驱动的自动化 | 独立执行的工作单元 |
| **触发方式** | Claude 自动匹配 | 每次对话加载 | 特定事件触发 | 父Agent手动委派 |
| **生命周期** | 跨对话持久 | 项目/用户级持久 | 跨对话持久 | 任务级（可复用定义） |
| **上下文消耗** | 低（progressive disclosure） | 中（每次加载） | 极低（仅触发时） | 高（独立context window） |
| **适用场景** | "教我怎么做某类任务" | "记住关于这个项目的规则" | "当X发生时自动做Y" | "帮我单独处理这个子任务" |
| **共享方式** | 文件/Repo/Plugins | Repo | 配置文件 | 文件定义（User/Project级） |
| **典型例子** | "写单元测试的规范" | "这个项目用TypeScript" | "提交前自动格式化" | "搜索整个代码库中的安全漏洞" |

**关键技能清单**：
- [ ] 创建第一个 SKILL.md（YAML frontmatter + Markdown正文）
- [ ] 设计能可靠触发的 description 字段
- [ ] 使用 progressive disclosure 目录结构
- [ ] 配置 allowed-tools 限制工具权限
- [ ] 将脚本部署为不消耗上下文的执行层
- [ ] 通过 plugins/claude.md 共享 Skills
- [ ] 排查 Skill 不触发/冲突问题

**最佳实践**：
- Description 描述具体场景而非堆砌关键词
- 复杂 Skill 必须用渐进式披露，不要把所有指令塞进 frontmatter
- 脚本层用 shell 工具调用，保持指令文件干净
- 团队 Skills 统一放在 repo 的 `.claude/skills/` 目录

**Anti-Patterns**：
- ❌ Description 写得过于宽泛 → 错误触发或永不触发
- ❌ 所有内容塞进 SKILL.md → 上下文浪费
- ❌ 不给 Skill 限制工具 → 安全隐患
- ❌ Skills 和 CLAUDE.md 内容重复 → 维护混乱

### 3.4 Introduction to Subagents

| 维度 | 内容 |
|------|------|
| **课程概述** | Subagents 让你把任务分派给独立上下文窗口执行，执行完后只把结果传回主对话。课程重点不是"怎么建"，而是"设计原则"。 |
| **核心价值** | 这是官方第一次把"什么时候不该用Subagents"（过度设计Anti-Pattern）写进课程。 |

**核心知识点**：

| 知识域 | 关键内容 |
|--------|---------|
| **子代理工作原理** | Claude Code 打开独立上下文窗口→注入任务描述+系统提示→子代理执行→只返回摘要/结构结果。主对话上下文不被污染。 |
| **创建方式** | `/agents` 命令界面生成，或手动写 YAML frontmatter 的 Markdown 文件。 |
| **结构化输出格式** | 子代理必须返回结构化结果（JSON/Markdown），而非完整对话日志。这是子代理的基础契约。 |
| **遇阻即报** | 子代理遇到无法解决的问题时，必须明确回报阻塞原因，而非静默失败后返回空结果。 |
| **工具存取范围限制** | 只授予子代理完成任务所需的最小工具集。内置 Explore 子代理只有只读工具。 |
| **内置子代理** | Explore（Haiku，只读代码库探索）、Plan（规划模式专用）、General-purpose（全工具复杂任务）。 |
| **用户级 vs 项目级** | User级（~/.claude/agents/）跨项目复用；Project级（.claude/agents/）项目专用。 |

**何时用 vs 何时过度设计（Anti-Pattern）**：

| 场景 | 判断 | 理由 |
|------|------|------|
| 搜索整个代码库找所有SQL注入点 | ✅ 用Subagent | 搜索结果量大，会淹没主对话 |
| 修改单个文件的函数签名 | ❌ 过度设计 | 单Agent足够，创建子代理的开销大于收益 |
| 分析一个大型日志文件（50000行） | ✅ 用Subagent | 日志内容不需要出现在主对话中 |
| 修复一个已知Bug（涉及2个文件） | ❌ 过度设计 | 单Agent直接修复更高效 |
| 并行研究3个独立主题 | ✅ 用Subagent | 并行执行，各自独立上下文 |
| 顺序执行A→B→C（B依赖A结果） | ❌ 过度设计 | 有强依赖，不宜拆分 |

**关键技能清单**：
- [ ] 使用 `/agents` 创建自定义子代理
- [ ] 设计清晰的任务描述（description 字段）
- [ ] 定义结构化输出格式
- [ ] 配置工具权限（Read-only / 特定工具）
- [ ] 理解并善用内置子代理（Explore/Plan/General-purpose）
- [ ] 判断何时适合/不适合使用子代理

**最佳实践**：
- 子代理 description 写清楚"什么时候用"，不要只写"能做什么"
- 大搜索/大日志分析/并行探索 → 子代理
- 小修改/单文件操作/强依赖任务 → 直接执行
- 子代理模型可选用更便宜的Haiku（成本优化）

**Anti-Patterns**：
- ❌ 为简单任务创建子代理 → 增加延迟和token消耗
- ❌ 子代理静默失败返回空结果 → 主Agent误判任务完成
- ❌ 给子代理全部工具权限 → 安全隐患
- ❌ 子代理嵌套子代理 → 无限嵌套导致上下文爆炸（Claude Code已内置防嵌套保护）

### 3.5 MCP 系列（基础 + 高级）

#### Introduction to Model Context Protocol

| 维度 | 内容 |
|------|------|
| **课程概述** | 使用 Python SDK 从零构建 MCP Server 和 Client，掌握 MCP 的三个核心原语。MCP 是 Anthropic 推出的开放标准，让 AI Agent 通过统一接口连接外部工具和数据源。 |
| **核心比喻** | MCP 是 Agent 的"神经系统"——解决AI在复杂任务中面临的"信息孤岛"问题。 |

**MCP 三原语**：

| 原语 | 方向 | 控制者 | 本质 | 示例 |
|------|------|--------|------|------|
| **Tools** | 模型→服务器 | 模型决策 | 模型控制的**动作** | 查数据库、发API请求、执行计算、读写文件 |
| **Resources** | 服务器→模型 | 应用控制 | 应用控制的**唯读数据** | 配置文件、数据库记录、文档（通过URI标识） |
| **Prompts** | 服务器→用户 | 用户调用 | 预定义的**指令模板** | "review这段code"、"生成报告" |

**理解三原语关系**：
- Tools = Agent的"手"（做什么）
- Resources = Agent的"眼"（看什么）
- Prompts = Agent的"口"（怎么说）

**关键技能清单**：

|------|------|---------|------|
| **Parallelization** | 多个Agent并行处理独立子任务 | 广度优先查询、独立分析 | 同时搜索3个数据源 |
| **Chaining** | Agent A输出→Agent B输入→Agent C输出 | 有依赖的步骤 | 生成草稿→审查→优化 |

- ❌ System Prompt 过长 → 挤占有效上下文

## 四、多Agent系统工程深度知识

> 来源：Anthropic 官方工程博客《How we built our multi-agent research system》

### 4.1 Orchestrator-Worker 架构模式

这是 Anthropic Research 功能的核心架构：

```
用户查询 → Lead Agent（Orchestrator）
                │
        ┌───────┼───────┐
        ▼       ▼       ▼
    SubA    SubB    SubC（Worker Agents）
        │       │       │
        └───────┼───────┘
                ▼
        Lead Agent 合成结果
                │
                ▼
        CitationAgent 标注引用
                │
                ▼
            最终回答（含引用）
```

**Lead Agent 职责**：分析问题→制定策略→创建子代理→合成结果→决定是否继续研究

**Worker Agent 职责**：接收具体任务→独立搜索→返回结构化发现

**Memory 模块**：当上下文超过200K tokens时，Lead Agent 将计划保存到 Memory 以持久化上下文。

### 4.2 子代理并行化策略

| 策略 | 说明 | 收益 |
|------|------|------|
| **Context Window 分离** | 每个子代理独立上下文窗口 | 避免搜索结果淹没主对话 |
| **关注点分离（Separation of Concerns）** | 不同子代理使用不同的工具集、提示词和探索路径 | 降低路径依赖性，实现独立深度调查 |
| **信息压缩** | 子代理搜索大量信息后压缩为关键token返回 | 搜索的本质是压缩——从海量语料中提炼洞察 |

### 4.3 评估数据

> 多Agent系统（Claude Opus 4 Lead + Claude Sonnet 4 Subagents）比单Agent Opus 4 在内部 Research Eval 上**高 90.2%**

**具体案例**：当被要求找出标普500信息技术行业中所有公司的董事会成员时——多Agent通过分解任务给子代理找到正确答案；单Agent因缓慢的顺序搜索未能找到答案。

### 4.4 Token 经济学

| 指标 | 数值 |
|------|------|
| 多Agent系统 vs Chat交互 | ≈ **15× tokens** |
| Agent vs Chat交互 | ≈ **4× tokens** |
| Token消耗解释性能方差 | **80%**（BrowseComp评估） |
| 其余解释因素 | 工具调用次数 + 模型选择 |

**经济可行性阈值**：
- 多Agent系统仅在任务价值足够高时才经济可行
- 模型升级（如 Sonnet 3.7→Sonnet 4）的性能提升 > 加倍Token预算

### 4.5 何时不适合多Agent

| 不适合场景 | 原因 |
|-----------|------|
| 需要所有Agent共享同一上下文 | 多Agent核心优势就是上下文分离 |
| 任务间强依赖 | LLM Agent 尚不擅长实时协调和委托 |
| 大部分编码任务 | 真正可并行的子任务比研究少 |
| 简单任务 | 创建子代理的开销 > 并行收益 |

### 4.6 多Agent系统八项设计原则（来自工程实践）

1. **像Agent一样思考**：用模拟和可视化工具观察Agent决策，及时发现和修正失败模式
2. **教会主控Agent如何分工**：为每个子Agent分配清晰目标、输出格式、工具指引和任务边界
3. **根据任务复杂度分配资源**：在提示词中嵌入"规模规则"——简单任务用少量Agent和工具调用
4. **工具设计与选择至关重要**：工具接口像人机界面一样清晰，描述明确，避免误用
5. **让Agent自我改进**：利用LLM自身能力优化提示词和工具描述，通过"工具测试Agent"不断发现和修正问题
6. **先广后深**：搜索策略先用宽泛查询探索全局，再逐步聚焦细节
7. **引导思考过程**：通过Extended Thinking模式让Agent显式规划、评估和调整策略
8. **并行工具调用极大提升效率**：主Agent和子Agent都应并行调用工具
