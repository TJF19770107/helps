第二部分：Claude Code 核心能力与最佳实践
================================================================================

2.1 Claude Code 是什么

Claude Code 是一个代理式编码环境（Agentic Coding Environment）。
与等待回答问题的聊天机器人不同，Claude Code 可以读取文件、运行命令、进行更改，
并在你观看、重定向或完全离开的情况下自主解决问题。

核心差异：
  传统：你编写代码，Claude 审查
  Claude Code：你描述目标，Claude 探索、规划并实现


2.2 核心约束：Context Window

Claude 的 context window 保存整个对话历史，包括每条消息、每个读取的文件、
每个命令输出。当 context 填充时，LLM 性能下降。

关键策略：
  频繁使用 /clear 在任务之间重置 context
  使用 subagents 进行隔离调查
  使用 /compact 指令主动压缩
  在 CLAUDE.md 中定义压缩行为
  使用 /btw 进行不影响 context 的快速查询


2.3 给 Claude 一种验证其工作的方式

提供可运行的验证：测试、构建、linter、对比脚本、浏览器截图。
这是"你观看的会话"和"你可以离开的会话"之间的区别。

策略对照表：
  之前：实现一个函数
  之后：实现函数 + 提供测试用例 + 运行测试验证

  之前：构建失败
  之后：提供错误信息 + 修复并验证 + 解决根本原因

  之前：改善 UI
  之后：提供设计截图 + 实现 + 截图对比 + 列出差异并修复

验证方式层级：
  单次提示内：要求 Claude 运行检查并迭代修复
  整个会话中：设置 /goal 条件，评估器每次转换后重新检查
  确定性门：Stop hook 运行检查脚本，阻止转换直到通过
  第二意见：子代理在新鲜 context 中审查


2.4 先探索，再规划，最后编码

四阶段工作流：

  阶段1  探索：进入 Plan Mode。Claude 只读文件，不做更改。
    示例：read /src/auth and understand session/login handling

  阶段2  规划：要求 Claude 创建详细实现计划。
    示例：I want to add Google OAuth. What files need to change? Create a plan.

  阶段3  实现：切换出 Plan Mode，根据计划编码。
    示例：implement the OAuth flow from your plan. write tests.

  阶段4  提交：使用描述性消息提交并创建 PR。
    示例：commit with a descriptive message and open a PR

适用场景：方法不确定、多文件改动、代码不熟悉时最有价值。
不适用场景：修复拼写错误、添加日志行、简单重命名  直接执行即可。


2.5 在提示中提供具体上下文

有效策略：
  限定任务范围：指定文件、场景、测试偏好
  指向信息来源：引导 Claude 到 git 历史、文档等
  参考现有模式：指向代码库中已有的模式作为范例
  描述症状：提供具体症状、可能位置、"修复"的定义
  提供丰富内容：使用 @ 引用文件、粘贴截图、管道数据


2.6 配置你的环境

2.6.1 CLAUDE.md
  运行 /init 生成启动文件，随时间精化。
  CLAUDE.md 在每个对话开始时自动加载，提供持久上下文。
  
  应该包括：
    非标准 Bash 命令
    与默认值不同的代码风格
    测试指令和首选测试运行器
    存储库礼仪
    架构决策
    环境怪癖和必需的环境变量
    常见陷阱或非显而易见的行为
  
  不应包括：
    Claude 可以从代码推断的内容
    标准语言约定
    详细 API 文档（改为链接）
    经常变化的信息
    自明的实践（如"编写干净的代码"）
    逐个文件描述的代码库
  
  多位置支持：
    ~/.claude/CLAUDE.md（全局，所有会话）
    ./CLAUDE.md（项目根目录，团队共享）
    ./CLAUDE.local.md（个人项目特定，加入 .gitignore）
    父目录和子目录（monorepo 支持）

  支持 @path/to/file 引用外部文件。

2.6.2 权限配置
  Auto mode：分类器模型审查命令，只阻止风险操作
  权限允许列表：对已知安全的命令白名单（如 npm run lint）
  沙箱：操作系统级隔离，限制文件系统和网络访问

2.6.3 CLI 工具集成
  安装 gh（GitHub CLI）、aws、gcloud、sentry-cli 等
  Claude 能自适应学习不熟悉的 CLI 工具


2.7 有效沟通

2.7.1 代码库问答
  "日志如何工作？"
  "我如何创建新的 API 端点？"
  "第 134 行的 async move { ... } 做什么？"
  "CustomerOnboardingFlowImpl 处理哪些边界情况？"

2.7.2 让 Claude 采访你
  用 "Interview me in detail using the AskUserQuestion tool" 启动
  Claude 会问技术实现、UI/UX、边界情况、权衡等问题
  采访完成后，Claude 输出完整规范到 SPEC.md
  然后启动新会话执行规范（干净 context）


2.8 会话管理

2.8.1 尽早且经常改正方向
  Esc：中途停止 Claude，保留 context
  Esc + Esc 或 /rewind：恢复到之前检查点
  "撤销那个"：让 Claude 恢复更改
  /clear：不相关任务间重置 context

  如果连续改正 2 次以上仍失败，/clear 后用更具体的提示重新开始。

2.8.2 检查点与 Rewind
  每个提示都创建检查点。可将对话和代码恢复到任意之前状态。
  检查点在会话中持久存在，关闭终端后仍可恢复。

2.8.3 恢复对话
  /rename 命名会话，像分支一样管理
  claude --continue 继续最近会话
  claude --resume 从列表中选择


2.9 自动化和扩展

2.9.1 非交互模式
  claude -p "your prompt"                       # 一次性查询
  claude -p "prompt" --output-format json       # 结构化输出
  claude -p "prompt" --output-format stream-json --verbose  # 流式输出

2.9.2 并行会话
  多个 Claude 会话并行运行，加速开发、运行隔离实验。
  
  Writer/Reviewer 模式：
    会话A（Writer）：实现功能
    会话B（Reviewer）：在新鲜 context 中审查，查找边界情况

2.9.3 跨文件扇出
  for file in $(cat files.txt); do
    claude -p "Migrate $file from React to Vue" --allowedTools "Edit,Bash(git commit *)"
  done

2.9.4 对抗性审查
  在将任务视为完成前，让子代理在新鲜 context 中审查差异并报告缺陷。
  只标记影响正确性或陈述要求的缺陷，避免过度工程化。


2.10 常见失败模式

  厨房水槽会话：一个会话混入多个不相关任务  context 被污染
   修复：任务之间 /clear

  反复改正：Context 积累失败方案，性能下降
   修复：2 次失败后 /clear，用更好的初始提示重启

  过度指定的 CLAUDE.md：太长导致关键规则被忽略
   修复：无情修剪，只保留 Claude 缺失时会犯错的规则

  信任-验证差距：实现看起来合理但不处理边界情况
   修复：始终提供验证（测试/脚本/截图），无法验证就不发布

  无限探索：未限定范围的调查导致 context 爆满
   修复：狭隘限定或使用 subagents

第三部分：子代理（Sub-agents）体系

3.1 Claude Code Swarm（Agent Teams）

3.1.1 概述
  Swarm 模式（或称为 Claude Code agent teams）将 Claude Code 从单 AI 助手
  转变为多 Agent 编排系统。核心洞察：不是一个强大的模型尝试做所有事情，
  而是一组专注的专业人员协调工作。

3.1.2 工作流程
  (1) 与团队领导对话：领导 agent 不写代码，而是规划、委派、综合。
  (2) 领导生成专家：进入委派模式，创建特定角色的 agent。
  (3) Agent 并行工作：每个专家有新鲜 context，共享任务板 + 依赖管理。
  (4) 结果回流：工人完成任务、标记完成、报告给领导，领导综合结果。

3.1.3 TeammateTool 操作为 13 个
  团队生命周期：spawnTeam、discoverTeams、cleanup
  加入工作流：requestJoin、approveJoin、rejectJoin
  协调：直接消息、广播消息、计划审批协议

3.1.4 任务系统
  共享任务列表位于 ~/.claude/tasks/{team-name}/
  任务属性：id、subject、status、owner、blocks（依赖）、description
  工人自组织：
    (1) 检查 TaskList 寻找可用工作
    (2) 认领未分配、未阻塞的任务
    (3) 完成后标记
    (4) 发现额外工作时创建新任务

3.1.5 Git Worktree 隔离
  每个 agent 在独立的 Git worktree 中工作，防止并发文件冲突。
  仅在测试通过后合并代码，保持主分支稳定。

3.1.6 环境变量
  CLAUDE_CODE_AGENT_ID      唯一标识符
  CLAUDE_CODE_AGENT_TYPE    角色（frontend/backend 等）
  CLAUDE_CODE_TEAM_NAME     团队归属
  CLAUDE_CODE_PLAN_MODE_REQUIRED  是否需要计划审批

3.1.7 适用场景
  适用：大型重构、多组件功能开发、需要并行工作流的项目、超单 agent context 限制的代码库
  不适用：快速修复和小改动、范围不清晰的探索工作、安全关键代码、不需要并行的简单任务


3.2 SDK 子代理编程（Agent SDK Subagents）

3.2.1 三种创建方式
  (1) 编程方式：在 query() 中使用 agents 参数（TypeScript / Python）
  (2) 文件系统方式：在 .claude/agents/ 目录定义 Markdown 文件
  (3) 内置通用子代理：Claude 可随时通过 Agent 工具调用 built-in general-purpose

3.2.2 编程方式（推荐）
  子代理定义结构：
    name：唯一标识符
    description：何时激活的描述（Claude 据此决定是否调用）
    tools：允许的工具列表
    model：指定模型（可选）
    instructions：系统提示（可选）

  示例（TypeScript）：
    agents: {
      "code-reviewer": {
        description: "Reviews code for bugs and style issues",
        tools: ["Read", "Grep"],
        model: "opus"
      },
      "test-runner": {
        description: "Runs tests and reports failures",
        tools: ["Bash(cd test && npm test *)", "Read"],
        instructions: "You are a test engineer..."
      }
    }

3.2.3 文件系统方式
  目录：.claude/agents/security-reviewer.md
  
  ---
  name: security-reviewer
  description: Reviews code for security vulnerabilities
  tools: Read, Grep, Glob, Bash
  model: opus
  ---
  You are a senior security engineer. Review code for:
  - Injection vulnerabilities (SQL, XSS, command injection)
  - Authentication and authorization flaws
  - Secrets or credentials in code
  - Insecure data handling
  Provide specific line references and suggested fixes.

3.2.4 上下文隔离
  子代理在独立 context 中运行，拥有自己的工具集。
  适用于：读取大量文件、需要专门关注、不污染主对话的任务。

3.2.5 调用方式
  "use subagent to review this code for security issues"
  "use subagents to investigate how auth handles token refresh"
  "use a subagent to review this code for edge cases"


3.3 四件套扩展栈：Skills + Hooks + Agents + MCP

这是 Claude Code 成为可编程 AI 平台的四大核心扩展原语：

  Skills：将工作流编码为斜杠命令
  Hooks：在非确定性 AI 行为上实施确定性护栏
  Agents：在隔离的 Git worktree 中生成并行子进程
  MCP：通过开放协议连接 1000+ 外部工具

四者组合解决了"最后一英里"问题，使 Claude Code 从个人玩具变成团队可编程平台。

扩展能力矩阵：
  需求          最佳选择
  每次必执行     Hook（确定性保证）
  按需加载知识   Skill（上下文效率）
  并行处理       Agent/Subagent（隔离 context）
  外部连接       MCP（开放协议）

第四部分：Skills 技能系统
================================================================================

4.1 Skills 概念

Skills 根据任务上下文动态加载，实现：
  无限容量：知识分散在多个文件中
  上下文效率：仅加载所需内容
  渐进式披露：三层加载机制

三层加载：
  (1) 前置元数据：启动时加载（触发条件）
  (2) SKILL.md 主体：激活时加载
  (3) references/：需要详细信息时加载


4.2 目录结构

  skills/
    skill-name/
      SKILL.md          # 核心内容
      references/        # 详细文档
        deep-dive.md
      examples/           # 工作代码示例
        example.md
      scripts/            # 实用工具
        tool.sh


4.3 SKILL.md 格式

  ---
  name: api-conventions
  description: REST API design conventions for our services
  ---
  # API Conventions
  - Use kebab-case for URL paths
  - Use camelCase for JSON properties
  - Always include pagination for list endpoints
  - Version APIs in the URL path (/v1/, /v2/)

4.4 可重复工作流 Skill

  ---
  name: fix-issue
  description: Fix a GitHub issue
  disable-model-invocation: true
  ---
  Analyze and fix the GitHub issue: $ARGUMENTS.
  1. Use `gh issue view` to get the issue details
  2. Understand the problem described in the issue
  3. Search the codebase for relevant files
  4. Implement the necessary changes to fix the issue
  5. Write and run tests to verify the fix
  6. Ensure code passes linting and type checking
  7. Create a descriptive commit message
  8. Push and create a PR

  使用 disable-model-invocation: true 时，只能通过 /fix-issue 1234 手动调用。


4.5 Skills 类型

  防护栏技能（Guardrail Skills）：
    目的：强制执行防止错误的关键最佳实践
    类型：guardrail
    执行级别：block
    优先级：critical 或 high
    使用场景：会导致运行时错误的错误、数据完整性担忧、关键兼容性问题

  领域技能（Domain Skills）：
    目的：为特定领域提供全面指导
    类型：domain
    执行级别：suggest
    优先级：high 或 medium
    使用场景：复杂系统深度知识、最佳实践文档、架构模式


4.6 安装与位置

  全局通用（所有项目生效）：~/.claude/skills/
  项目专用（仅当前仓库）：项目根目录的 .claude/skills/
  Plugins 市场：运行 /plugin 浏览安装

第五部分：Hooks 钩子系统
================================================================================

5.1 Hooks 概述

Hooks 在 Claude Code 工作流中的特定点自动运行脚本。
与 CLAUDE.md 指令不同，hooks 是确定性的，保证操作发生。

5.2 钩子事件类型

  事件              触发时机              典型用例
  PreToolUse         工具使用前            验证、审批
  PostToolUse        工具使用后            测试、代码检查、lint
  SessionStart       会话开始时            日志记录、环境设置
  SessionEnd         会话结束时            清理
  UserPromptSubmit   用户提交提示时        预处理
  PreCompact         压缩前                状态保存
  Notification       显示通知时            自定义提醒
  Stop               用户停止时            清理
  SubagentStop       子代理结束时          日志记录

5.3 配置方式

  方式一：内联配置（在 plugin.json 中）
  {
    "hooks": {
      "PostToolUse": [{
        "matcher": "Write|Edit",
        "hooks": [{
          "type": "command",
          "command": "${CLAUDE_PLUGIN_ROOT}/scripts/lint.sh"
        }]
      }]
    }
  }

  方式二：独立 hooks.json
  匹配器支持工具名称正则匹配。

5.4 双 Hook 架构（高级模式）

  (1) UserPromptSubmit Hook（主动建议）
    触发：在 Claude 看到用户提示之前
    目的：基于关键词 + 意图模式建议相关技能
    方法：将格式化的提醒作为上下文注入

  (2) Stop Hook  错误处理提醒（温和提醒）
    触发：在 Claude 完成响应之后
    目的：温和提醒自我评估错误处理
    方法：分析编辑过的文件以查找风险模式

第六部分：MCP (Model Context Protocol)
================================================================================

6.1 MCP 概述

MCP 是连接 AI 代理与企业系统的通用标准协议。
三大核心原语：tools、resources、prompts。

6.2 MCP 生产部署 15 个最佳实践

  (1) 将每个服务器视为有界上下文：围绕单个微服务域构建
  (2) 首选无状态、幂等的工具设计：接受请求 ID，确定性结果
  (3) 选择正确的传输方式：stdio（最大兼容）+ 可流式 HTTP（网络化部署）
      注意：SSE 传输已弃用，被可流式 HTTP 取代
  (4) 实现请求取消和超时：防止长时间运行调用占用资源
  (5) 拥抱启发式（Elicitation）：填补缺失参数，但绝不收集敏感数据
  (6) 首先构建安全性（OAuth 2.1）：自 2025 年 3 月起 OAuth 2.1 是 HTTP 传输的强制要求
  (7) 采用"为代理和人类"的用户体验：响应必须 LLM 可解析且人类可读
  (8) 像生产微服务一样检测：结构化日志、相关 ID、延迟、成功率、令牌成本
  (9) 对表面积进行版本控制：语义版本控制、功能声明
  (10) 保持提示、工具和资源解耦和独立
  (11) 负责任地处理流式传输和大型输出：增量块，返回资源 URI 而非内联大数据

7.2 Python SDK 示例

  import asyncio
  from claude_agent_sdk import query, ClaudeAgentOptions
  from claude_agent_sdk import AssistantMessage, ResultMessage

  async def main():
      async for message in query(
          prompt="Review utils.py for bugs. Fix any issues.",
          options=ClaudeAgentOptions(
              allowed_tools=["Read", "Edit", "Glob"],
              permission_mode="acceptEdits",
          ),
      ):
          if isinstance(message, AssistantMessage):
              for block in message.content:
                  if hasattr(block, "text"):
                      print(block.text)
                  elif hasattr(block, "name"):
                      print(f"Tool: {block.name}")
          elif isinstance(message, ResultMessage):

第十一部分：AI Agent 设计原则（SOUL.md 补充素材）

11.1 代理设计核心理念

  (1) 自主但不失控：
      给 agent 明确的边界和验证标准
      使用 Hooks 实现确定性护栏
      使用 auto mode 分类器进行运行时安全检查

  (2) 上下文是稀缺资源：
      每个 token 都有成本
      使用 subagents 隔离上下文
      频繁清理不相关对话

  (3) 验证优先于信任：
      始终提供可运行的验证
      新鲜 context 审查（对抗性审查）
      检查点支持快速回滚

  (4) 先探索再行动：
      Plan Mode 将探索与执行分离
      清晰的规范比盲目编码更高效

  (5) 专业化优于通才化：
      子代理按角色分工
      每个 agent 有自己的工具集和 context
      Skills 按需加载领域知识

11.2 多 Agent 设计原则

  (1) 团队领导模式：
      领导 agent 只规划和综合，不执行
      避免单个 agent 负载过重

  (2) Git Worktree 隔离：
      并发 agent 使用独立工作目录
      仅在验证通过后合并

  (3) 任务依赖管理：
      共享任务板，支持阻塞关系
      Agent 自组织认领任务

  (4) 状态同步：
      通过任务板和环境变量传递状态
      避免 agent 间直接共享状态

第十二部分：多 Agent 协作流程（USER.md 补充素材）
================================================================================

12.1 标准协作流程

  步骤1：需求分析
    主 Agent 理解用户需求，判断是否需要多 Agent 协作
    如需协作，进入规划阶段

  步骤2：任务分解
    将需求拆解为独立子任务
    定义子任务间的依赖关系
    为每个子任务选择合适的 Agent 类型

  步骤3：并行执行
    Agent 团队并行处理各自任务
    通过任务板通信和协调
    领导 Agent 监控进度

  步骤4：结果整合
    各 Agent 完成后报告结果
    领导 Agent 综合所有结果
    对抗性审查验证最终输出

  步骤5：交付与归档
    生成最终交付物
    提交代码和文档
    清理临时资源

12.2 Writer/Reviewer 模式

  阶段1：Writer Agent 实现功能
  阶段2：Reviewer Agent 在新鲜 context 中审查

  阶段4：重复直到通过
