## 四、Claude Code Agent Teams 深度解析

> 来源：code.claude.com/docs/zh-CN/agent-teams · 2026年6月

### 4.1 Agent Teams vs Subagents 对比

| 维度 | Subagents | Agent Teams |
|------|-----------|-------------|
| **上下文** | 独立 context window，结果返回给调用者 | 独立 context window，完全独立 |
| **通信** | 仅向主代理报告结果 | 队友间直接相互发送消息 |
| **协调** | 主代理管理所有工作 | 自我协调的共享任务列表 |
| **最佳场景** | 结果重要的专注任务 | 需要讨论和协作的复杂工作 |
| **令牌成本** | 较低：结果汇总回主 context | 较高：每个队友是独立 Claude 实例 |

### 4.2 Agent Teams 核心架构

| 组件 | 角色 |
|------|------|
| **Team lead** | 主 Claude Code 会话，创建团队、生成队友、协调工作 |
| **Teammates** | 独立 Claude Code 实例，各自处理分配任务 |
| **Task list** | 队友认领和完成的共享工作项列表 |
| **Mailbox** | Agent 间通信的消息系统 |

### 4.3 最强用例场景

1. **研究与审查**：多个队友同时调查问题的不同方面，分享和质疑彼此发现
2. **新模块/功能开发**：队友各自拥有独立部分，互不干扰
3. **竞争假设调试**：队友并行测试不同理论，更快收敛答案
4. **跨层协调**：跨前端、后端、测试的变更，每个由不同队友负责

### 4.4 Agent Teams 使用模式

**指定队友和模型**：
```
Create a team with 4 teammates to refactor these modules in parallel.
Use Sonnet for each teammate.
```

**要求队友计划批准**：
```
Spawn an architect teammate to refactor the authentication module.
Require plan approval before they make any changes.
```

**使用 subagent 定义作为队友**：
```
Spawn a teammate using the security-reviewer agent type to audit the auth module.
```

**并行代码审查**：
```
Create an agent team to review PR #142. Spawn three reviewers:
- One focused on security implications
- One checking performance impact
- One validating test coverage
```

**竞争假设调查**（科学辩论模式）：
```
Users report the app exits after one message instead of staying connected.
Spawn 5 agent teammates to investigate different hypotheses. Have them talk to
each other to try to disprove each other's theories, like a scientific debate.
```

### 4.5 Agent Teams 最佳实践

- **给队友足够的 context**：队友不继承负责人对话历史，需在生成提示中包含任务特定详情
- **选择适当的团队规模**：3-5个队友最佳，每个队友5-6个任务
- **适当调整任务大小**：自包含的单位，产出清晰可交付成果
- **避免文件冲突**：每个队友拥有不同的文件集
- **从研究和审查开始**：不涉及编码的任务最适合入门
- **使用 hooks 强制质量门**：在队友完成任务后强制执行规则

### 4.6 已知限制

- In-process 队友没有会话恢复（/resume 和 /rewind 不会恢复）
- 任务状态可能滞后
- 关闭可能缓慢
- 每个会话一个团队（不能嵌套）
- 负责人是固定的（不能转移领导权）
- 分割窗格需要 tmux 或 iTerm2

## 五、Claude Code 最佳实践精选

> 来源：code.claude.com/docs/zh-CN/best-practices

### 5.1 核心约束：上下文窗口管理

上下文窗口是最重要的资源。对话、文件读取、命令输出都会快速填充上下文。上下文满时 LLM 性能下降。

**关键策略**：
- 在任务之间频繁使用 `/clear` 重置上下文
- 使用 subagents 进行研究调查，保持主对话干净
- 使用 `/compact` 压缩对话历史
- 使用 `/btw` 提出不留在上下文中的快速问题

### 5.2 四阶段工作流：Explore → Plan → Code → Commit

| 阶段 | 操作 | 示例 |
|------|------|------|
| **探索** | Plan Mode 下读取文件，不进行更改 | `read /src/auth and understand how we handle sessions` |
| **规划** | 要求 Claude 创建详细实现计划 | `I want to add Google OAuth. What files need to change?` |
| **实现** | 切换出 Plan Mode，编码并验证 | `implement the OAuth flow from your plan. write tests` |
| **提交** | 描述性提交并创建 PR | `commit with a descriptive message and open a PR` |

### 5.3 给 Claude 验证其工作的方式

**验证循环**：Claude 完成工作 → 运行检查 → 读取结果 → 迭代直到通过

| 策略 | 之前 | 之后 |
|------|------|------|
| 提供验证标准 | "实现一个验证电子邮件的函数" | "编写 validateEmail 函数。示例测试用例：user@example.com 为真，invalid 为假。运行测试" |
| 视觉验证 UI | "让仪表板看起来更好" | "[粘贴截图] 实现此设计。截图并与原始设计比较。列出差异并修复" |
| 解决根本原因 | "构建失败" | "构建失败，出现此错误：[粘贴]。修复并验证构建成功。解决根本原因" |

### 5.4 环境配置五件套

| 组件 | 位置 | 用途 |
|------|------|------|
| **CLAUDE.md** | 项目根目录 / ~/.claude/ | 持久上下文、代码风格、工作流规则 |
| **Skills** | .claude/skills/ | 领域知识、可复用工作流 |
| **Subagents** | .claude/agents/ | 专用助手定义、隔离任务委托 |
| **Hooks** | .claude/settings.json | 确定性事件触发（每次编辑后运行 eslint） |
| **Plugins** | `/plugin` 市场安装 | Skills + Hooks + Subagents + MCP 捆绑包 |

### 5.5 CLAUDE.md 编写原则

**✅ 包括**：
- Claude 无法猜测的 Bash 命令
- 与默认值不同的代码风格规则
- 测试指令和首选测试运行器
- 存储库礼仪（分支命名、PR 约定）
- 特定于项目的架构决策
- 开发者环境怪癖（必需的环境变量）
- 常见陷阱或非显而易见的行为

**❌ 排除**：
- Claude 可以通过读取代码推断的任何内容
- 标准语言约定
- 详细的 API 文档（改为链接到文档）
- 经常变化的信息
- 长解释或教程
- 自明的实践（如"编写干净的代码"）
- 逐文件代码库描述

### 5.6 会话管理

- **Esc**：中途停止 Claude，上下文保留
- **Esc+Esc 或 /rewind**：恢复到之前的检查点
- **"撤销那个"**：让 Claude 恢复更改
- **/clear**：在不相关任务之间重置上下文
- **/rename**：给会话命名（如"oauth-migration"）
- **claude --continue**：继续最近会话
- **claude --resume**：从列表中选择会话

### 5.7 自动化与扩展

| 方法 | 命令 | 场景 |
|------|------|------|
| 非交互模式 | `claude -p "prompt"` | CI / pre-commit hooks / 脚本 |
| 流式输出 | `claude -p "..." --output-format stream-json --verbose` | 实时处理 |
| 多会话并行 | 并行运行多个 Claude 会话 | 加快开发、隔离实验 |
| 跨文件扇出 | `for file in $(cat files.txt); do claude -p "Migrate $file" ...; done` | 大规模迁移 |
| Auto mode | `claude --permission-mode auto -p "fix all lint errors"` | 无人值守执行 |
| 对抗性审查 | 使用子代理在新鲜上下文中审查差异 | 质量保证 |

### 5.8 有效沟通技巧

1. **提出代码库问题**：像问另一个工程师一样问 Claude（日志如何工作？这个函数处理哪些边界情况？）
2. **让 Claude 采访你**：对于大功能，让 Claude 用 AskUserQuestion 工具采访你
3. **使用 @ 引用文件**：而非描述代码位置，Claude 在响应前读取文件
4. **直接粘贴图像**：复制/粘贴或拖放截图到提示中
5. **尽早且经常改正方向**：一旦注意到 Claude 偏离轨道，立即改正

## 六、Claude Managed Agents 企业级平台

> 来源：Anthropic Engineering 2026年2月 · nexracorp.com 深度分析

### 6.1 核心定位

Claude Managed Agents 是一套 **pre-built、可配置、运行于托管基础设施上的 agent harness**。开发者不需要从零实现 agent loop、sandbox、工具执行层与长任务状态管理。

### 6.2 四大核心概念

| 概念 | 职责 |
|------|------|
| **Agent** | 模型设定、系统提示、工具权限配置 |
| **Environment** | 容器环境、沙箱隔离、资源初始化 |
| **Session** | 单次任务执行、事件流记录、可恢复状态 |
| **Events** | 执行事件流、用户事件、agent 事件、session 事件、span 级记录 |

### 6.3 关键架构决策："大脑与双手解耦"

把 Claude + harness（大脑）从 sandbox + 工具（双手）解耦：

- **结果**：p50 TTFT 下降约 60%，p95 降幅超过 90%
- **安全**：凭证不暴露在 Claude 执行代码的 sandbox 中
- **扩展**：容器按需唤醒，不预启动

### 6.4 企业价值

1. **从模型 API 走向托管式 agent runtime**：不只是单轮问答，而是长流程多步骤执行
2. **状态保存升级为平台能力**：事件流保存 session 状态，可恢复、可重读、可追踪
3. **安全边界更清晰**：Git 权限、MCP/OAuth 通过资源初始化、proxy 与 vault 处理
4. **可观测性是一级能力**：Console tracing、raw event retrieval、token 使用量追踪

### 6.5 路线图

- **Multiagent**（research preview）：多代理协作
- **Memory**（research preview）：跨 session 记忆
- **Outcomes**（research preview）：任务目标管理

## 七、核心技能提炼

### 7.1 子代理设计原则

1. **独立上下文窗口**：每次委托创建新上下文，不污染主对话
2. **结果精炼回传**：子代理只返回摘要，不返回完整执行日志
3. **安全隔离**：子代理权限独立控制，可限制工具列表和模型
4. **并行执行**：多个子代理可同时处理不同子任务
5. **可复用定义**：通过 .claude/agents/ 目录定义的子代理可被委托和 Agent Team 队友复用

### 7.2 多 Agent 协作流程

| 模式 | 机制 | 适用场景 |
|------|------|----------|
| **委派（Subagents）** | 主Agent→子Agent→结果回传 | 任务可拆分为独立子任务 |
| **Agent Teams** | 队友间直接通信、共享任务列表 | 需要讨论和协作的复杂工作 |
| **Writer/Reviewer** | 独立会话A编写→会话B审查→会话A修复 | 代码质量保证 |
| **竞争假设** | 多个队友并行探索不同的根因假设 | 复杂调试 |
| **对抗性审查** | 新鲜上下文的子代理审查差异并报告缺陷 | 质量门 |

### 7.3 Claude Code 自动化配置清单

1. `CLAUDE.md`：持久上下文和项目规则
2. `.claude/agents/`：可复用子代理定义（security-reviewer、test-runner）
3. `.claude/skills/`：领域知识和可复用工作流
4. `.claude/settings.json`：Hooks 配置（pre-edit、post-edit、stop hooks）
5. MCP Servers：外部工具集成（Notion、Figma、数据库等）
6. Plugins：社区/Anthropic 提供的捆绑包
7. 权限配置：`/permissions` 允许列表、auto mode 分类器

### 7.4 Agent Teams 调度最佳实践

- **启动方式**：自然语言描述任务和团队结构
- **团队规模**：3-5个队友（平衡并行与协调开销）
- **任务粒度**：每个队友5-6个任务，自包含且产出清晰可交付成果
- **文件分区**：每个队友拥有不同的文件集，避免文件冲突

## 九、Agent Teams v2.1.33-v2.1.45 实战最佳实践（2026-06-11更新）

### 9.1 Delegate Mode（默认开启）

Delegate Mode（Shift+Tab）是 Agent Teams 最关键的控制机制：
- **作用**：限制 Lead Agent 只能执行协调操作，禁止直接实现代码
- **原理**：Lead 只负责分发任务、监控进度、汇总结果，不抢队友的工作
- **团队规模**：3-5个Teammate为实践甜点区。超过5个时协调开销呈指数增长，建议分阶段运行（Phase 1: 3人 → Phase 2: 3人）
- **Vague Prompt 反模式**：`review the auth module` 导致队友浪费token探索代码库。正确写法：`Review src/auth/ for security vulnerabilities. Focus on token handling, session management, input validation. JWT stored in httpOnly cookies. Report issues with severity ratings.`

### 9.2 Plan Mode 行为规则

- Plan Mode 在每位 Teammate 的**整个生命周期**内生效，每轮都评估（非仅一次）
- Teammate 的模式**固定不可切换**：Plan Mode 的队友无法转换为执行模式，需 Spawn 新的 Default Mode 队友接手
- **实战建议**：Plan Mode 用于架构审查/设计角色（只读），Default Mode 用于需要写代码/修改文件的角色
- 若需要 Plan-then-Implement 流程，使用 Plan Approval 功能而非尝试切换模式

### 9.3 文件冲突解决方案

- **首要原则**：每个 Teammate 拥有独立的文件集，杜绝两人编辑同一文件
- **自然隔离**：按目录边界分配，如 `src/api/users/` vs `src/api/billing/`
- **人工隔离**：若项目结构不支持自然隔离，通过任务分解创建隔离：`refactor API layer` → 拆分为 `refactor user endpoints in src/api/users/` + `refactor billing endpoints in src/api/billing/`
- **不可避共享文件**：在 CLAUDE.md 标记为 `coordinate before editing`，由 Lead 通过任务排序管理访问

### 9.4 任务规模黄金法则

- 每个 Teammate 5-6个任务（每个独立可交付）
- 1个巨量任务 = 无自然检查点 → 高风险浪费
- 5-6个聚焦任务 = 每次完成上报进度 → 可及时转向

### 9.5 渐进式上手路径

1. 从研究/审查任务开始（Review PR、Research库、Investigate Bug）——无代码破坏风险
2. 熟悉团队协作动态后切入实现任务
3. 始终执行 Ctrl+T 定期监控，无人值守过久 = 风险累计

### 9.6 Troubleshooting 速查

| 症状 | 根因 | 修复 |
|------|------|------|
| 队友在文件上互相覆盖 | 共享文件无隔离 | 明确定义文件边界 |
| Lead 在执行而非协调 | Delegate Mode 未开启 | Shift+Tab 开启 |
| 任务永远"In Progress" | 任务过大无check-in点 | 拆分为5-6个小任务 |
| Token燃烧无结果 | Prompt太模糊 | 加入具体路径+验收标准+约束 |
| Plan Mode队友不写代码 | 模式固定不可切换 | Spawn新Default Mode队友 |

## 十五、Dynamic Workflows 动态工作流 — 2026年6月11日正式发布（R66新增 · ⭐核心）

> Claude Code 的最新能力：根据任务动态生成 JavaScript 工作流，协调多个子 Agent，将复杂任务分解为可并行执行的子任务。

### 15.1 定位与核心价值

**核心转变**：从"单 Agent 在单一上下文内规划并执行"到"动态生成 Harness，调度多个拥有独立上下文的子 Agent 并行处理、交叉验证、迭代汇总"。

**解决三大单Agent固有缺陷**：

| 缺陷 | 表现 | 工作流解法 |
|------|------|------|
| Agentic Laziness（惰性早停） | 50项安全审查只处理了35项就宣布完成 | 拆给多个子Agent，各自独立验证 |
| Self-preferential Bias（自我偏好） | 自己验证自己输出时倾向认可自我 | 独立验证Agent进行对抗式检查 |
| Goal Drift（目标漂移） | 长任务中逐渐偏离原始目标 | 子Agent拥有独立上下文和更聚焦目标 |

### 15.2 激活方式

- 明确要求 Claude 创建工作流
- 启用 `ultracode` 设置 → Claude 自动判断何时启用工作流
- `/goal` + `/loop` 结合使用

### 15.3 技术特点

- 执行一段 JavaScript 文件，含特殊函数创建/协调多个 subagent
- 每个子 Agent 可独立选择模型（成本控制+效果优化）
- 独立 worktree 隔离（大规模重构互不干扰）
- 中断后可从中断位置继续执行（长期运行支持）
- 可通过 `s` 保存工作流，check in 到 `~/.claude/workflows`，或通过 skill 分发

### 15.4 六种模式（Pattern Map）

| 模式 | 英文名 | 流程 | 适用场景 |
|------|------|------|------|
| 分类-行动 | Classify-and-act | 分类Agent判断类型 → 路由到对应Agent | 工单分类（Bug/反馈/咨询） |
| 扇出-合成 | Fanout-and-synthesize | 任务拆成小步骤 → 并行执行 → 汇总 | 80条技术说法逐一核查 |
| 对抗式验证 | Adversarial verification | 产出Agent生成 → 验证Agent检查 → 反驳Agent复核 | 代码审查/安全分析/事实核查 |
| 生成-筛选 | Generate-and-filter | 批量生成候选 → 评分/去重/筛选 | 命名/方案/架构候选项 |
| 锦标赛 | Tournament | 多Agent不同思路 → 两两比较 → 评审Agent选出胜者 | CLI工具命名/产品方案选择 |
| 循环至完成 | Loop until done | 持续启动Agent直到停止条件满足 | 调试/根因分析/持续分拣 |

### 15.5 六大使用场景

1. **大规模迁移与重构**：项目级字段改名/代码迁移，子Agent在独立worktree中修改，最后统一审查合并
2. **深度研究**：`/deep-research` skill 已用上，并行搜索→抓取→对抗验证→合成报告
3. **深度验证**：抽取待核查声明→逐条验证→检查来源质量
4. **大规模排序**：1000行数据不能塞一个prompt → 两两比较/先分桶再排序
5. **记忆与规则遵守**：每条规则配一个 verifier agent → 从历史纠错中沉淀回 CLAUDE.md
6. **根因分析**：不同Agent从不同证据提假设 → 验证Agent+反驳Agent分别检查

### 15.6 限制与建议

- 消耗远高于典型 Claude Code 会话
- 建议从规模小、范围明确的任务开始
- 改一个函数/补一个测试 → 普通 Claude Code 足够
- 可用性：Claude Code Max/Team/Enterprise + Claude API + Bedrock/Vertex AI/Foundry

## 十六、Agent Harness 设计哲学（R66新增 · Dynamic Workflows启示）

### 16.1 Harness 定义

Agent Harness 是一套"让 Agent 更有组织地干活"的执行框架。负责：
- 任务拆解策略
- Agent 调用方式
- 上下文隔离方案
- 结果合并逻辑
- 中断恢复机制

**Claude Code 设计路径演进**：
```
默认 Harness（单Agent单上下文）
  → 开发者手写自定义 Harness（静态工作流，通用但僵化）
```

| # | 原则 | 说明 |

### 17.4 四层扩展栈设计哲学

Claude Code 的扩展能力由四层解耦架构构成，每层解决不同维度的问题：

| 层级 | 问题域 | 决策原则 | 典型场景 |
|------|--------|---------|---------|
| **Skills** | 行为知识（怎么做） | 任务需要"知道什么"而非"连接什么" | 代码规范、测试策略、领域知识 |
| **Hooks** | 自动化规则（必须做） | 行为可以在事件触发时脚本化 | 自动lint、安全检查、会话停止反思 |
| **Agents** | 空间隔离（在哪做） | 任务需要独立上下文、并行执行 | 代码审查、多角度分析、大规模迁移 |
| **MCP** | 外部能力（用什么做） | 需要访问外部系统或数据源 | 数据库查询、API调用、文件系统访问 |

**四层协作流程图**：
```
用户任务
  │
  ├→ Skills 注入知识（如"用TDD方式开发"）
  │
  ├→ Hooks 自动触发（如"每次编辑后运行lint"）
  │
  ├→ Agents 并行分解（如"审查+测试+文档三路并行"）
  │
  └→ MCP 外部连接（如"查询GitHub PR详情"）
```

**常见误用与纠正**：

| 误用 | 正确做法 |
|------|---------|
| 把简单Shell脚本做成Skill | 只有需要LLM推理的流程才做成Skill |
| 在Hook中做复杂逻辑 | Hook应轻量（<500ms），重逻辑交给Agent |
| 给Agent全部MCP工具 | 按需分配，测试Agent只需要database-mcp |
| 为单次任务创建Agent | Agent适合复用场景，单次任务用子代理即可 |

**Worktree隔离机制**：
- 每个子Agent在独立 Git worktree 中工作
- 大规模重构互不干扰
- 最终由Lead Agent统一审查合并
- 类似多分支并行开发 → 代码评审 → 合并主干

### 17.5 四件套进阶路径
