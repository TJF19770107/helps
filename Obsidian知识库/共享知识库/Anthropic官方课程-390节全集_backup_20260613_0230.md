### 4.4 Introduction to Subagents

- **报名链接**：https://anthropic.skilljar.com/introduction-to-subagents
- **核心价值**：保持主 Context 干净专注，结果只传回主对话

**课程重点（设计原则而非操作细节）**：
- 结构化输出格式：子代理返回结果的标准化 schema
- 遇到阻碍时如何回报：异常处理与降级机制
- 工具存取范围限制：只读/读写/执行三级权限
- **Anti-Pattern 讨论**（官方文件缺失但在课程中明确）：
  - 子代理不是越多越好：3~8个是最佳范围
  - 过度拆分导致协调成本 > 并行收益
  - 粒度判断：独立可并行的任务才拆
- **与 Agent Teams 的区分**（v2.1.32+）：
  | 维度 | Subagents | Agent Teams |
  |------|-----------|-------------|
  | Context | 独立Context Window，结果返回主代理 | 独立Context Window，队友直接通信 |
  | 通信 | 仅向主代理汇报 | 队友间直接互发消息 |
  | 协调 | 主代理管理所有工作 | 共享任务列表自我协调 |
  | 适用 | 只需结果、专注任务 | 需讨论协作、复杂工作 |
  | Token成本 | 较低（摘要回传主Context） | 较高（每个队友独立Claude实例） |

**子代理类型（内置）**：
| 类型 | 工具权限 | 适用场景 |
|------|---------|---------|
| Explore 代理 | Glob/Grep/Read（只读） | 代码库探索、架构分析 |
| Plan 代理 | 全部只读工具 | 方案设计、技术选型 |
| Bash 代理 | Bash/Read/Grep | 命令执行、测试运行 |
| Code 代理 | Edit/Write/Read/Grep/Glob | 代码编写与修改 |

## 五、Claude Agent Teams（2026年3月实验性功能）

### 5.1 核心架构

```
Team Lead（队长）
    ├── Frontend Agent（前端）
    ├── Backend Agent（后端）
    ├── Security Agent（安全）
    ├── Testing Agent（测试）

```

### 5.2 与普通 Sub-Agent 的关键区别

| 对比维度 | 普通 Sub-Agent | Agent Teams |
|---------|---------------|-------------|
| 执行方式 | 队长依次调用 | 全员同时开工 |
| 互动模式 | 单次任务 | 实时协作 + 互相审查 |
| 上下文 | 独立隔离 | 共享 Workspace |
| Agent数量 | 1~5 | 3~15 |
| 适用场景 | 简单的任务拆解 | 复杂项目团队协作 |

## 六、Agent SDK 子代理编程接口

### 6.1 定义方式

```javascript
import { query } from '@anthropic-ai/claude-agent-sdk';

const result = query({
  prompt: "审查认证模块的安全问题",
  options: {
    agents: {
      'code-reviewer': {
        description: '代码审查专家。用于质量、安全、可维护性审查。',
        prompt: `你是代码审查专家，擅长安全、性能和最佳实践。
审查时：识别安全漏洞 / 检查性能问题 / 验证编码标准 / 提出具体改进建议。`,
        tools: ['Read', 'Grep', 'Glob'],
        model: 'sonnet'
      },
      'test-runner': {
        description: '运行和分析测试套件',
        prompt: '你是测试执行专家...',
        tools: ['Bash', 'Read', 'Grep'],
      }
    }
  }
});
```

### 6.2 AgentDefinition 配置字段

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| description | string | 是 | 何时使用此Agent的自然语言描述 |
| prompt | string | 是 | Agent的系统提示词 |
| tools | string[] | 否 | 允许的工具列表；省略则继承全部 |
| model | 'sonnet'/'opus'/'haiku'/'inherit' | 否 | 模型覆盖；默认继承主模型 |

### 6.3 工具权限模式

| Agent类型 | 工具配置 | 说明 |
|-----------|---------|------|
| 只读分析 | `['Read', 'Grep', 'Glob']` | 分析审查，不能修改 |
| 测试执行 | `['Bash', 'Read', 'Grep']` | 运行测试，读取结果 |
| 代码修改 | `['Read', 'Edit', 'Write', 'Grep', 'Glob']` | 完整读写能力 |

### 6.4 文件系统定义方式

```yaml
# .claude/agents/code-reviewer.md
---
name: code-reviewer
description: 代码审查专家。用于质量、安全、可维护性审查。
tools: Read, Grep, Glob, Bash
---
你的子代理系统提示词写在这里。
```

- 项目级：`.claude/agents/*.md`（仅当前项目可用）
- 用户级：`~/.claude/agents/*.md`（跨项目可用）
- 编程定义优先于文件系统定义（同名时）

## 七、Claude Code 四件套（Skills / Hooks / MCP / Subagents）

### 7.1 心智模型

```
Skills = AI 的教育（长期记忆与专业知识）
Hooks = AI 的反射（事件触发的自动行为）
MCP   = AI 的感官（对外部系统的实时感知）
Subagents = AI 的双手（并行、隔离的独立执行）
```

### 7.2 CLAUDE.md 框架（WHY-WHAT-HOW）

一个优秀的 CLAUDE.md 应回答三个问题：

```
# WHY（为什么）
这个项目解决什么问题？目标用户是谁？

# WHAT（是什么）
- 技术栈：React 18 + TypeScript + Node.js
- 目录结构：src/ components/ pages/ api/ utils/
- 关键模块：auth（认证）/ payment（支付）/ notification（通知）

# HOW（怎么做）
- 代码风格：ESLint airbnb + Prettier
- Git工作流：feature branch → PR → review → merge
- 测试标准：单元测试覆盖率 > 80%
```

### 7.3 Skills 结构

```
your-skill-name/
├── SKILL.md          # 必选：核心指令 + YAML frontmatter
├── scripts/          # 可选：可执行脚本
├── templates/        # 可选：输出模板
└── references/       # 可选：延迟加载的参考文档
```

**SKILL.md 关键配置**：
```yaml
---
name: sprint-planning

tools: Read, Write, Bash
model: sonnet
---
```

**架构优势**：Claude 会话启动时仅扫描 frontmatter（每个 skill 约 20-50 token），仅在任务匹配时加载完整内容。50个 skill 的库约增加 ~2000 token 开销。

### 7.4 Hooks 配置

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit",
        "hooks": [
          {
            "type": "command",
            "command": "cd $CLAUDE_PROJECT_DIR && npx tsc --noEmit 2>&1 | head -20"
          }
        ]
      }
    ],
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "echo \"[$(date)] $CLAUDE_TOOL_INPUT\" >> ~/.claude/logs/bash-audit.log"
          }
        ]
      }
    ]
  }
}
```

**关键 Hook 事件**：
| 事件 | 触发时机 | 典型用途 |
|------|---------|---------|
| PreToolUse | 工具使用前 | 安全检查、审计日志 |
| PostToolUse | 工具完成后 | 类型检查、测试运行 |
| SessionStart | 新会话开始 | 环境检查、上下文加载 |
| SessionEnd | 退出时 | 清理、总结 |

**Hooks 相对于 Skills 的关键优势**：无条件触发。阻止在生产路径上运行 `rm -rf` 的 hook 比"小心删除"的 Skill 指令更可靠。

### 7.5 MCP 配置

```json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "your-token" }
    },
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres", "postgresql://localhost/mydb"]
    }
  }
}
```

**MCP配置最佳实践**：
1. 分层配置：全局(~/.claude.json) → 项目(.mcp.json) → 本地(.claude/settings.local.json)
2. 控制数量：3个是最佳平衡点，超过5个开始拖慢响应
3. 优先HTTP传输：远程HTTP Server不需要本地安装依赖
4. 权限最小化：只给Agent必要的访问权限

## 十二、R17 新增：Agent SDK 子代理完整配置手册

> 来源：Anthropic官方SDK文档 (code.claude.com/docs/en/agent-sdk/subagents)

### 12.1 子代理三种创建方式

| 方式 | 适用场景 | 特点 |
|------|---------|------|
| 程序化 (agents参数) | SDK应用推荐 | 代码内定义，动态可调 |
| 文件系统 (.claude/agents/) | Claude Code项目 | Markdown文件声明 |
| 内置通用型 (general-purpose) | 快速探索任务 | 无需定义，随时可用 |

### 12.2 AgentDefinition 配置字段

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| description | string | 是 | 自然语言描述何时使用此代理（用于自动匹配） |
| prompt | string | 是 | 子代理的系统提示词 |
| tools | string[] | 否 | 允许的工具列表，省略则继承全部 |
| disallowedTools | string[] | 否 | 从继承工具中移除的工具 |
| model | string | 否 | 模型覆盖（sonnet/opus/haiku/inherit/完整ID） |
| skills | string[] | 否 | 预加载的技能列表 |
| memory | string | 否 | 记忆来源（user/project/local） |
| mcpServers | array | 否 | MCP服务器配置 |
| maxTurns | number | 否 | 最大轮次限制 |
| background | boolean | 否 | 是否作为非阻塞后台任务运行 |
| effort | string/number | 否 | 推理力度（low/medium/high/xhigh/max） |
| permissionMode | PermissionMode | 否 | 工具执行权限模式 |

### 12.3 子代理继承规则

**子代理收到**：
- 自己的系统提示词 (AgentDefinition.prompt)
- Agent工具的提示字符串
- 项目级 CLAUDE.md（通过settingSources加载）
- 工具定义（继承自父代理或限制子集）

**子代理不收到**：
- 父代理的对话历史或工具结果
- 未在skills列表中列出的预加载技能内容
- 父代理的系统提示词

### 12.4 子代理恢复 (Resume)

- 子代理完成后，Agent工具结果包含 `agentId: <id>`
- 可通过 `agentId` 恢复子代理，保留完整对话历史
- 内置Explore和Plan代理为一次性代理，不返回agentId
- 恢复时必须使用相同的session（通过resume参数）

### 12.5 动态代理配置（工厂模式）

```python
def create_security_agent(security_level: str) -> AgentDefinition:
    is_strict = security_level == "strict"
    return AgentDefinition(
        description="Security code reviewer",
        prompt=f"You are a {'strict' if is_strict else 'balanced'} security reviewer...",
        tools=["Read", "Grep", "Glob"],
        model="opus" if is_strict else "sonnet",
    )
```

## 十四、R18 新增：Claude Code 五大核心原语与生产级多Agent工作流（2026-06-12）

> 来源：Anthropic 官方最佳实践（anthropic.com/engineering/claude-code-best-practices）+ 全网实战精华

### 14.1 Claude Code 五大核心原语

Claude Code 的本质是一个可编程的 AI 开发环境。真正理解它，要从五个核心原语开始，它们是脚手架层面的架构能力：

| 原语 | 配置位置 | 加载方式 | 核心价值 |
|------|---------|---------|---------|
| **子代理 (Subagents)** | `.claude/agents/*.md` | 任务匹配时自动创建 | 独立上下文窗口，不污染主对话 |
| **命令 (Commands)** | `.claude/commands/*.md` | 手动 `/命令名` 触发 | 可复用提示词模板 |
| **技能 (Skills)** | `.claude/skills/` | 按需触发（渐进式加载） | 可复用专业流程 |
| **钩子 (Hooks)** | `settings.json` | 事件自动触发（无条件） | 确定性检查点，比提示词更可靠 |
| **记忆 (Memory)** | `CLAUDE.md` | 每次会话自动加载 | 项目背景与规范 |

**心智模型**：
```
Skills = AI 的教育（长期记忆与专业知识）
Hooks = AI 的反射（事件触发的自动行为）
MCP   = AI 的感官（对外部系统的实时感知）
Subagents = AI 的双手（并行、隔离的独立执行）
Commands = AI 的快捷键（一次性操作模板）
Memory  = AI 的常识（项目上下文基线）
```

### 14.2 CLM.md 写作最佳实践（官方推荐）

**核心原则：精炼至上。每一行都要问"删掉这句会让 Claude 出错吗？"——如果是"不会"，就删掉。**

| ✅ 应该包含 | ❌ 不应包含 |
|-----------|-----------|
| Claude 猜不到的 bash 命令 | Claude 读代码就能推断的内容 |
| 与默认不同的代码风格规则 | 标准语言惯例 |
| 测试说明和偏好测试框架 | 详细 API 文档（应链接） |
| 仓库规范（分支命名、PR 惯例） | 频繁变化的信息 |
| 项目特定的架构决策 | 长篇解释或教程 |
| 开发环境特性（必需的环境变量） | 代码库逐文件描述 |
| 常见陷阱或非显而易见的行为 | "写干净的代码"等不言自明规则 |

**强调语法**：使用 `IMPORTANT` 或 `YOU MUST` 提高关键规则的遵循率。

### 14.3 子代理 5 大生产级工作流模式

> 来源：dibi8.com + codewithseb.com 实战模式（2026年5月）

**模式1：并行调研扇出（Parallel Research Fan-Out）**
```
问题：代码库里哪里处理 X？我们处理 Y 的模式是什么？
串行方案：3轮文件读取，父会话塞 40K+ token grep 输出
并行方案：同时派出 3 个 Explore 子代理，每个在独立沙箱执行
父代理收到 3 个精简段落，而非 3 个 grep 倾倒
```

**模式2：风险编辑的 Worktree 隔离**
```
高风险重构/配置变更时，子代理在独立 git worktree 中执行
主代理在原 worktree 继续工作，互不干扰
子代理完成后，主代理审查变更并合并
```

**模式3：Writer/Reviewer 双 Agent 模式**
```
会话 A（Writer）：实现功能 X
会话 B（Reviewer）：全新上下文中审查 @src/X.ts，查找边界情况
→ 新鲜上下文审查更客观——Reviewer 未受实现过程先入为主影响
```

**模式4：Orchestrator-Worker 编排模式**
```
Orchestrator（编排者）→ 任务分解 → Workers（执行者）
Anthropic 内部测试：Opus 4 编排 + Sonnet 4 子代理
性能提升：比单 Agent 模式高 90.2%
关键：Lead 用强大模型（Opus），Worker 用性价比模型（Sonnet/Haiku）
```

**模式5：测试时计算（Test-Time Compute）**
```
一个代理可能导致 bug → 另一个相同模型的代理可以发现
原因：独立的上下文窗口让模型看到不同的东西
应用：避免单一对话上下文过长导致模型能力下降
```

### 14.4 子代理 5 大常见错误

| 错误 | 后果 | 正确做法 |
|------|------|---------|
| 用子代理做实现工作 | 浪费 700K+ token | 子代理仅用于研究/分析，实现由主代理完成 |
| 给所有代理全部工具权限 | 安全风险 + 上下文浪费 | 按需分配：只读/测试/代码修改三类权限 |
| 用描述性名称（如"helper"） | 匹配机制失效 | 使用功能描述性名称（如"security-reviewer"） |
| 忽略上下文压缩 | 上下文膨胀 | 子代理返回精简摘要，不含完整执行日志 |
| 并行文件编辑无协调 | 合并冲突 | 无冲突操作才并行，有重叠部分串行执行 |

### 14.5 MCP 配置进阶

**MCP 三大 Primitives 正确使用时机**：

| Primitive | 控制对象 | 正确时机 | 错误用法 |

### 14.6 Agent Teams 完整指南（Claude Code v2.1.32+ 实验功能）

> **来源**：code.claude.com/docs/zh-CN/agent-teams（官方中文文档）
> **状态**：实验功能，默认禁用。需 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` 启用。
> **版本要求**：Claude Code v2.1.32 或更高

#### 14.6.1 核心概念

Agent Teams 让你协调多个 Claude Code 实例一起工作。一个会话充当团队负责人，协调工作、分配任务和综合结果。队友独立工作，每个都在自己的 Context Window 中，并可以直接相互通信。

**与 Subagents 的关键区别**：Subagents 只能向主代理报告，Agent Teams 队友之间可以直接互发消息、共享任务列表、自我协调。

**Agent Team 组成**：
| 组件 | 角色 |
|------|------|
| Team Lead（团队负责人） | 创建团队、生成队友、协调工作的主 Claude Code 会话 |
| Teammates（队友） | 各自处理分配任务的独立 Claude Code 实例 |
| Task List（任务列表） | 队友认领和完成的共享工作项列表 |
| Mailbox（邮箱） | 代理之间通信的消息系统 |

#### 14.6.2 最佳用例

Agent Teams 增加协调开销，Token 使用量明显多于单个会话。**当队友可以独立运作时效果最好。**对于顺序任务、同一文件编辑或有许多依赖关系的工作，单个会话或 Subagents 更有效。

**最强用例**：
- **研究和审查**：多个队友同时调查问题不同方面，然后分享和质疑彼此发现
- **新模块或功能**：队友各自拥有独立部分，不会相互干扰
- **使用竞争假设进行调试**：队友并行测试不同理论，更快收敛到答案
- **跨层协调**：前端、后端和测试的更改，每个由不同队友负责

#### 14.6.3 团队规模与成本

- **推荐起步**：3~5 个队友（平衡并行工作与可管理协调）
- **无硬限制**：但收益递减，超过一定点额外队友不会按比例加快工作
- **Token 成本**：每个队友都有自己的 Context Window 并独立消耗 Token，成本线性增加
- **任务粒度**：每个队友 5~6 个任务，太小则协调开销超过收益，太大则浪费风险增加

#### 14.6.4 显示模式

| 模式 | 说明 | 要求 |
|------|------|------|
| In-process | 所有队友在主终端内运行。Shift+Down 循环浏览队友 | 任何终端，无需额外设置 |
| Split panes | 每个队友获得自己的窗格。可同时看到所有人输出 | 需要 tmux 或 iTerm2 |

#### 14.6.5 队友管理命令

```bash
# 创建团队
"I'm designing a CLI tool. Create an agent team: one on UX, one on architecture, one devil's advocate"

# 指定队友和模型
"Create a team with 4 teammates. Use Sonnet for each."

# 要求队友计划批准（先规划后执行）
"Spawn an architect teammate. Require plan approval before changes."

# 关闭队友
"Ask the researcher teammate to shut down"

# 清理团队
"Clean up the team"  # 删除共享团队资源
```

#### 14.6.6 使用 Subagent 定义作为队友

生成队友时可以引用已有的 Subagent 定义，定义一次角色即可同时用于委派的 Subagent 和 Agent Team 队友：

```
Spawn a teammate using the security-reviewer agent type to audit the auth module.
```

队友遵守定义中的 `tools` 允许列表和 `model`，但 `skills` 和 `mcpServers` frontmatter 字段不作为队友运行时应用（队友从项目和用户设置加载这些资源）。

#### 14.6.7 最佳实践

1. **给队友足够的 Context**：队友自动加载项目 Context（CLAUDE.md/MCP Servers/Skills），但不继承负责人对话历史。在生成提示中包含特定于任务的详细信息。
2. **适当调整任务大小**：自包含的单位，产生清晰可交付成果（函数/测试文件/审查）。
3. **从研究和审查开始**：新手从有明确边界、不需要编写代码的任务开始。
4. **避免文件冲突**：两个队友编辑同一文件会导致覆盖，分解工作使每个队友拥有不同文件集。
5. **监控和指导**：检查队友进度，重定向不起作用的方法，及时综合发现。

#### 14.6.8 已知限制（实验功能）

- In-process 队友没有会话恢复（/resume 和 /rewind 不会恢复 in-process 队友）
- 任务状态可能滞后（队友有时无法将任务标记为已完成）
- 关闭可能较慢（队友在关闭前完成当前请求）
- 每个会话一个团队（负责人一次只能管理一个团队）
- 没有嵌套团队（队友无法生成自己的团队或队友）
- 负责人是固定的（无法将队友提升为负责人或转移领导权）
- 权限在生成时设置（所有队友从负责人的权限模式开始）

## 九、Claude Code 五层架构详解（R20新增 · 核心专题）

> **来源**：Anthropic 官方2026年5月公布的 Claude Code 五层架构 + 稀土掘金深度解读（chenguangliang.com）

### 9.1 五层架构总览

| 层 | 角色 | 核心问题 | 关键概念 |
|---|------|---------|---------|
| **MCP** | 连接层 | Agent 怎么访问外部世界（API、数据库、私有工具） | 标准化外部接口、三种使用模式 |
| **Skills** | 任务知识层 | 把"playbook"变成可被自动加载的可复用步骤 | SKILL.md、context: fork |
| **Agent** | 主工作者 | 处理你的对话主线，调用工具完成任务 | CLAUDE.md、claude --agent |
| **Subagents** | 并行隔离工作者 | 把"会污染上下文的活"派出去做 | 独立上下文、持久记忆 |
| **Agent Teams** | 多Agent协调层 | 跨会话、跨独立上下文的Agent协作 | SendMessage、长期并行 |

**上下文隔离粒度对比**：

| 层级 | 执行上下文 | 会话范围 | 通信方式 |
|------|-----------|---------|---------|
| Skills | 主对话上下文（除非 context: fork） | 单会话 | 直接注入 |
| Subagents | 每个Subagent独立上下文 | 单会话内 | 单向结果汇报 |
| Agent Teams | 每个成员独立会话 + 独立上下文 | 跨会话 | SendMessage双向通信 |

### 9.2 第一层：MCP（Model Context Protocol）

MCP是底层连接器，解决"让Claude能访问GitHub、数据库、Notion、内部API，不需要给每个服务写自定义代码"。

**三种使用模式**：

1. **全局配置**（.mcp.json）：任何Claude Code会话都能用
2. **Subagent内联**：MCP只在Subagent启动时连接、结束时断开，主对话看不到工具描述，**节省token**
3. **引用全局服务器**：Subagent配置中直接引用全局已定义的MCP服务器名

**决策规则**：需要访问带状态的外部系统→MCP；纯本地脚本逻辑→用Skill比写MCP server简单一个量级。

### 9.3 第二层：Skills

Skills是"任务知识"层——把重复粘贴的指令变成Claude自动加载的资源。

**Skill与Subagent的双向关系**：

| 方向 | 配置方式 | 效果 |
|------|---------|------|
| Skill调Subagent | context: fork + agent: Explore | Subagent类型决定system prompt，Skill内容作为task |
| Subagent用Skills | skills: [api-conventions, ...] | Subagent自己的prompt，Skill内容注入到context |

**决策树**：
- 有"指令模板"想固化 → Skill
  - Skill内容长 + 会产生大量输出 → 加 context: fork
  - 否 → 普通Skill，主对话执行
- 需要"专门类型的工作者"反复出现 → Subagent
  - 有反复使用的领域知识 → Subagent里preload Skills
  - 否 → 直接写在Subagent的system prompt里

### 9.4 第三层：Agent（主工作者）

- 主Agent是对话主线，`claude`命令启动的就是默认Agent
- `claude --agent code-reviewer`让整个会话变成专项Agent
- 主Agent可以spawn Subagent，但Subagent不能spawn其他Subagent（硬约束）
- 嵌套委派方案：Skills（Skill可fork Subagent绕开限制）或chain subagents

### 9.5 第四层：Subagents

**Subagent完整YAML字段**：

| 字段 | 说明 |
|------|------|
| `name` | 唯一标识符 |
| `description` | Claude决定何时委派的关键文本 |
| `tools` / `disallowedTools` | 工具白/黑名单 |
| `model` | sonnet / opus / haiku / 全ID / inherit |
| `permissionMode` | default / acceptEdits / auto / bypassPermissions / plan |
| `skills` | 启动时预加载的Skills列表 |
| `mcpServers` | 仅本Subagent可见的MCP服务器 |
| `memory` | user / project / local — 持久记忆作用域 |
| `isolation: worktree` | 在git worktree里跑，仓库副本隔离 |
| `background: true` | 后台并行执行 |
| `maxTurns` | 最大轮次限制 |
| `hooks` | 事件钩子 |
| `effort` | 努力程度 |
| `initialPrompt` | 初始提示 |

**Subagent持久记忆机制（最被低估的特性）**：
- `memory: project` → `.claude/agent-memory/<subagent-name>/`（含MEMORY.md）
- `memory: user` → `~/.claude/agent-memory/<name>/`（跨所有项目）
- `memory: local` → `.claude/agent-memory-local/<name>/`（不入git）
- Subagent在每次任务后主动更新自己的记忆，下次被调用时先读MEMORY.md

**内置Subagent**：

| Subagent | 模型 | 用途 |
|----------|------|------|
| Explore | Haiku | 只读探索代码库，找文件、读引用 |
| Plan | inherit | plan mode下的研究Agent |
| general-purpose | inherit | 多步任务，需要探索+修改 |
| statusline-setup | Sonnet | 配置status line（隐藏，自动调用） |
| claude-code-guide | Haiku | 回答Claude Code自身的问题 |

### 9.6 第五层：Agent Teams

Agent Teams解决Subagent解决不了的场景：多Agent长期并行 + 跨会话协调。

**启用**：`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 claude`

**适用场景**：
- 长时间运行的复杂项目（设计→实现→测试→文档）
- 各成员需要长记忆和持续状态
- 任务能拆解成几个独立但有交互的子任务

**Subagent vs Agent Teams**：

| 维度 | Subagent | Agent Teams |
|------|---------|------------|
| 生命周期 | 一次性，任务完即结束 | 持续性，长期存在 |
| 通信 | A和B不互相通讯 | 成员间直接通讯（SendMessage） |
| 上下文 | 单上下文树 | 每个成员自己的会话 |
| 复杂度 | 低 | 高（多数场景Subagent+Skills+MCP已够） |

## 十一、Skills / Hooks / MCP / Subagents 四件套分层解析（R20新增 · 核心专题）

> **来源**：CSDN深度解析 + Claude Skills Hub + Anthropic官方文档

### 11.1 一句话定义

| 组件 | 角色 | 一句话 | 最像什么 |
|------|------|--------|---------|
| **Skills** | 任务知识层 | 把"常用做法"封装成可被自动加载的能力包 | 可复用剧本/清单 |
| **Hooks** | 事件驱动层 | 在Claude Code生命周期特定节点自动触发逻辑 | 条件反射 |
| **MCP** | 外部连接层 | 把外部工具/数据库/API标准化接进来 | 感官/接口 |
| **Subagents** | 任务分工层 | 把复杂任务拆给专门代理去处理 | 双手/执行者 |

### 11.2 四件套协同典型场景

```
用MCP接进JIRA、Sentry、数据库
→ 用Subagent先做探索和计划
→ 用Skill固化"修Bug的标准流程"
→ 用Hook在修改后自动跑测试和报告结果
```

### 11.3 先加哪一层的四问判断法

| 问题 | 回答"是"→优先做什么 |
|------|-------------------|
| 是不是总在重复给Claude讲同一套流程？ | **Skill** |
| 是不是希望某些动作在固定时机自动执行？ | **Hook** |
| 是不是总在手动把外部系统的信息复制进聊天？ | **MCP** |
| 任务是不是复杂到一个代理做会把上下文搞得很乱？ | **Subagent** |

### 11.4 常见误解澄清

1. **"Subagent比Skill更高级"** → 错。Skill="把指令固化"，Subagent="把工作者隔离"。简单playbook用Skill就够。
2. **"用了Subagent就比Skill慢/贵"** → 部分对。Subagent启动有延迟，但当任务输出超5K token时用Subagent反而更便宜（大量输出留在子上下文）。
3. **"Subagent能spawn其他Subagent"** → 不能。硬限制。嵌套委派方案：Skills fork Subagent 或 Main Agent chain。
4. **"skills字段把Skill注册给Subagent，Subagent能用/命令调用"** → 错。skills字段是预加载（注入到system prompt），不是注册为可调用的命令。

### 11.5 渐进式学习路径

| 周次 | 任务 | 效果 |
|------|------|------|
| 第1周 | 把所有重复指令变成Skills | 体会"按需加载" |
| 第2周 | 当某个Skill输出爆炸时加 context: fork | 体会上下文隔离 |
| 第3周 | 设计第一个带memory的Subagent | 跨会话累积知识 |
| 第4周 | 把GitHub/Linear/数据库接MCP | 外部状态接入 |
| 第N周 | 真正复杂的产品级协作再考虑Agent Teams | 分布式Agent协作 |

## 十二、子代理设计最佳实践（R20新增）

### 12.1 子代理Spec模板

设计子代理规格时须明确：
- **输入输出格式**：JSON / YAML / 纯文本

### 12.2 并行子代理实战模式

**任务拆解示例**：生成README首段+安装步骤 → 拆成4个子任务：
- iOS（iPhone17）
- macOS

### 12.3 Multi-Agent Orchestration模式（Orchestrator-Subagent）

**架构**：
```
Orchestrator Agent（拆解任务、委派）
  ├── Subagent 1（研究主题）
  ├── Subagent 2（撰写报告）
  ├── Subagent 3（验证输出）
  └── Integration Agent（格式化发布）
```

**决策要点**：
- 独立任务 → 并行（研究+撰写可同时进行）
- 有依赖的任务 → 串行（验证必须在撰写之后）
- 每个Subagent独立上下文，不污染主对话
- 成本控制：设定每个Subagent的token预算上限
