## 第二部分：Claude Code Subagents SDK 核心技术

### 2.1 三种子智能体创建方式

1. **编程式定义（推荐）**：通过 `AgentDefinition` 在代码中创建
2. **文件系统定义**：在 `.claude/agents/` 目录下写 Markdown 文件
3. **内置通用型**：Claude 自动调用内置 `general-purpose` 子智能体

### 2.2 AgentDefinition 完整配置参数

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `description` | string | 是 | 自然语言描述，Claude 据此自动判断何时使用 |
| `prompt` | string | 是 | 子智能体的系统提示词 |
| `tools` | string[] | 否 | 允许的工具列表，空则继承全部 |
| `disallowedTools` | string[] | 否 | 禁止使用的工具 |
| `model` | string | 否 | 模型覆盖（sonnet/opus/haiku/inherit） |
| `skills` | string[] | 否 | 预加载的技能列表 |
| `memory` | string | 否 | 记忆来源（user/project/local） |
| `mcpServers` | array | 否 | MCP 服务器配置 |
| `maxTurns` | number | 否 | 最大自主执行轮次 |
| `background` | boolean | 否 | 是否作为后台任务运行 |
| `effort` | string/number | 否 | 推理努力级别 |
| `permissionMode` | PermissionMode | 否 | 工具权限模式 |

### 2.3 核心优势

- **上下文隔离**：子智能体独立上下文窗口，中间结果不污染主上下文
- **并行化**：多个子智能体并发执行，耗时等于最慢者而非总和
- **专业化**：每个子智能体独立系统提示词和工具权限

### 2.4 子智能体继承规则

| 子智能体能获取 | 子智能体不能获取 |
|---------------|-----------------|
| 自身系统提示词 + Agent tool 的 prompt | 父智能体的对话历史 |
| 项目 CLAUDE.md | 未在 skills 列表中声明的技能 |
| 工具定义（继承或子集） | 父智能体的系统提示词 |

### 2.5 五种内置子智能体类型

| 类型 | 能力 | 工具权限 | 适用场景 |
|------|------|---------|---------|
| Explore | 代码库探索 | Glob/Grep/Read | 快速定位文件、搜索关键词 |
| General-purpose | 全功能 | 全部工具 | 独立完成多步骤任务 |
| Plan | 方案设计 | 只读工具 | 架构规划、任务分解 |
| codex:codex-rescue | 救援诊断 | 共享运行时 | Claude Code 陷入困境时 |
| statusline-setup | 状态栏配置 | 轻量级 | 状态栏设置 |

### 2.6 子智能体恢复（Resume）

- 子智能体可恢复继续上次工作，保留完整对话历史
- 从 Agent tool result 提取 `agentId`，在后续请求中传入 `resume: sessionId`
- 子智能体会话独立于主对话，不受主对话压缩影响
- 默认 30 天自动清理

## 第三部分：提示词工程 · 6 种行为引导模式

### 模式速查表

| 序号 | 模式 | 解决的核心问题 | 一句话抓手 |
|------|------|--------------|-----------|
| 1 | 极简主义指令 | 防止顺手过度工程 | 不该加的别加，少量重复也比过早抽象安全 |
| 2 | 渐进式升级 | 防止失败后死循环或秒放弃 | 先诊断，再调整，最后才求助 |
| 3 | 可逆性意识 | 防止高风险动作误触发 | 难回滚、影响大、对外可见的动作先确认 |
| 4 | 工具偏好引导 | 防止通用工具抢走专用工具 | 把开放选择题改成明确路由 |
| 5 | Agent 委托指引 | 防止多 Agent 协作失控 | 不要偷看，不要抢答，身份先声明 |
| 6 | 数值锚定 | 防止输出失控、成本漂移 | 用具体数字代替"简洁一点" |

### 模式一：极简主义指令

```
# 极简主义模板
不要在任务范围之外增加功能、重构或"顺手优化"。
修复问题时，只修改与当前问题直接相关的代码。
不要为了一次性操作创建新的 helper / util / abstraction。
少量重复代码可以接受，先以可读、可交付为优先。
```

### 模式二：渐进式升级

```
# 渐进式升级模板
当操作失败时，先阅读错误信息并检查当前假设。
不要原样重复同一个动作。
基于诊断结果做一次有针对性的修复。
只有在完成排查后仍然无法前进时，再向用户说明卡点并请求帮助。
```

### 模式三：可逆性意识（风险门）

| 风险类别 | 英文分类 | 典型动作 |
|---------|---------|---------|
| 破坏性操作 | Destructive operations | 删除文件/分支、清理未提交修改、杀进程 |
| 难以逆转 | Hard-to-reverse | force push、reset --hard、改已发布提交 |
| 对外可见 | Actions visible to others | 推代码、关 PR、发消息、改共享环境 |
| 第三方上传 | Uploading to third-party | 发到外部平台、渲染器、gist 等 |

```
# 风险门模板
在执行动作前，先评估：
1) 这件事是否容易回滚？
2) 它是否会影响共享系统、外部用户或他人可见结果？
本地且可逆的动作可以直接做。
难回滚或影响范围大的动作，先确认后执行。
NEVER 做危险操作，除非用户明确要求。
用户一次批准，不代表所有后续场景都自动批准。
```

### 模式四：工具偏好引导

```
# 工具偏好模板
当需要搜索文件时，使用 Glob，而不是 find / ls。
当需要搜索内容时，使用 Grep，而不是 grep / rg。
当需要读取文件时，使用 Read，而不是 cat / head / tail。
当需要编辑文件时，使用 Edit，而不是 sed / awk。
Bash 仅用于真正需要 shell 执行的系统命令。
```

### 模式五：Agent 委托指引

```
# 子 Agent 协作模板
当中间过程不值得保留在主上下文中时，派给子 Agent。
主 Agent 不读取子 Agent 的中间产物，等待完成通知。
结果返回前，主 Agent 只汇报状态，不猜测结论。
子 Agent 需要先确认自身身份：你是执行者，不是主控，不要再次派生。
```

### 模式六：数值锚定

```
# 数值锚定模板
工具调用之间的说明保持在 ≤25 词。
最终回复保持在 ≤100 词，除非任务确实需要更多细节。
子 Agent 汇报保持在 ≤500 词。
提交信息控制在 1-2 句，重点说明"为什么"。
```

## 第四部分：多智能体系统设计原则

> 来源：Anthropic "How we built our multi-agent research system"

### 4.1 架构模式：Orchestrator-Worker（编排者-工作者）

- **主智能体**：分析用户意图 → 制定策略 → 分解任务 → 创建子智能体
- **子智能体**：并行探索不同方向 → 返回结构化结果 → 主智能体整合答案

### 4.2 8 个设计原则

1. **像智能体一样思考**：用模拟和可视化工具观察智能体决策，及时修正失败模式
2. **教会主控智能体如何分工**：为每个子智能体分配清晰目标、输出格式、工具指引和任务边界
3. **根据任务复杂度分配资源**：在提示词中嵌入"规模规则"，简单任务少用资源，复杂任务多用
4. **工具设计与选择至关重要**：工具接口要像人机界面一样清晰，描述明确，避免误用
5. **让智能体自我改进**：利用大模型自身能力优化提示词和工具描述
6. **先广后深搜索策略**：先用宽泛查询探索全局，再逐步聚焦细节
7. **引导思考过程**：通过扩展思考模式让智能体显式规划、评估和调整策略
8. **并行工具调用**：主智能体和子智能体都应并行调用工具

### 4.3 6 条工程化实践经验

1. **结果导向评测**：关注最终结果是否正确，而非过程是否完全按预设执行
2. **LLM 自动评测 + 人工检查**：用大模型自动打分，人工补充发现边界问题
3. **状态管理与错误恢复**：智能体需持久化状态，优雅处理错误，不能简单重启
4. **灰度部署与升级**：采用渐进式部署，避免影响正在运行的智能体
5. **长对话上下文管理**：用摘要、外部记忆等机制防止上下文溢出
6. **子智能体直接产出结构化结果**：如代码、报告等，减少信息损失和 Token 消耗

### 4.4 性能数据

- 多智能体系统（Opus 4 主 + Sonnet 4 子）比单智能体 Opus 4 **高出 90.2%**
- Token 消耗：Agent 约为聊天的 4x，多智能体系统约为聊天的 15x
- 三个因素解释 95% 性能差异：Token 用量（80%）、工具调用次数、模型选择

### 4.5 多智能体系统最适合的三类场景

1. **高价值并行任务**：大量真正独立的子任务可同时执行
2. **超出单上下文窗口**：信息量超过单个模型处理能力
3. **多个复杂工具交互**：需要操作多种不同工具

**不适合的场景**：
- 所有智能体需要共享同一上下文
- 智能体之间存在复杂依赖关系
- 编码任务中可并行部分较少

## 第五部分：Skills / MCP / Hooks 四件套

### 5.1 Claude Skills 机制

- 每个 Skill 是一个包含 `SKILL.md` 的文件夹
- `SKILL.md` 以 YAML front matter 开头，定义名称和描述
- 两类：Anthropic 预置 Skills + 自定义 Skills
- 可组合、可移植、按需加载

**默认 Skills 清单**：
| Skill | 功能 |
|-------|------|
| algorithmic-art | p5.js 生成式艺术 |
| artifacts-builder | React + Tailwind 构建 HTML artifacts |
| brand-guidelines | Anthropic 品牌色与字体 |
| canvas-design | .png/.pdf 视觉设计 |
| internal-comms | 内部沟通文档 |
| mcp-server | 创建 MCP 服务器指南 |
| slack-gif-creator | Slack 优化的 GIF 动图 |
| skill-creator | 创建自定义 Skills 指南 |
| template-skill | 新 Skills 基础模板 |
| theme-factory | 10 个预设主题 |
| webapp-testing | Playwright UI 测试 |

### 5.2 Skills vs MCP

| 维度 | Skills | MCP |
|------|--------|-----|
| 本质 | 自包含知识模块 | 外部系统连接桥梁 |
| 依赖 | 不依赖外部连接 | 依赖外部 API/服务 |
| 用途 | 提供流程性知识 | 提供实时数据与操作 |
| Token 消耗 | 低（按需加载） | 高（需详细上下文） |
| 组合性 | 可组合、可移植 | 通过工具暴露能力 |

**关键结论**：Skills 不替代 MCP，而是让 Claude 更聪明地使用 MCP 工具。

### 5.3 Skills 文件结构

```
.claude/skills/
├── my-skill/
│   ├── SKILL.md        # 核心文件（必选）
│   ├── reference.md    # 参考文件（可选）
│   ├── script.py       # 可执行脚本（可选）
│   └── resources/      # 资源文件（可选）
```

### 5.4 Claude Code 配置体系

```
project/
├── AGENTS.md           # 跨工具通用配置（核心）
├── CLAUDE.md           # 引用 AGENTS.md + Claude Code 专属规则
├── .cursorrules        # Cursor 专属
├── .windsurfrules      # Windsurf 专属
├── CLAUDE.local.md     # 个人偏好（.gitignore）
└── .claude/
    ├── agents/          # 子智能体定义
    ├── skills/          # 自定义 Skills
    └── rules/
        ├── code-style.md
        └── api-rules.md
```

**CLAUDE.md 最佳内容结构**：
1. 常用 Bash 命令（构建、测试、部署）
2. 核心文件和工具函数位置
3. 代码风格指南
4. 项目架构说明
5. 外部依赖和 API 文档链接

## 第六部分：Claude Code 子智能体 Prompt 最佳实践

### 6.1 四个关键原则

1. **提供完整上下文**：不写"根据之前的讨论修复 bug"，而要写明文件路径、函数名、具体行为
2. **区分研究和执行**：明确"只搜索和报告"还是"找到问题后直接修复"
3. **选对子智能体类型**：搜索用 Explore，规划用 Plan，重构用 General-purpose
4. **独立任务才并行**：任务 B 依赖任务 A 的结果则串行执行

### 6.2 不该用 Subagents 的场景

- 简单的单文件编辑
- 已经知道目标文件位置
- 需要连续对话的调试（子智能体是一次性的）

### 6.3 经验法则

如果任务需要搜索超过 3 个文件，或可拆成两个独立子任务，就用 Subagent。否则直接做。

## 第七部分：Multi-Agent Workflow 四种架构模式

### 模式 1：Parallel Fan-Out（并行扇出）
- N 个独立项同时处理
- 使用 Haiku 处理单项（成本低、速度快），Opus 做最终合成
- 吞吐量提升 10x

### 模式 2：Hierarchical Orchestration（层级编排）
- 编排器分解任务 → 派发给工作器 → 收集结果 → 合成
- 每个工作器返回置信度评分

### 模式 3：Checker / Verifier Agent（审核智能体）
- 一个智能体生产，另一个审核验证
- 实现独立质量检查

### 模式 4：Agent-to-Agent Communication（智能体间通信）
- 通过共享上下文实现智能体间直接通信
- 适用于有依赖关系的协作场景
