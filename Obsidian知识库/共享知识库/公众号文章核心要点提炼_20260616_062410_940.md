## 一、文章核心脉络（推断）

根据标题「如何通过 Codex 对话接入飞书完整版来了！」，文章核心价值应覆盖以下维度：

### 1.1 问题起点
- **痛点**：传统飞书操作依赖手动点击、API 开发门槛高、非技术人员无法高效利用飞书自动化能力
- **解决方案**：通过 Codex CLI 的自然语言对话能力，零代码/低代码接入飞书全系 API

### 1.2 技术路线
```
Codex CLI (AI 执行引擎)
    ↕ MCP 协议
飞书开放 API (办公平台)
    ↕
六大办公场景：文档 / Base / 消息 / 日历 / 会议 / 审批
```

### 1.3 预期效果
- **效率提升**：飞书操作从「分钟级手动」→「秒级对话驱动」
- **门槛降低**：非技术人员用自然语言即可操作飞书
- **集成深度**：Codex 沙箱模型保证安全，MCP 协议保证标准化

## 二、可复用的 SOP 模板

### SOP-01：飞书文档自动化工作流

| 步骤 | 操作 | 工具/API | 预期产出 |
|:---:|------|---------|---------|
| 1 | 确认文档需求 | 对话交互 | 文档标题、结构、内容要点 |
| 2 | 生成文档内容 | Codex + LLM | 结构化 Markdown |
| 3 | 创建飞书文档 | `POST /docx/v1/documents` | 文档 ID + URL |
| 4 | 写入内容块 | `POST /docx/v1/documents/{id}/blocks/{id}/children` | 格式化文档 |
| 5 | 设置权限 | `PATCH /drive/v1/permissions` | 按需分享 |
| 6 | 通知相关人员 | `POST /im/v1/messages` | 飞书卡片通知 |

### SOP-02：飞书 Base 数据管理

| 步骤 | 操作 | 工具/API | 预期产出 |
|:---:|------|---------|---------|
| 1 | 明确数据操作类型 | 对话确认 | CRUD 操作定义 |
| 2 | 定位目标表格 | `GET /bitable/v1/apps` | app_token + table_id |
| 3 | 执行数据操作 | `POST/PATCH/DELETE /bitable/v1/apps/.../records` | 操作结果 |
| 4 | 验证数据一致性 | 回读 + 比对 | 确认报告 |

### SOP-03：Codex MCP 飞书接入检查清单

```
□ 飞书开放平台已创建应用
□ 已获取 App ID 和 App Secret
□ 权限 scope 按最小原则配置
□ MCP 服务器已注册（codex mcp add feishu）
□ MCP 连接测试通过（codex mcp test feishu）
□ 环境变量已配置（不硬编码凭证）
□ 速率限制策略已就绪
□ 错误处理与重试逻辑已实现
□ 审计日志已启用
□ 安全合规自检通过（对应协议#235）
```

## 三、关键技术点提炼

### 3.1 MCP 协议在飞书集成中的角色

- **标准化接口**：MCP 统一了 Codex 与飞书之间的工具调用协议
- **安全沙箱**：Codex 的 Seccomp/gVisor/VM 三层沙箱确保飞书操作不会越权
- **凭证隔离**：App Secret 仅在 MCP Server 环境变量中存在，不进入 LLM 上下文

### 3.2 Codex 对话的优势

| 特性 | 传统方式 | Codex 对话方式 |
|------|---------|---------------|
| 操作方式 | 手动点击 / 编写 API 代码 | 自然语言一句话 |
| 学习成本 | 需了解飞书 API 文档 | 零学习，描述需求即可 |
| 错误处理 | 手动 try-catch | AI 自动重试 + 降级 |
| 批量操作 | 逐条执行 | 并行批量处理 |
| 审计追踪 | 手动记录 | Codex 执行日志自动归档 |

### 3.3 安全注意事项

1. **MCP 配置完整性**：定期校验 `mcp.json` 签名（对应协议#227）
2. **Token 管理**：tenant_access_token 有效期 2 小时，需自动刷新
3. **零点击防护**：消息发送需用户确认（对应协议#210）
4. **供应链安全**：MCP 插件来源验证（对应协议#208）
