## 一、多 Agent 编排核心模式（Orchestrator-Subagent Pattern）

> **来源**：Anthropic Claude Certified Architect (CCA) 课程 + aiforanything.io 实战教程

### 1.1 为什么需要多 Agent

单次 Claude 调用存在四大硬限制：
- **上下文窗口上限**：复杂任务需要的信息超出单次 Prompt 容量
- **无并行能力**：顺序推理在子任务独立时效率低下
- **无专业化**：通用 Prompt 无法同时成为研究员、审查员和格式化器
- **无检查点**：在 10000+ Token 的思维链中偏离方向，浪费整次调用

### 1.2 Orchestrator-Subagent 三阶段模式

```
用户请求
     │
     ▼
┌─────────────┐
│ Orchestrator │  ← 拆解任务、管理状态
└──────┬──────┘
       │  派发
  ┌────┴────┐
  ▼         ▼
[Agent A] [Agent B]   ← 子代理：各司其职、并行执行
  │         │
  └────┬────┘
       ▼
  [Integration]       ← 编排器合并结果
       │
       ▼
  最终输出
```

### 1.3 三阶段详解

**阶段 1：编排（Orchestration）**
- 编排器接收用户目标，输出结构化 JSON 子任务定义
- 每个子任务必须独立可完成（无循环依赖）
- 子任务输入自包含，不引用其他子代理

**阶段 2：执行（Execution）**
- 使用 Promise.all() 并行调度所有子代理
- 每个子代理用 try/catch 隔离，单点失败不影响整体
- 子代理用 Haiku 模型（快速便宜），编排器用 Sonnet（强推理）

**阶段 3：集成（Integration）**
- 最终 Claude 调用合成所有子代理输出
- 不简单拼接，需找关联、解决矛盾、产出统一整体
- 保留各子代理输出的事实细节

### 1.4 成本管理四策略

| 策略 | 说明 | 效果 |
|------|------|------|
| Haiku for focused tasks | 子代理用 Haiku，比 Sonnet 便宜 **20 倍/Token** | 子代理成本 ~$0.0003/次 |
| Structured outputs reduce tokens | 要求子代理返回 JSON/Markdown 表格而非散文 | 输出 Token 减少 40-60% |
| Gate expensive calls | 用廉价分类Agent判断是否需要全管道 | 避免不必要的高成本调用 |
| Cache orchestration plans | 同类任务缓存编排器计划，只重新执行子代理 | 编排成本归零 |

### 1.5 常见错误与规避

| 错误 | 说明 | 解决方案 |
|------|------|---------|
| 循环依赖 | 子代理 B 需要子代理 A 的输出 | 设计真正独立的子任务，或分阶段串行执行 |
| 全量上下文传入 | 每个子代理接收所有信息 | 每个子代理只收到必需信息 |
| 无输出验证 | 子代理可能返回格式错误或幻觉 | 始终验证再传给集成器 |
| 无界并行 | 一次启动 20+ 子代理触发速率限制 | 使用 p-limit 限制并发 5-10 |

### 1.6 并行控制最佳实践

```typescript
import pLimit from "p-limit";
const limit = pLimit(5); // 最多 5 个并发

const results = await Promise.all(
  subtasks.map((task) =>
    limit(() => runAgent(task.systemPrompt, task.input))
  )
);
```

### 1.7 何时用多 Agent vs 单次调用

| 场景 | 方案 |
|------|------|
| 简单 Q&A、单步生成 | 单次调用 |
| 2+ 独立子任务 | 多 Agent（并行） |
| 需要 >100K Token 上下文 | 多 Agent（拆分上下文） |
| 需要专家专业化 | 多 Agent（专用系统提示） |
| 实时响应 <2s | 单次调用或用 Haiku 预计算 |
| 成本敏感、简单输出 | 单次调用 + Haiku |

## 二、Claude Agent SDK 深度解析

> **来源**：Anthropic 官方文档 + Charlie Fei 深度解析 + Claude Agent SDK 源码

### 2.1 SDK 定位与历史

- Claude Code as a Library：将 Claude Code 完整引擎暴露为可编程库
- 支持 TypeScript（npm `@anthropic-ai/claude-agent-sdk`）和 Python（pip `claude-agent-sdk`）
- 2025年9月首发 → 2025年底更名 Agent SDK → 截至2026年3月 npm 130+ 版本、Python 4800+ Stars
- 2026年6月15日起 SDK 和 `claude -p` 从独立额度池扣费

### 2.2 14 种内置工具

| 工具 | 用途 | 龙虾对标 |
|------|------|---------|
| `Read` | 读取工作目录中任意文件 | `read_text` |
| `Write` | 创建新文件 | `write_file` |
| `Edit` | 精确编辑已有文件（字符串替换） | `edit_file` |
| `Bash` | 执行终端命令、脚本、Git 操作 | `shell_executor` |
| `Glob` | 按模式匹配查找文件 | file-agent 搜索 |
| `Grep` | 正则搜索文件内容 | file-agent 搜索 |
| `WebSearch` | 搜索互联网最新信息 | `web_search` |
| `WebFetch` | 抓取并解析网页内容 | `web_fetch` |
| `AskUserQuestion` | 向用户展示多选问题 | `ask_user` |
| `Task` | 派发子代理 | `dispatch_task` |
| `Skill` | 调用自定义技能 | `use_skill` |
| `ToolSearch` | 动态发现和按需加载工具 | - |
| `Monitor` | 监控后台脚本并响应输出 | - |

### 2.3 Agent Loop 消息类型体系

| 消息类型 | 含义 | 关键字段 |
|---------|------|---------|
| `SystemMessage` | 会话初始化、上下文压缩等系统事件 | `subtype`: `"init"` 或 `"compact_boundary"` |
| `AssistantMessage` | Claude 回复（文本或工具调用） | `message.content`: TextBlock 或 ToolUseBlock |
| `UserMessage` | 用户输入或工具执行结果 | `message.content` |
| `ResultMessage` | Agent 循环最终结果 | `subtype`, `result`, `total_cost_usd`, `session_id` |

### 2.4 六种权限模式

| 模式 | 行为 | 适用场景 |
|------|------|---------|
| `default` | 不在允许列表的工具触发回调 | 自定义审批流 |
| `acceptEdits` | 自动批准文件编辑和常用文件系统命令 | 受信任的开发工作流 |
| `plan` | 只读模式，不修改任何文件 | 方案设计和分析 |
| `dontAsk` | 从不提示，仅允许规则中的工具 | 锁定无头 Agent |
| `auto`（仅 TS） | 模型分类器决定是否批准 | 带安全护栏的自动 Agent |
| `bypassPermissions` | 运行所有允许的工具不询问 | 沙盒 CI、完全信任环境 |

### 2.5 会话管理三种模式

| 模式 | 行为 | 使用场景 |
|------|------|---------|
| Continue | 自动找到当前目录最近一次会话 | 日常连续工作 |
| Resume | 指定 Session ID 恢复特定会话 | 精确恢复上下文 |
| Fork | 从某个 Session 分叉出新分支 | 方案探索、A/B 测试 |

**设计原则**：一个 `query()` 调用 = 一个完整任务单元（内部可有多个 turn）。不要把任务拆成多个独立 query()。

### 2.6 子代理（Subagents）配置

```yaml
agents:
  security-reviewer:
    description: 安全漏洞检测专家
    prompt: 专注 SQL 注入、XSS、CSRF、暴露凭证、不安全认证
    tools: [Read, Grep, Glob]
    model: sonnet
  test-analyzer:
    description: 测试覆盖率和质量分析
    prompt: 分析测试覆盖、边界情况、测试质量
    tools: [Read, Grep, Glob]
    model: haiku  # 简单任务用更快便宜的模型
```

**子代理模型选择策略**：
- 重度推理（架构分析、Bug 定位）→ Opus
- 中等复杂度（代码审查、重构）→ Sonnet
- 轻量任务（测试分析、文件统计）→ Haiku

### 2.7 结构化输出（JSON Schema）

支持通过 `outputFormat` 强制 Agent 按 JSON Schema 返回结构化数据：
```json
{
  "type": "json_schema",
  "schema": {
    "type": "object",
    "properties": {
      "issues": { "type": "array", "items": { "type": "object" } },
      "summary": { "type": "string" },
      "overallScore": { "type": "number" }
    }
  }
}
```

### 2.8 成本追踪

每个 `ResultMessage` 包含：
- `total_cost_usd`：总花费
- `usage`：Token 用量
- `modelUsage`：按模型细分（使用子代理时尤其有用）

### 2.9 Hooks 钩子系统

| Hook | 触发时机 | 常见用途 |
|------|---------|---------|
| `PreToolUse` | 工具执行前 | 校验输入、阻止危险命令 |
| `PostToolUse` | 工具返回结果后 | 审计输出、触发副作用 |
| `UserPromptSubmit` | 用户发送 prompt 时 | 注入额外上下文 |
| `Stop` | Agent 完成时 | 验证结果、持久化会话状态 |
| `SubagentStart/Stop` | 子代理启动/完成 | 追踪并行任务 |
| `PreCompact` | 上下文压缩前 | 存档完整对话记录 |

## 三、Agent Skills 官方标准

> **来源**：Anthropic 官方工程博客 "Equipping agents for the real world with Agent Skills" (2025.12.18)

### 3.1 Skills 的核心设计：渐进式加载（Progressive Disclosure）

Skill 是一个包含 `SKILL.md` 文件的目录，分三层加载：

| 层级 | 内容 | 加载时机 | 上下文占用 |
|------|------|---------|-----------|
| 第一层 | YAML frontmatter（name + description） | Agent 启动时预加载 | 极少（每个 Skill ~50 token） |
| 第二层 | SKILL.md 正文 | Agent 判断当前任务需要时 | 完整 Skill 正文 |
| 第三层+ | 关联文件（references/、scripts/） | Agent 按需读取 | 仅读所需文件 |

**核心优势**：可以安装 50 个 Skills，Agent 只加载当前真正需要的几个。

### 3.2 Skill 文件结构

```
skill-name/
├── SKILL.md        # 必须：主文件（必须全大写）
├── scripts/        # 可选：可执行脚本（Python、Bash 等）
├── references/     # 可选：参考文档，按需加载
└── assets/         # 可选：模板、图标等资源
```

### 3.3 SKILL.md 规范

```markdown
---
name: code-review
description: 代码审查流程。Use when user asks to "review code", "check PR", or "审查代码".
---

## 审查流程
1. 读取变更文件列表（git diff）
2. 对照项目代码规范逐文件检查
3. 输出审查报告，按严重程度分级
4. 如果发现严重问题，阻止合并
```

**关键原则**：
- description 必须包含具体触发词（不能模糊）
- 步骤必须具体可执行
- 考虑异常情况和错误处理

### 3.4 Skills vs MCP 互补关系

| 维度 | Skills | MCP |
|------|--------|-----|
| 是什么 | 知识、工作流和参考材料 | 连接外部服务的协议 |
| 给予 Claude | 关于如何有效使用工具的知识 | 与外部系统交互的能力 |
| 类比 | 菜谱（告诉你如何组合食材） | 专业厨房（提供工具和食材） |

### 3.5 Skills 安全注意事项

- 仅从可信来源安装 Skills
- 安装前审计：读取 SKILL.md 和 bundled 脚本
- 特别注意代码依赖和外部网络连接
- Agent Skills 已发布为跨平台开放标准：[agentskills.io](https://agentskills.io/)

## 四、CLAUDE.md/Skills/MCP/Hooks 四件套实战

> **来源**：popring.cn 深度指南 + Anthropic 官方文档

### 4.1 四件套定位（类比员工入职）

| 组件 | 类比 | 解决问题 | 表现形式 | 加载方式 | 执行方式 |
|------|------|---------|---------|---------|---------|
| **CLAUDE.md** | 员工手册 | "这是什么项目" | Markdown 文件 | 自动加载 | LLM 推理 |
| **Skills** | SOP 流程 | "遇到 X 怎么做" | Markdown 文件 | 按需触发 | LLM 推理 |
| **MCP** | 工具箱接口 | "能用什么工具" | Server 服务 | 按需连接 | LLM 推理 |
| **Hooks** | 流水线钩子 | "自动执行任务" | Shell 脚本 | 事件触发 | 确定性脚本 |

**核心区别**：CLAUDE.md + Skills = 知识层；MCP + Hooks = 能力层

### 4.2 CLAUDE.md 写法：WHY-WHAT-HOW 框架

```markdown
# CLAUDE.md

## 项目概览（WHY）
这是一个面向 B2C 的电商项目，支持多语言、多币种。

## 技术栈与目录结构（WHAT）
Next.js + TypeScript + Tailwind CSS
src/
├── app/          # Next.js App Router 页面
├── components/   # 共享组件
├── lib/          # 工具函数
└── services/     # API 调用层

## 开发规范（HOW）
- 使用 pnpm 作为包管理器
- 提交前运行 pnpm lint && pnpm test
- 不要修改 .env 文件
```

### 4.3 CLAUDE.md 关键原则

1. **少即是多**：控制在 300-500 行以内
2. **只放全局通用信息**：特定任务指令放 Skills
3. **不要写代码风格**：交给 ESLint/Prettier/Biome
4. **指向而非复制**：引用文件路径比粘贴代码片段更好
5. **渐进式信息披露**：详细文档放单独目录，CLAUDE.md 只列索引

### 4.4 CLAUDE.md 三层生效机制

```
~/.claude/CLAUDE.md          ← 全局：所有项目通用偏好
项目根目录/CLAUDE.md          ← 项目级：团队共享规范
项目子目录/CLAUDE.md          ← 模块级：特定目录规则
```

加载规则：所有层级都加载，冲突时更具体的覆盖更宽泛的。

### 4.5 Skills 的两种类型

| 类型 | 触发方式 | 例子 |
|------|---------|------|
| 参考型（知识库） | Claude 自动判断 | API 风格指南、错误处理模式 |
| 操作型（工作流） | `/skill-name` 手动触发 | `/deploy`、`/code-review` |

**省上下文技巧**：对副作用操作型 Skill 加 `disable-model-invocation: true`，对 Claude 完全隐藏，仅手动调用。

### 4.6 Hooks 典型场景

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{"type": "command", "command": "pnpm lint-staged"}]
      }
    ],
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{"type": "command", "command": "./scripts/validate-commit.sh"}]
      }
    ]
  }
}
```

### 4.7 四件套配合编排示例

```
PR 被创建
  │
  ▼
Agent 启动 → 自动加载 CLAUDE.md（理解项目规范）
  ▼
触发 pr-review Skill（按流程逐步执行）
  ▼
通过 GitHub MCP 读取 PR diff
  ▼
逐文件审查 → 生成审查报告
  ▼
通过 GitHub MCP 提交 Review Comments
  ▼
PostToolUse Hook 触发 → 自动 lint-staged
  ▼
通过 Slack MCP 发送通知 → 完成
```

## 五、Claude Code 五件套完整指南

> **来源**：123ai.org 五件套指南 + Anthropic 官方文档

### 5.1 五件套全家福

| 组件 | 作用 | 触发方式 |
|------|------|---------|
| **Commands** | 快捷入口，一键跑工作流 | 你主动调用 `/xxx` |
| **Skills** | 可复用技能，AI 自动判断何时用 | AI 自动识别场景 |
| **Subagents** | 子代理，专家团队干专业活 | 主 AI 派发任务 |
| **Hooks** | 钩子，关键时刻自动触发脚本 | 事件自动触发 |
| **MCP** | 外部系统连接，让 AI 会做事 | AI 调用外部工具 |

### 5.2 七周学习路径

| 周次 | 任务 | 目标 |

## 六、Dynamic Workflows（编排即代码）

> **来源**：Anthropic Dynamic Workflows（2026-05-28）+ SimonAKing 深度解析

### 6.1 核心理念

编排即代码：把协调逻辑从 LLM 上下文窗口移出，放入运行时 JavaScript 脚本。

### 6.2 五大设计原则

| 原则 | 说明 |
|------|------|
| **编排即代码** | 编排脚本掌管循环/分支/中间变量，运行时执行，LLM 上下文只收最终答案 |
| **对抗式验证** | 独立 Agent 反驳检验，避免"自我评估者总倾向于证实自己" |
| **脚本保存与复用** | 工作流脚本保存为 `/命令`，可审计可重跑 |
| **中间状态不回流上下文** | 子 Agent 中间结果存在脚本变量中，不回流 LLM 上下文窗口 |
| **运行时沙盒隔离** | 脚本本体无文件系统/shell 权限，只有被派发的子 Agent 可读写 |

### 6.3 六层架构

```
MCP → Skills → Agent → Subagents → Agent Teams → Dynamic Workflows
(连接层) (知识层) (工作者) (并行隔离) (协调层)   (编排层)
```

### 6.4 关键指标

- 最多协调 1000 子 Agent，最高并行 16
- 内置 `/deep-research` 工作流
- Bun 案例：4 段串联 Workflow，11 天完成 75 万行 Zig→Rust 迁移

### 6.5 运行时沙盒权限模型

| 执行单元 | 文件系统 | Shell | MCP 工具 | 说明 |
|---------|:---:|:---:|:---:|------|
| Workflow 脚本本体 | ❌ | ❌ | ❌ | 仅控制流逻辑 |
| 被派发的子 Agent | ✅ | ✅ | ✅ | 按各自工具白名单 |
| 对抗式验证 Agent | 只读 | 只读 | 只读 | 只做反驳判断 |
