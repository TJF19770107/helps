## 第二部分：Claude Code 核心扩展层架构

### 2.1 六层扩展体系

Claude Code 的扩展能力分为六层，每一层解决不同的问题：

| 扩展层 | 作用 | 加载时机 | 典型用途 |
|--------|------|----------|----------|
| CLAUDE.md | 持久上下文，每次会话自动加载 | 每次会话 | 项目约定、编码规范、always-do 规则 |
| Skills | 可复用知识与工作流 | 手动调用或自动触发 | 部署检查清单、API 文档、重复性任务 |
| Subagents | 隔离上下文运行，仅返回摘要 | Claude 判断触发或手动委派 | 研究任务、代码审查、并行处理 |
| Hooks | 生命周期事件触发 | 匹配事件时自动执行 | ESLint 检查、自动格式化、CI 触发 |
| MCP | 连接外部服务与工具 | 服务连接时可用 | 数据库查询、Slack 通知、浏览器控制 |
| Plugins | 打包分发以上所有扩展 | 安装后持续可用 | 团队共享能力包、市场分发 |

### 2.2 扩展层对比：谁持有计划、中间结果存哪

| 执行方式 | 谁持有计划 | 中间结果存储 | 隔离上下文 | 并行运行 |
|----------|-----------|-------------|-----------|----------|
| Subagents | 父 Agent | 不存储（返回摘要） | 是 | 最多 10 个 |
| Skills | Claude（加载后执行） | 不存储 | 可选（可委托给 Subagent） | 否 |
| Agent Teams | 协调者 Agent | 线程内消息交换 | 是 | 多个独立会话 |
| Workflows | JS 脚本 | 脚本内部状态 | 不适用 | 可编排数百子代理 |

## 第三部分：子代理（Subagents）完整指南

### 3.1 核心概念

子代理是 Claude Code 中在隔离上下文中运行的专用 AI 代理，处理特定类型任务后仅返回摘要给主会话。核心价值：**上下文隔离 + 并行处理 + 专业化分工**。

### 3.2 官方内置子代理

| 子代理 | 模型 | 工具 | 用途 |
|--------|------|------|------|
| Explore | Haiku | 只读（Read/Grep/Glob） | 快速代码库搜索与分析 |
| Plan | 继承主会话 | 只读 | 规划模式下的代码库调研 |
| general-purpose | 继承主会话 | 全部工具 | 复杂多步任务（探索+修改） |
| statusline-setup | Sonnet | 特定 | /statusline 配置状态栏 |
| claude-code-guide | Haiku | 特定 | Claude Code 功能问答 |

### 3.3 三个配置入口

| 入口 | 位置 | 作用 | 适用范围 |
|------|------|------|----------|
| Agent 工具委派 | 自然语言对话中 | 日常并行处理 | 当前会话 |
| 项目级定义 | `.claude/agents/` | 团队共享，纳入版本控制 | 当前仓库 |
| 用户级定义 | `~/.claude/agents/` | 跨项目复用 | 所有项目 |

### 3.4 子代理定义文件完整 Frontmatter

```yaml
---
name: code-reviewer           # 必填：唯一标识符（小写+连字符）
description: 代码审查专家...  # 必填：描述何时使用此子代理
model: claude-sonnet-4-20250514  # 可选：sonnet/opus/haiku/inherit
tools: [Read, Grep, Glob, Bash]  # 可选：allowlist 白名单模式
denied_tools: [Edit, Write]       # 可选：denylist 黑名单模式
max_turns: 10                     # 可选：最大轮次后自动停止
skills: [my-skill]               # 可选：预载入上下文的技能列表
mcp_servers: [github, slack]     # 可选：可用的 MCP 服务器
memory:                          # 可选：跨会话持久记忆
  enabled: true
  path: ~/.claude/memory/code-reviewer.md
permission_config: default       # 可选：权限模式
effort: high                     # 可选：努力级别
background: false                # 可选：是否后台非阻塞运行
color: blue                      # 可选：UI 标识颜色
allowedAgents:                   # 可选：可spawn的子代理白名单
  - debugger
hooks:                           # 可选：子代理专属 Hook
  PreToolUse:
    - matcher: "Bash"
      hooks:
        - type: command
          command: "echo 'Subagent running bash'"
start_first_turn:                # 可选：自动提交的第一轮提示
  "请审查最新的提交..."
---
```

### 3.6 子代理关键规则

| 规则 | 说明 |
|------|------|
| 最多一层嵌套 | 子代理不能再创建子代理 |
| 最多 10 个并行 | 同一时刻最多 10 个子代理并行运行 |
| 名称覆盖优先级 | 管理 > CLI 标志 > 项目 > 用户 > 插件 |
| 前台 vs 后台 | 前台阻塞等待；后台（Ctrl+B）并发运行，自动拒绝权限提示 |
| Token 成本 | 多 Agent 系统~15× 普通 chat，单 Agent~4× chat |

## 第四部分：多 Agent 协作（Agent Teams）

### 4.1 Orchestrator-Worker 模式



Anthropic Research 产品架构的核心模式：

- **主代理（Orchestrator）**：Opus 4.6+ 负责规划、分解子任务、收集结果、合成、引用对齐
- **子代理（Workers 3-5 个）**：Haiku 4.5 负责并行执行独立子任务
- **效果提升**：内部评测比单 Opus 4 强 90.2%
- **成本代价**：Token 用量约 15× 普通聊天

### 4.2 Claude Managed Agents（CMA）多代理模式

通过 `managed-agents-2026-04-01` Beta 实现的异构团队模式：

```python
BETAS = ["managed-agents-2026-04-01"]
client = anthropic.Anthropic()

# 定义三个专业子代理，各自拥有不同的工具集和上下文
researcher = client.beta.agents.create(
    name="researcher",
    description="研究目标行业",
    system="使用 web_search 搜索行业趋势...",
    tools=[{"type": "agent_toolset_20260401",
            "configs": [{"name": "web_search"}, {"name": "web_fetch"}]}]
)

# 通过 send_to_parent 将结果返回给协调者
```

### 4.3 多 Agent 适用性判断

| 适合多 Agent | 不适合多 Agent |
|-------------|---------------|
| 独立可并行的检索/调研 | 紧耦合的代码任务 |
| 法律尽调、文献综述 | 复杂业务流程（共享大量隐含状态） |
| 跨域信息汇总 | AGent 需要频繁对齐的场景 |
| 总信息量超单窗口容量 | 简单单步任务 |

### 4.4 多 Agent 失败模式分析

综合研究数据：多 Agent 系统失败率 41%-86.7%，其中 **79% 来自规范与协调问题**，非模型能力不足。关键教训：

1. 定义每个 Agent "干什么、不干什么"到文档级清晰度
2. 任务边界划分比模型升级更重要
3. 先单 Agent 跑 baseline，再选择最痛的 1-2 个子任务并行化

## 第五部分：Skills 工程完整指南

### 5.1 Skills 与 Agent Skills 开放标准

Skills 是包含知识、工作流和指令的 Markdown 文件。Claude Code Skills 遵循 Agent Skills 开放标准，可在多个 AI 工具间移植。

### 5.2 渐进式揭露（Progressive Disclosure）

Agent 初始阶段仅看到技能描述，只有在触发时才加载详细指令内容：

| 阶段 | 加载内容 | Token 成本 |
|------|----------|-----------|
| 初始 | `description` 字段 | ~50 tokens |
| 触发后 | 完整 `SKILL.md` 内容 | 按需加载 |
| 未触发 | 零成本 | 0 tokens |

### 5.3 Skills Frontmatter 完整配置

```yaml
---
description: 技能描述，帮助 Claude 判断何时加载
allowed-tools: [Read, Bash]      # 允许使用的工具
model: inherit                   # 使用的模型
---
```

### 5.4 Bundled Skills（内置技能）

| 技能 | 用途 |
|------|------|
| /code-review | 代码质量审查 |
| /batch | 批量处理多个文件 |
| /debug | 交互式调试 |
| /loop | 循环迭代改进 |
| /run | 启动应用验证变更 |
| /verify | 构建运行确认修改 |
| /run-skill-generator | 记录项目构建启动配方 |
| /simplify | 并行审查代码简化 |

### 5.5 Skill 创建步骤

```
1. 创建目录: ~/.claude/skills/my-skill/
2. 编写 SKILL.md（frontmatter + 指令内容）
3. 目录名 = 命令名（如 /my-skill）
4. description 决定 Claude 是否自动加载
```

### 5.6 Skills 作用域优先级

管理级 > 用户级 > 项目级 > 插件级（命名空间隔离）

## 第六部分：MCP 协议 12 大设计模式

### 6.1 工具交互面（Tool Surface）

#### 模式 1：远程优先服务器模式
- MCP Server 远程运行，跨 Web/移动/云端环境访问
- 本地 MCP Server 适合开发环境，远程模式是生产分发形态

#### 模式 2：按意图组织工具模式
- 不要将每个 API endpoint 一对一映射为 tool
- 按用户意图组织：`create_issue_from_thread` 代替四个底层调用
- 工具设计围绕 Agent 的任务体验，不是 API 翻译层

#### 模式 3：薄交互面模式（Thin Surface）
- 适用于 API 面巨大的系统（AWS/Cloudflare/K8s）
- 仅暴露少量高能力工具：`search` + `execute`
- Cloudflare MCP Server 案例：2 个工具覆盖 ~2500 个 endpoint，~1000 tokens

### 6.2 交互语义（Interaction Semantics）

#### 模式 4：内联 UI 模式
- 工具返回可视化界面（Dashboard/图表/搜索结果/审批表单）
- MCP Apps 允许客户端在聊天界面直接渲染可交互 UI

#### 模式 5：引导式输入模式
- 工具调用中途返回表单 schema，请求用户结构化输入
- 适用：缺少参数、多候选项选择、高风险操作确认

#### 模式 6：外部跳转交接模式
- URL Mode Elicitation：Server 返回 URL，用户浏览器完成 OAuth/支付/敏感输入
- 关键：设计 resume-after-redirect 流程

### 6.3 认证与凭证流

#### 模式 7：可发现认证模式
- CIMD（Client ID Metadata Documents）标准化 OAuth 发现
- 客户端无须手工配置 token，通过元数据自动发现认证方式

#### 模式 8：凭证托管到 Vault 模式
- 凭证生命周期上移到平台层（Claude Managed Agents Vault）
- Token 刷新、撤销、轮换由平台负责，不散落在工具代码中

### 6.4 上下文经济（Context Economy）

#### 模式 9：按需加载工具模式
- Tool Search 延迟加载工具定义
- 官方测试：减少 85%+ tool-definition tokens

#### 模式 10：程序化工具调用模式
- Agent 在代码沙箱中处理工具结果（过滤/聚合/排序/统计）
- 官方测试：复杂多步流程减少 ~37% token 使用

### 6.5 打包与分发

#### 模式 11：插件打包模式
- Skills + MCP servers + Hooks + Subagents + LSP 统一打包
- 一次安装获得完整能力包（如 Cowork data plugin：10 Skills + 8 MCP servers）

#### 模式 12：服务器分发 Skills 模式
- MCP Server 不只分发工具，还分发使用工具的方法和操作手册
- 未来方向：工具 + 流程 + 经验 + 安全边界一起交付

## 第七部分：Agent SDK 编程指南

### 7.1 AgentDefinition 核心字段

| 参数 | 说明 |
|------|------|
| `description` | 告诉 Claude 何时使用此子代理 |
| `prompt` | 子代理系统提示词/行为规范 |
| `tools` | 可用工具列表（省略则继承父级） |
| `model` | sonnet/opus/haiku/inherit 或完整模型 ID |
| `background` | 是否非阻塞后台运行 |
| `maxTurns` | 最大 agentic turn 数 |
| `skills` | 注入的技能列表 |

### 7.2 Python SDK 基础用法

```python
from claude_agent_sdk import query, ClaudeAgentOptions, AgentDefinition

async def main():
    async for message in query(
        prompt="使用 code-reviewer 审查代码库",
        options=ClaudeAgentOptions(
            allowed_tools=["Read", "Glob", "Grep", "Agent"],
            agents={
                "code-reviewer": AgentDefinition(
                    description="代码审查专家",
                    prompt="分析代码质量并建议改进...",
                    tools=["Read", "Glob", "Grep"],
                )
            },
            mcp_servers={
                "playwright": {"command": "npx", "args": ["@playwright/mcp@latest"]}
            }
        ),
    ):
        if hasattr(message, "result"):
            print(message.result)
```

### 7.3 子代理上下文注入三种方式

1. **Skills 注入**：在 `skills` 字段指定，完整技能内容注入子代理
2. **Memory 持久化**：子代理可拥有持久记忆目录，跨会话积累知识
3. **工具访问控制**：通过 `tools`/`denied_tools` 精细控制能力边界

## 第九部分：Claude Code 动态工作流

### 9.1 Dynamic Workflows

Claude Code v2.1.154+ 提供动态工作流能力，通过 JavaScript 脚本编排数百子代理：

## 第十部分：上下文工程最佳实践

### 10.1 Context Rot（上下文退化）

Chroma 对 18 个前沿模型的系统测试结论：

- 所有模型随输入变长而退化，退化发生在窗口远未填满时
- 上下文窗口容量 ≠ 模型在该容量下的表现保持
- "塞得进去"不等于"用得好"

### 10.2 三大应对策略

1. **按需检索**：Vector search 粗筛 + JIT 二次检索，不要全部灌入
2. **上下文裁剪**：摘要 + 旧片段裁剪中间步骤
3. **子代理隔离**：小 context 互不污染主代理

### 10.3 Token 经济学计算

| 场景 | Token 倍率 |
|------|-----------|
| 普通 chat | 1× |
| 单 Agent（含工具调用） | ~4× |
| 多 Agent 系统 | ~15× |
| Haiku 子代理输出需主代理用 Sonnet 矫正 >20% | 价格优势被抵消 |

## 第十一部分：Harness Engineering

### 11.1 核心原则

> 不要让 LLM 直接执行工具调用。模型只返回结构化的 tool call，由外层 harness 做 schema 校验、权限检查、沙箱执行。

### 11.2 Harness 三层分工

| 层 | 职责 | 负责方 |
|----|------|--------|
| Skill | "怎么做"（prompt/约定/风格） | 知识层 |
| MCP | "从哪儿拿数据"（DB/API/Slack/Sentry） | 连接层 |
| Subagent | "在哪儿做"（隔离上下文/限制工具范围） | 执行层 |

### 11.3 最小可用组合

Haiku 子代理 + 预加载一组 Skill + 一个 scope 严格的 MCP Server
