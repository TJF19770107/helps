## 二、子代理架构（Agent SDK / Subagents）

### 2.1 Agent SDK 核心概念

```typescript
// AgentDefinition 核心字段
interface AgentDefinition {
  description: string;    // 告诉 Claude 什么时候该用这个子代理
  prompt: string;         // 子代理的系统提示词 / 行为规范
  tools?: string[];       // 子代理可用工具（省略则继承父级）
  model?: "sonnet" | "opus" | "haiku" | "inherit" | string;
  background?: boolean;   // 是否作为非阻塞后台任务运行
  maxTurns?: number;      // 最大 agentic turn 数
  skills?: string[];      // 明确注入的技能列表
}
```

### 2.2 常用子代理类型

| 类型 | 用途 | 可用工具 |
|------|------|---------|
| Explore | 快速搜索代码库（Haiku 驱动，速度最快） | Read、Grep、Glob |
| Bash | 执行终端命令、git 操作 | Bash |
| code-reviewer | 代码审查 | Read、Grep、Glob、Bash |
| general-purpose | 通用多步骤任务 | 全部工具 |
| Plan | 设计实现方案 | 全部（不含写入） |

### 2.3 五种生产级子代理模式（2026）

| # | 模式 | 说明 | 适用场景 |
|---|------|------|---------|
| 1 | **Divide-and-Conquer** | 拆分任务→并行子代理→聚合结果 | 大型代码审查、多文件迁移 |
| 2 | **Specialist Routing** | 按任务类型路由到专家子代理 | 前端/后端/数据库分离处理 |
| 3 | **Parallel Research** | 多角度并行研究→交叉验证 | 技术调研、竞品分析 |
| 4 | **Judge-and-Iterate** | 生成→评委打分→低于阈值重做 | 代码质量保障、文档审查 |
| 5 | **Error-Recovery** | 检测失败→诊断→修复→重试 | 自动化修复流水线 |

### 2.4 编排者-工作者（Orchestrator-Worker）实战

**八步法建造多Agent系统**：

1. **定义数据契约**：子代理输入=自包含子问题+上下文；输出=结构化对象（发现字符串+置信度+来源列表）
2. **任务分解**：主代理将复杂问题拆分为独立子问题
3. **并行派发**：所有子代理同时启动，独立上下文
4. **紧凑交接**：子代理只返回结构化结果，不返回冗长推理过程
5. **合成阶段**：主代理评估每个子代理结果的质量
6. **循环决策**：判断是否需要补充研究或重新派发
7. **引用纪律**：严格标注信息来源
8. **终止条件**：所有证据冲突已解决或达到最大迭代次数

### 2.5 子代理上下文注入三种方式

| 方式 | 说明 | 使用场景 |
|------|------|---------|
| Skills 注入 | 在定义中指定 skills 字段，完整技能内容直接注入 | 专用技能传递 |
| Memory 持久化 | 子代理拥有持久记忆目录，跨会话积累知识 | 长期经验积累 |
| 工具访问控制 | 通过 tools/disallowedTools 精细控制子代理能力 | 安全隔离 |

### 2.6 关键限制

- 子代理不能再创建子代理（只有一层嵌套）
- 最多同时运行 10 个并行子代理（Agent SDK）
- Dynamic Workflows 模式可突破至数百/千级并行

## 三、Skills 技能体系

### 3.1 Skills 本质

Skills 是 Claude 的**长期记忆和专业知识**，用 Markdown + YAML frontmatter 定义可复用的工作流。

```
~/.claude/skills/          ← 全局安装
.claude/skills/            ← 项目特定
```

### 3.2 Skills 最佳实践（Anthropic 内部总结）

| # | 实践 | 说明 |
|---|------|------|
| 1 | description 是触发条件 | 写"什么时候该用"，不是"这个 skill 是什么" |
| 2 | 给信息，也给灵活性 | 避免"必须先做A再做B再做C"，写"通常先做A效果较好" |
| 3 | 避免过度限制 | 让 Claude 根据上下文判断，不要写死路径 |
| 4 | 初始化配置 | 用 config.json 存配置，未配置时用 AskUserQuestion 问用户 |
| 5 | description 写给模型看 | 启动时列出所有 skill description，包括触发词帮助匹配 |
| 6 | 内置记忆 | append-only 文本日志，让 Claude 记住上次执行了什么 |
| 7 | 按需 Hooks | /careful 拦截危险命令、/freeze 限制编辑范围，用完即关 |

### 3.3 Skills 分发路径

- **小团队**：直接提交到 repo 的 `.claude/skills` 目录
- **规模化**：走内部 Plugin Marketplace
- **自然生长**：有人想分享就放到 sandbox，Slack 吆喝，有 traction 再 PR 进 marketplace

### 3.4 Skills 四种方言（SkillOS 范式）

| 方言 | 压缩方式 | 适用场景 |
|------|---------|---------|
| 指令式 | 直接给步骤 | 简单固定流程 |
| 声明式 | 描述期望结果 | 复杂灵活任务 |
| 约束式 | 限定边界条件 | 安全敏感操作 |
| 模板式 | 提供可填充模板 | 重复性生成任务 |

## 四、Hooks 生命周期管理

### 4.1 25 个生命周期事件

Claude Code 提供 25 个 Hook 事件，覆盖完整 Agent 生命周期：

| 阶段 | 事件 | 用途 |
|------|------|------|
| 会话启动 | on-start | 加载项目上下文 |
| 工具调用前 | pre-tool-use | 拦截敏感操作、block .env |
| 文件编辑后 | post-edit | 格式化、类型检查 |
| Bash 执行前 | pre-bash | 阻止破坏性命令 |
| Git 提交前 | pre-commit | 密钥检测、调试代码检查 |
| Git 提交后 | post-commit | 备份、推送、变更日志 |
| 会话结束 | on-stop | 自检提醒、通知 |

### 4.2 12 个生产级 Hook 配置（工业级架构）

```
User prompt → Claude Code session
  → on-start hook: 加载 PROJECT_CONTEXT
  → AI 工作中
    → pre-tool-use hook: block .env
    → Edit file
    → post-edit hook: format + type-check
    → Bash command
    → pre-bash hook: block destructive
    → git commit
    → pre-commit hook: secret / debug / test
    → post-commit hook: backup push + changelog
  → Session end
  → on-stop hook: 自检提醒 + 通知
```

### 4.3 按需 Hooks（用完即关）

| Hook | 功能 | 触发条件 |
|------|------|---------|
| /careful | 拦截 rm -rf、DROP TABLE、force-push、kubectl delete | 碰生产环境时才开 |
| /freeze | 只允许在指定目录里 Edit/Write | 调试时防止顺手修改 |

## 五、Dynamic Workflows 动态工作流

### 5.1 概念

Dynamic Workflows 是一种 JavaScript 脚本，用于编排大规模子代理。Claude 根据任务描述编写脚本，运行时在后台执行。

### 5.2 四种编排方式对比

| 方式 | 谁决定下一步 | 中间结果存放 | 适用规模 |
|------|------------|------------|---------|
| Subagents | Claude，逐轮决定 | Claude 上下文窗口 | 1-10 子代理 |
| Skills | Claude，遵循 prompt | Claude 上下文窗口 | 单任务 |
| Agent Teams | 主代理，逐轮决定 | 共享文件系统 | 3-10 代理 |
| Dynamic Workflows | **脚本** | 脚本变量（不污染上下文） | 数百~千级 |

### 5.3 何时使用 Dynamic Workflows

- 代码库级 Bug 扫描
- 500 文件级迁移
- 需要来源交叉验证的研究问题
- 从多个独立角度起草方案再选择

### 5.4 运行管理

- 脚本可保存、审阅、重跑
- 运行时后台执行，主会话保持响应
- 全流程可视化 Dashboard
- 支持多平台部署：Bedrock / Vertex AI / Foundry

### 5.5 性能数据

- Bun→Rust 75 万行代码迁移
- 99.8% 通过率
- 1000 并行子代理
- 11 天完成大规模工程

## 六、MCP 协议与工具集成

### 6.1 MCP 架构层次

```
Claude Code 应用层
  ↑
Skills / Hooks / Plugins 扩展层
  ↑
MCP 协议层（工具发现、调用、安全）
  ↑
外部工具服务器（stdio / HTTP / SSE）
```

### 6.2 MCP 三大传输方式

| 方式 | 适用场景 | 特点 |
|------|---------|------|
| stdio | 本地进程 | 最简单、延迟最低 |
| HTTP | 远程服务 | 标准 HTTP、负载均衡 |
| SSE | 实时推送 | 服务器推送事件、流式更新 |

### 6.3 延迟加载机制

会话开始时只把工具名称放进上下文，模型需要用的时候通过 ToolSearch 工具按需拉取完整 schema。与 Hermes 的 progressive disclosure 异曲同工。

## 七、Claude Code 四件套扩展体系

### 7.1 四大支柱思维模型

| 组件 | 角色 | 何时使用 |
|------|------|---------|
| Skills | Claude 的长期记忆和专业知识 | 始终——这是基础 |
| Hooks | 事件触发自动反射 | 质量门控和审计追踪 |
| MCP | 与外部系统的实时连接 | 需要实时数据时 |
| 子代理 | 并行、隔离的 Claude 会话 | 大型或独立任务 |

### 7.2 比喻理解

- Skills = AI 的**教育**
- Hooks = AI 的**反射**
- MCP = AI 的**感官**
- 子代理 = AI 的**双手**

### 7.3 Plugins 插件体系

Plugins 把 Skills、Hooks、MCP 配置、子代理定义打包成一个可分发的单元。支持插件市场分发、版本兼容检查、一键安装。

### 7.4 全局与项目级配置

```
~/.claude/
  ├── settings.json       # 全局配置
  ├── skills/             # 全局技能
  ├── hooks/              # 全局钩子
  ├── agents/             # 全局子代理定义
  └── mcp.json            # 全局 MCP 配置

项目/.claude/
  ├── settings.json       # 项目配置（覆盖全局）
  ├── skills/             # 项目特定技能
  └── agents/             # 项目特定子代理
```

## 八、Agent 作为 AI 操作系统

### 8.1 范式转换

2026 年的 Claude Code 不应被理解为"AI 编程助手"，而应理解为**AI 操作系统**——一个配置一次就能放大通过它运行的每个工作流的平台。

### 8.2 五层模块化生态

```
L5: Plugins（打包分发层）
L4: Subagents（并行隔离执行层）
L3: MCPs（外部系统连接层）
L2: Skills（专业知识层）
L1: Claude.md（基础配置层）
```

### 8.3 Developer OS 核心理念

从代码助手进化到模块化操作系统：跨会话持久上下文、五层生态架构、可编程可扩展、社区驱动生长。

## 九、多Agent 协作最佳实践

### 9.1 上下文工程三阶段（ACE）

| 阶段 | 内容 | 目的 |
|------|------|------|
| PROFILE | 项目背景、技术栈、架构决策 | 让 Agent 理解环境 |
| PLAYBOOK | 行为准则、工作流程、质量标准 | 让 Agent 知道怎么做 |
| PROJECT | 当前任务、关键文件、上下文 | 让 Agent 聚焦当前 |

### 9.2 Advisor-Critic 多层决策

- **Advisor（顾问）**：用 Haiku 模型快速生成建议（~12% 成本获得 90% 智能）
- **Critic（评论者）**：用 Opus 模型深度审查
- **三段审查**：技术正确性→业务合理性→安全合规

### 9.3 自验证驱动深度测试时扩展

- 自验证先行：在正式执行前生成预防性修复
- TAPO 轮次级信用分配
- 20+ 轮推理自进化
