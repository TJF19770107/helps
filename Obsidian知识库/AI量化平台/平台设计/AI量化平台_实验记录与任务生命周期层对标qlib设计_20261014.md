## 二、qlib 的六条可迁移设计（D14~D19）

### D14 · 崩溃安全的「领取 → 提交 / 归还」三段式

**qlib 做法**（`task/manage.py`）：

| 段 | 方法 | 行 | 作用 |
|---|---|---|---|
| ① 原子领取 | `fetch_task()` | L265-286 | `find_one_and_update({status:WAITING}, {$set:{status:RUNNING}})` —— **查询即更新，一步原子** |
| ② 异常归还 | `safe_fetch_task()` | L288-310 | 上下文管理器；`except (Exception, KeyboardInterrupt)` → `return_task(task, status=原状态)` |
| ③ 启动复位 | `reset_waiting()` | L416-427 | 进程重启后把悬挂的 `running` 全扫回 `waiting` |

**★ 为什么三段缺一不可**：
- 只有 ①：worker 崩了任务永远卡 `running`（**死锁**）。
- 只有 ①②：整机断电时归还代码**根本没有机会执行** → 仍死锁。②覆盖「进程还活着」，③覆盖「进程已死」。
- `safe_fetch_task` 的注释直说了这层取舍：**at-least-once** 语义（任务可能被执行两次），
  所以业务侧必须**幂等**。

**★ 我方现状**：`live.py` 只有 142 行，**没有订单生命周期层**。`risk.py` 的
`reserve_order / release_order / release_fill` 是**资金额度**语义，不是**订单状态**语义。

**AtomCode 复核的边界划分（采纳）**：
> 「risk.py 的 reserve_order 管**资金额度占用/释放**（**事前闸门**），
> 生命周期层管**报单状态机 + 崩溃恢复**（**事中事后**）。」

→ 两者**不重复**：一个是「准不准你下」，一个是「下了之后到哪一步了」。
→ 三段式的等价物在我方是：**提交前落盘（write-ahead）→ 崩溃后对账归还 → 启动复位**。

**可迁移点**：`ClaimLedger`（已落地）—— 四态 + 原子领取 + `safe_claim` + `reset_waiting`。

### D15 · 记录模板链：显式依赖 + 递归校验 + 幂等重跑

**qlib 做法**（`record_temp.py`）：
- `depend_cls`（L36）每个记录声明「依赖哪个上游记录类」
- `check()`（L127-165）**递归**顺着 `depend_cls` 往上，断言**产物文件真的存在**
  （`recorder.list_artifacts`），而不是「上一步返回了」
- `ACRecordTemp.generate()`（L226-245）缺依赖 → `logger.warning(...) ; return`（**跳过而非崩溃**）
- `skip_existing`（L228-235）产物已存在 → 跳过（**幂等**）

**★ 这条对应我方哪条铁律**：
> 「**日志说成功 ≠ 东西真的在。** 日志统计的是「我做了几个动作」，不是「用户能不能看见」。」

qlib 把这条血泪教训**写成了结构**：`depend_cls` + `check()` 强制把「我做了」和「产物在」分成两个断言。

**AtomCode 复核的关键修正（采纳）**：
> 「更廉价替代：不搬 `depend_cls` 类体系，只在每步产物旁写 `manifest.json`（**输入哈希 + 代码版本**），
> 下游启动时校验哈希，不符即跳过。递归校验自然由链式 manifest 达成，**成本约为 qlib 方案的十分之一**。」

→ **采纳**。我方产物链是「数据→信号→回测→绩效→归因」五段，不需要类体系，
只需要**每段产物旁边放一个 manifest**（输入哈希 + 代码版本 + 参数快照）。
→ 这样「改了信号定义 → 从信号段重算」就是**哈希比对的自然结果**，
而不需要人记住「我改了哪一步所以要先清哪几个文件」。
→ `RecordChain`（已落地）实现了类体系版本，**manifest 版本列为 P1**（更轻）。

### D16 · 四态状态机与「做了一半」（`STATUS_PART_DONE`）

**qlib 做法**：`waiting / running / part_done / done`（L79-82）。
`run_task` 支持 `before_status → after_status` 映射（L485-551），
且 `PART_DONE` 的任务被再次领取时，喂给它的是**中间结果 `task["res"]`**（L538-540）。

**★ 为什么这个状态值重要**：它让「断点续跑」成为**状态机的第一等公民**，
而不是散落在业务代码里的 `if resume:` 分支。

**对应我方欠账 G2**：`RiskLevel` 目前只有三档 ——

```python
NORMAL  = "normal"    # 正常放行
WARNING = "warning"   # 预警：缩小仓位
HALTED  = "halted"    # 停机：只许平仓
```

缺的正是 `PART_DONE` 的等价物：**「恢复中 / 半开」**。停机之后若直接跳回 `NORMAL`，
等于把导致停机的风险条件一笔勾销；正确的做法是经过一个**只减不增的观察窗**再放开。
→ 本轮仍**未回填**（P0 挂账，见 §四）。

### D17 · 在途态属于订单本体，不属于第三方簿记

**qlib 做法**（`backtest/decision.py:36-151`）：
```python
stock_id: str
amount: float          # 目标量（非负）
direction: OrderDir
start_time / end_time  # 订单所属区间（≠预期成交区间）
deal_amount: float = 0.0   # 已成交量（成交系统回填）
factor: Optional[float] = None   # 部分成交系数
```
注释还把三种情形写清了（L67-72）：
> - 不可交易：`deal_amount == 0`，`factor is None`，**该订单不产生成本**
> - 已成交 / 部分成交：`deal_amount >= 0` 且 `factor is not None`

外加两个**带符号增量**：`amount_delta`（L89-96）/ `deal_amount_delta`（L98-105）。

**★ 我方差距**：`PendingOrder` 挂在 `RiskEngine` 上 ——
订单本体（策略层产出）**不知道自己在途**。于是「策略以为成交了、风控以为还挂着」
这类错位只能靠调用方自觉对齐。

**AtomCode 复核的补强（采纳）**：
> 「会引入新失败模式（共享可变引用被策略层篡改）。
> 防线：① 订单对外暴露**只读视图**（frozen dataclass 或只读 property）；
> ② 状态迁移只有 **RiskEngine / 执行器可写**（**单一写者原则**）；
> ③ risk.py 的 reserve/release 仍保留**资金语义**，订单字段只**镜像状态**，
> **两者对账不一致即 HALTED**。」

→ 第 ③ 点尤其有价值：它把「两套簿记」从隐患变成了**互相校验的冗余**——
不一致本身就是停机信号。这与我方 R 系列闸门「宁可错停不可错放」的气质一致。

**可迁移点**：`InFlightOrder`（已落地）—— 目标量/已成交量/加权均价/**撤单释放额度**。

**★ 自测抓到的真坑（写进模块注释）**：`outstanding` 若简单写成 `amount - filled`，
则**撤单后仍占着未成交量**（撤单只改了 `status`，减法照旧）。
后果等价于 **R7 顺序锁定被绕过** —— 撤掉的单继续吃额度，新单被误拒。
正确语义：**撤单/拒单 = 在途敞口立即归零（额度释放）**。
（这正是我方 2026-10-12 血泪规则①「默认值必须与多数情形一致」的同族错误。）

### D18 · 毛账 / 净账**强制并列**

**qlib 做法**（`record_temp.py:514-528`）：
```python
analysis["excess_return_without_cost"] = risk_analysis(ret - bench,           freq=...)
analysis["excess_return_with_cost"]    = risk_analysis(ret - bench - report["cost"], freq=...)
```
两套结果**同时**落盘 + 同时 `log_metrics`。

**★ 为什么这条对我方是「正中靶心」**：
我方已有两条实测恰好指向它 ——
- **H-009**：成交口径现实化后 4/4 总收益下降（BTC 219.3% → 116.3%，**−103.0pp**）。
- **H-011**：消融归因 → **乐观偏差主因是执行成本假设，不是成交时点**（BTC 成本项 ×344）。

也就是说，**毛账与净账的差距本身就是我们最重要的那个数字**。
既然如此，它就不该是「想起来了才算一下」，而应该是**默认输出的两列**。
→ 我方 `core/report.py`（156 行）**没有这一列** → P0。

**AtomCode 复核的关键警示（采纳，且改变了呈现方式）**：
> 「滑点未标定时净账确实是用假数校真数，但**只给毛账更危险**（实测偏差×344）。
> 诚实做法：净账必须标注『k=估计值，未经实盘标定』，
> 并列出 **k ∈ [0.5k, 2k] 的净账区间** ——
> **若区间横跨零，策略不可上实盘**，这才是净账的真正用途。」

→ **采纳并强化**：`gross_net_dual_account` 已实现 `cost_drag` / `cost_share_of_gross` / `decision`；
`decision == "cost_dominated"`（**毛赚净亏**）自动升级为最高优先级警报。
→ **新增 P1 项**：`report.py` 输出净账时**必须并列 k 的敏感性区间**，
   并给出「区间是否横跨零」的布尔判定。**只输出单点净账 = 用假数掩盖假数。**

## 三、本轮实测（H-016 / H-017，均已证伪）

两条都取自 qlib 的**纪律**而非其**功能**：

| # | 假设 | 来源 | 结果 |
|---|---|---|---|
| **H-016** | 入场「放量」门槛从**固定倍数**改为**滚动 90 分位** | qlib rolling normalization 纪律（`RobustZScoreNorm` / `CSQuantileNorm`：只用截至该时点的历史统计量） | **已证伪** 1/4 |
| **H-017** | 只在 MA30 上行趋势**刚转正后 ≤96 根内**入场 | qlib `workflow/online`（OnlineManager：「预测的新鲜度有寿命」）★ **类比到「趋势状态新鲜度」，非 qlib 原生实现** | **已证伪** 2/4 |

### ★ 但真正有价值的产出是「门槛咬合力」这个额外诊断

| 标的 | 基线入场 | H-016 保留 | H-016 咬合力 | H-017 保留 | H-017 咬合力 |
|---|---|---|---|---|---|
| BTCUSDT | 43,521 | 9,708 | **砍 77.7%** | 42,967 | 砍 1.3% |
| ETHUSDT | 43,207 | 9,465 | 砍 78.1% | 42,727 | 砍 1.1% |
| BNBUSDT | 43,355 | 9,870 | 砍 77.2% | 42,660 | 砍 1.6% |
| DOGEUSDT | 35,432 | 9,082 | 砍 74.4% | 34,929 | 砍 1.4% |

- **H-016 的证伪是强证据**：门槛砍掉约 **3/4** 入场（真咬合），单笔均值**反而下降**
  （BTC 2.0061→1.7914 / ETH 2.373→2.0759 / BNB 2.3238→2.5804 / DOGE 0.6738→0.6011）
  → 结论升级：**「放量」这条线（不论固定阈值还是自适应分位）整体不具备入场筛选力**。
  不能再把责任推给「1.5 这个数没选好」—— **否掉的是阈值形式，不只是阈值。**
- **H-017 的证伪是弱证据，必须标注**：BTC/ETH 只砍掉 ~1.2%，故 BTC 的 `Δ=0.0000`
  是「**门槛几乎没咬到**」，**不构成「门槛无效」的证据**；提供信息的是 BNB（−0.1620）/
  DOGE（−0.0131）—— 砍掉 1.5% 反而更差。
  → 若要重测必须换更长窗口让门槛真正咬合。

### ★★ 方法论级结论（本轮最大产出）

这是**第 5 / 第 6 条「让策略更保守」型假设**（H-012 / H-013 / H-014 / H-015 / H-016 / H-017）**全数证伪**。
累计证据已足够下一条判断：

> **「加门槛」这一整类思路在黑马策略上系统性无效。**
> 下一步应转向**出场端**或**成本端** —— H-009 / H-011 已指出**成本才是最大偏差项**。

**并且**：今后任何「加门槛」结论必须**附门槛咬合力**（砍掉多少 %），
否则无法区分「门槛无效」与「门槛没咬到」——
本轮 H-017 就是差点把「没咬到」误报成「无效」。**这条已写入技能 v1.1.6。**
