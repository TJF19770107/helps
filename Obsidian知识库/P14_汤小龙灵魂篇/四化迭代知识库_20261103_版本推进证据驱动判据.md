**连续 8 轮，全部 +0.0.1，一次 0 都没有过。** 一个「只在有实质改进时才推进」的判据，连续 8 次都判定有改进——那它就不是判据，是常量。

### 根因

`_tools/soul_daily_evolution.py` 的 `step4_iterate()`：

```python
# 注释说：
# "灵魂层健康度只在有实质改进时才 +0.0.1；P0 存在时不推进版本（禁止粉饰）"

if p0:
    grade, delta = "需抢修", None
elif p1:
    grade, delta = "亚健康", "+0.0.1"
elif healthy:
    grade, delta = "健康", "+0.0.1"      # ← 就是这里
else:
    grade, delta = "待观察", None
```

**注释和实现是反的。** `healthy` 判断的是「覆盖率 100% + 宪法在位 + 正本 ≥100」——这是**达标线**，不是**改进量**。
达标 ≠ 改进。天天达标，就天天 +0.0.1。这属于**粉饰型缺陷**：功能没坏，但它系统地、无意识地告诉我「今天也进化了」。

> 比报错更危险的不是红，是**常绿的假绿**。

## 一·标准化（把判据说死，不留解释空间）

新判据只有一句：

> **版本推进只认「实质改进证据」。没有证据，一律输出 `None` 并显式写「本轮进化为 0」。**

「实质改进证据」白名单（六类，全部可独立核验）：

| # | 证据类型 | 判定方式 | 为什么算改进 |
|---|---|---|---|
| 1 | 覆盖率修复 | 上轮 < 100%，本轮 == 100% | R1 缺口真的补上了 |
| 2 | 正本扩容 | 本轮文件数 > 上轮 | 新资产真落地 |
| 3 | 宪法恢复 | 上轮 False，本轮 True | 丢了又找回来 |
| 4 | 死链清零 | 上轮 dead > 0，本轮 == 0 | 缺陷真消掉 |
| 5 | 工具新增 | `_tools/*.py` 数量上升 | 工程能力真的多了 |
| 6 | 引擎实修 | 当日有 `.py` 被改（mtime = 今天） | 判据/工具链真的改了 |

**明确不算改进的**（必须写清，否则边界会被自己慢慢放宽）：

- 覆盖率本来就 100% 且不变 —— 这是**巡检正常**
- 正本文件数不变 —— 这是**巡检正常**
- git 干净 —— 这是**巡检正常**
- P2 级源端死链长期存在但没动 —— 这是**已知遗留**

判据优先级（P0 永远压过证据）：

```
P0 存在        → delta = None，即使有证据也禁止推进
基础健康项不达标 → delta = None，grade = 待观察
有证据         → delta = "+0.0.1"，evolved = 1
无证据         → delta = None，  evolved = 0，reason 明说「本轮进化为 0」
```

## 三·自动化（脚本自己证明自己不是恒绿）

新增的变更测试是关键，因为这里最容易骗自己的地方恰恰是**判据本身**：

```python
# 用例 1：上一轮和这一轮完全一样 → 必须 0
("纯巡检（无任何变化）", {"rate":100.0,"files":147,...}, {}, {"evolved":0, "patch_bump":None})
# 用例 2：覆盖率 88% → 100% → 必须 1
("覆盖率 88%→100% 修好", {"rate":88.0,...}, {}, {"evolved":1, "patch_bump":"+0.0.1"})
# 用例 3：正本 144 → 147 → 必须 1
("正本 144→147 新资产落地", {"files":144,...}, {}, {"evolved":1, "patch_bump":"+0.0.1"})
# 用例 4：P0 宪法丢失 → 必须 0（即使有证据）
("P0 宪法丢失 + 覆盖率全崩", {"rate":50.0,...}, {"cons":False}, {"evolved":0, "patch_bump":None})
# 用例 5：无基线快照 → 必须 0
("无基线快照（首轮）", {}, {}, {"evolved":0, "patch_bump":None})
```

实测输出（`_tools/test_engine_evidence.py`）：

```
✅ 纯巡检（无任何变化）        进化为0 推进=None
✅ 覆盖率 88%→100% 修好        进化为1 推进=+0.0.1
✅ 正本 144→147 新资产落地     进化为1 推进=+0.0.1
✅ P0 宪法丢失 + 覆盖率全崩    进化为0 推进=None
✅ 无基线快照（首轮）          进化为0 推进=None
结论： PASS 判据随输入变化，非恒绿
```

**为什么必须做这一步**：旧判据的形式是 `if healthy: delta = "+0.0.1"`。这个分支**永远走得到**，所以「输出 == 期望 +0.0.1」的断言**永远绿**。
它连「判据根本没区分能力」都发现不了。只有拿两组不同输入跑出两个不同结果，才证明它有区分能力。

> **「输出 == 期望」型断言，对常量型缺陷完全失明。**

## 五·踩到的真坑（本轮新增，按形态编号）

1. **坑：注释与实现相反，且没人发现，因为结果看起来一直是对的。**
   「健康就推进」这件事，在任何一轮里都**讲得通**——今天确实健康、确实该记一笔。所以八轮里没有任何一轮会觉得异常。
   判据错了不会报错，只会**持续产出看起来合理的结论**。这类缺陷只能靠**纵向比对历史台账**发现（八轮全是同一个值 = 常量）。
   → **判据必须定期做「纵向自证」：把历史结果摊开看分布。分布退化成单点 = 判据死了。**

2. **坑：报「已修」把「建占位」也算修。**
   03:00 首跑时打出了「已修：创建当日日志占位」。但当日日志缺失是**跨日效应**，建占位是**补齐常识**，不是修缺陷。
   把常识动作算进「已修」，会让「修复数」虚高，也让真正的修复被稀释。
   → **修复清单要分级：「修缺陷」/「补占位」/「重试成功」，三者不能混计。**

3. **坑：`-` 号格式串在证据文本里二次转义。**
   证据模板写 `"覆盖率从 %.2f%%→100%%"`，在 f-string 外面又套一层 `%` 格式化时，`%%` 被吃成 `%` 后又触发一次格式化，输出出现 `88%%→100%%`。
   → **带 `%` 的字符串，格式化只做一层；要嵌进 `%` 模板的，先把 `%` 换成 `.pct.` 或直接 f-string。**

4. **坑（老坑复发提醒）：改文件一律写独立 `.py`，不要 `python -c "..."`。**
   本轮全程用 `_tools/xxx.py`，没有再踩反引号被 bash 命令替换的坑。这条继续有效。
