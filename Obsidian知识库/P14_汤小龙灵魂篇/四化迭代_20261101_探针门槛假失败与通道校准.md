## 一 · 标准化（S）—— 把「探针该给多少 token」立成规矩

**规矩**：给**推理型模型**（响应含 `reasoning_content`）发探活请求时，`max_tokens` 不得低于 **32**。

- 理由：reasoning 段与 content 段**共用** `max_tokens` 预算。给 4，reasoning 自己就能吃光，
  `choices[0].message.content` 返回空串，而 `usage.completion_tokens` 恰好等于 4 —— 这就是本轮看到的
  `empty_content(usage=4)`。
- 反例证据（本轮实测，同一分钟）：

  | 调用 | max_tokens | 结果 |
  |---|---|---|
  | `probe_channels()`（脚本） | 4 | `reject: empty_content(usage=4)` → 判 DOWN |
  | 手工 `http_chat` 同参 | 4 | `content="Pong. How can I help?"` → 判 UP |

  **同一个参数，两种结论** = 门槛贴着下限 = 判据不成立。凡是「时好时坏」的探活，先怀疑预算太薄，不要怀疑服务。

- 推论（更普适）：**任何「够用就行」的预算参数（max_tokens / timeout / buffer）都必须留出至少一个数量级的余量**，
  否则它会把「慢但可用」判成不可用。这与脚本自己 2026-10-23 那条注释（timeout 8→25）是同一类病，只是换了参数。

## 三 · 自动化（A）—— 把「备份必须先活下来」写进脚本

本轮所有写操作都走同一套模板，任何一环缺失就 return 非 0：

1. `read_bytes()` → 只认字节，不认文本模式（避免 CRLF 被吃掉）
2. 打印「原大小 + sha + 待替换片段出现次数」，**不等于 1 就停**，不猜
3. `uniq_bak()`：`<原名>.bak_<时间戳>_<sha8>_<字节>B`，同名则递增序号
4. 写回 `open(p,"wb")`
5. 回读四断言：新大小 / 旧片段清零 / 新片段在位 / 备份字节数 == 原大小

本轮实测：`27546 B → 27637 B（+91）`，sha `1728bcad… → 26a91ef7…`，备份 `27546 B` 完整，`py_compile` 通过。
**「+91」这个数字本身就是证据** —— 若 diff 规模与预期不符，说明混进了别的东西（这条以前踩过，所以现在必看）。

## 五 · 踩到的真坑（四个，全是本轮真发生）

### 坑 1 · `max_tokens=4` 的探针在推理型模型上必然假死

- **现象**：`probe_channels()` 报 `reject: empty_content(usage=4)`，三通道全 DOWN。
- **误判路径**：先怀疑网关挂了 → 实测 `/v1/models` 200、手工 chat 200 出 `Pong` → **推翻**。
- **真因**：`max_tokens` 同时约束 reasoning 与 content，4 个 token 被 reasoning 独占。
- **教训**：**同参数两次结论相反 = 判据本身不成立**，别在「服务坏了」上继续花时间。

### 坑 2 · 「环境变量设了」不等于「脚本用上了」

- 第一次重跑：`EVOLVE_BASE="http://127.0.0.1:15740/v1" python scripts/self_evolve.py tick` → 仍报「全部不可用」。
- 差点归因为「环境变量没传进去」→ 实际用 `import self_evolve; probe_channels()` 打出来
  `EVOLVE_BASE=http://127.0.0.1:15740/v1`、`base` 也确实指向 15740，**变量是通的，是探针判据不通**。
- **教训**：验证「配置是否生效」要打印**脚本内部实际使用的值**，不是打印 `os.environ`。
  两者一致才能排除配置问题，转向判据问题。

### 坑 3 · 离线降级不报错，只把产物变丑

- tick 返回码 0、L4 校验 4/4 全绿、版本号照常 +1 —— **没有任何红灯**。
- 但经验条目是代码碎片，技能候选 0 个。**「全绿」和「有质量」是两件事。**
- **教训**：降级路径必须自己也有一条 L4 断言（本轮之后应加：`assert lessons 每条 action 非空且不含 def/if/= 符号`）。

### 坑 4 · 报错码把方向指错了三次的老毛病，这次出现在「仓库不存在」上

- `git ls-remote origin` → `remote: Repository not found.`
- 这个报错**既可能是**「没权限」，**也可能是**「仓库根本不存在」，措辞不区分。
- 证伪顺序：① 读 `.git-credentials` 有 2 条 github 凭据 → ② `GET /user` 两条都 200，
  scopes 含 `repo` → ③ `GET /repos/TJF19770107/p14-tangxiaolong-soul` 返回 **404** →
  **结论：凭据是好的，仓库从来没建。**
- **教训**：`Repository not found` 的第一步不是换 token，是**分开验「身份」与「对象」**（`/user` vs `/repos/...`）。
