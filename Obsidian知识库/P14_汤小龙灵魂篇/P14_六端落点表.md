### 3.1 GitHub：从「四条通道全断」到真通（2026-11-01）

旧的四条通道确实全断（`gh` 未登录 / GCM 路径写死 G 盘 / SSH 未被接受 / 连接器建仓 403）。
本轮换了判定顺序，一次打通 —— **关键是把「身份坏」和「对象不存在」分开验**：

| 步骤 | 命令 / 端点 | 结果 |
|---|---|---|
| ① 凭据是否存在 | 读 `~/.git-credentials` | 有 2 条 github 凭据（`gho_` x-access-token / `ghp_` TJF19770107） |
| ② 身份是否有效 | `GET https://api.github.com/user` | 两条都 **200**，scopes 含 `repo` |
| ③ 对象是否存在 | `GET /repos/TJF19770107/p14-tangxiaolong-soul` | **404** → 仓库从来没建，不是没权限 |
| ④ 建仓 | `POST /user/repos` `{private:true}` | **201** created |
| ⑤ 推送 | `git push -u origin main` | `[new branch] main -> main` |
| ⑥ 独立核验 | `git ls-remote origin refs/heads/main` | `c4716d0…` **与本地 HEAD 逐字一致** |
| ⑦ **后续推送（2026-11-01 07:56）** | 首次出现 `Recv failure: Connection was reset` | **真因：git 不走 Windows 系统代理**。系统代理 `127.0.0.1:8888`，给仓库配 `http.proxy` 后 `c4716d0..df09626` 一次推成 |

```bash
# 复核命令（任何时候可重跑，数字当场取，不写死在文档里）
cd C:/Users/Administrator/WorkBuddy/汤小龙灵魂篇
git rev-list --count origin/main..HEAD           # 期望 0
R=$(git ls-remote origin refs/heads/main 2>/dev/null | awk '{print $1}')
[ "$R" = "$(git rev-parse HEAD)" ] && echo 真闭环   # 期望打印「真闭环」
git ls-tree -r --name-only origin/main | wc -l   # 远端实际文件数
```

> ⚠️ 推送时会打印 `git-credential-manager.exe: No such file or directory`（GCM 路径写死 G 盘）。
> **这是噪声，不是失败** —— 它 fallback 到 `store` 凭据后照常推送（rc=0 + `[new branch]` 已证）。
> 判据永远看 `ls-remote` 的 sha，不看这行 stderr。

> ⚠️ **`Recv failure: Connection was reset` 不是凭证问题，是代理问题。**
> `git` **不会自动使用 Windows 系统代理**（注册表 `ProxyServer=127.0.0.1:8888` 对 git 无效）。
> 已把代理固化到**仓库级**配置（不污染全局）：
> `git config http.proxy http://127.0.0.1:8888` / `git config https.proxy http://127.0.0.1:8888`
> 判伪方法：拿 `git/git.git` 做对照（能拉到 5441 ref）→ 说明网络通，问题在本仓库请求被 RST。
> 另一条陷阱：`cmd | head` 之后 `echo $?` 拿到的是 `head` 的码，**永远是 0**，不能当判据。

### 3.2 CNB：不是网络问题，是 token 的 scope 与时效问题

`cred_triage.py probe` 报 `ConnectionResetError(10054)` / `Tunnel 502`，看着像网络断。
本轮直连 API 复测，**网络是通的，问题在凭据本身**：

| 凭据 | 长度 | 端点 `GET /user` | 判定 |
|---|---|---|---|
| `env CNB_TOKEN`（遮蔽层） | 27 | **403** `Missing required scopes: account` | 活着，但 scope 不够 |
| `file ~/.cnb/token`（被遮蔽层） | 94 | **401** `invalid or expired` | **已过期** |

→ 结论反转：`cred_triage` 的「YELLOW 被遮蔽」预警，本轮**反而救了一次** — 被遮蔽的那把是死的，遮蔽它的那把是活的。

进一步探 scope：
- `GET /user/repos`、`GET /user/groups` → 均 **403** `Missing required scopes: account-engage:r`
- `GET /TJF19770107/repos` → **404** Resource not found
- `git ls-remote https://cnb.cool/TJF19770107/{p14-tangxiaolong-soul,p14-dandao,tangxiaolong-soul}.git` → 三个都无 ref

**但通道本身是通的（07:55 补充实证）**：
```bash
git ls-remote https://cnb.cool/TJF19770107/NPC_Hermes_Gateway.git
# -> fe9ec699…  HEAD / refs/heads/main      ← 既有仓可读，凭证能用
git ls-remote https://cnb.cool/TJF19770107/N8N20250913.git
# -> (无 ref，可能改名/删除/无权限，无法区分)
```
→ **结论精确化为：CNB 的 git 通道可读、可写既有仓；卡点在「建新仓」这一步（需 `group-resource:rw`）。**
→ 本轮**没有盲推**到 `TJF19770107/p14-tangxiaolong-soul.git`：一是建仓缺权限，二是 CNB 新仓默认可见性未核实，
   灵魂内容不能被上成公开仓。**宁可标未闭环，不冒泄露风险。**

**待办**：在 CNB 控制台重签一把带 `group-resource:rw` + `account-engage:r` 的 token，替换 `CNB_TOKEN`，
删掉过期的 94 位那把；建仓时**先确认是私有**。
