# FP8 量化技术全景

> 模块1 主线一：**模型量化**（不是交易量化）。目标：搞清楚一个 744B 的模型怎么塞进有限的显存里还不掉点。
> 配套：[[量化_论文精读清单]]、[[GLM-5_本地部署实操与踩坑]]

## 一、先分清三件完全不同的事（90% 的人在这里搞混）

| 对象 | 什么时候产生 | 量化难度 | 典型精度 |
|---|---|---|---|
| **权重（Weights）** | 训练完就固定 | 低，可离线校准 | FP8 / INT4 / INT8 |
| **激活（Activations）** | 推理时实时算出来 | 中，分布随输入变 | FP8（训练/推理） |
| **KV Cache** | 每个请求运行时产生 | **高，动态波动剧烈** | FP8 / INT4 / 3bit |

> ⚠️ **最反直觉的一条**：**权重量化不会自动量化 KV Cache**。一个 INT4 权重模型完全可能还在用 BF16 的 KV Cache。
> 看到"4bit 模型"就假设缓存也是 4bit —— 这是部署事故的高发点。**部署参数、校准方式、内核支持必须分别确认。**

## 二、FP8 两种格式（选错就掉点）

| 格式 | 动态范围 | 精度 | 适合 |
|---|---|---|---|
| **E4M3** | ±448 | 高 | **训练、权重**（推荐默认） |
| **E5M2** | ±57344 | 低 | 推理中的梯度/异常值场景 |

**选型口诀**：**E4M3 保精度，E5M2 保范围**。训练用 E4M3 存权重和激活，梯度通信可用 E5M2 防溢出。

**为什么 FP8 是甜点**：
- 相对 BF16：显存**直接减半**，H100/H200 的 Transformer Engine 原生支持，矩阵乘吞吐翻倍
- 相对 INT4：**几乎不掉点**，不需要复杂校准，工程风险低
- GLM-5 744B：BF16 ≈ **1.49TB** → FP8 ≈ **约 745GB**（仍需 8×H100 级）

## 三、四条技术路线（按侵入性从低到高）

### 路线 1：PTQ 训练后量化（最省事）
- **GPTQ**（arXiv 2210.17323）：逐层二阶误差补偿，一次性权重量化，INT4 常用
- **AWQ**（arXiv 2306.7761）：激活感知的权重量化，保护 1% 显著通道，INT4 精度更好
- **适用**：只想省显存、不改训练流程
- **代价**：极低比特（<4bit）时掉点明显

### 路线 2：平滑量化（治"激活离群值"）
- **SmoothQuant**（arXiv 2211.10438）：把激活的量化难度**数学等价地迁移一部分到权重**上，`Y=(X·diag(s)⁻¹)·(diag(s)·W)`
- **LLM.int8**（arXiv 2208.07339）：发现 0.1% 的离群特征维度主导误差 → 混合精度分解，离群维度走 FP16
- **本质**：大模型激活里存在**系统性离群通道**，不处理就会把动态范围吃光

### 路线 3：FP8 训练（GLM-5 走的路）
- **FP8-LM**（arXiv 2310.18313）：首个 FP8 全流程训练框架（前向/反向/优化器状态）
- **关键工程**：
  - **per-tensor / per-block scaling**（block-wise 更稳，Hopper 的 TE 支持 128×128 block）
  - **delayed scaling**：用历史窗口的 amax 估 scaling factor，避免每步同步
  - **master weights 保持高精度**（FP32/BF16），只在矩阵乘时转 FP8
- **GLM-5 的实证**：技术报告确认 **INT4 QAT 用于 SFT 阶段**，并做到训练与离线权重量化**共用量化内核、逐位一致（bit-exact）**

### 路线 4：QAT 量化感知训练（最贵但最稳）
- 训练时插入 FakeQuantize，让模型"适应"量化误差
- **GLM-5 的做法**：SFT 阶段就上 INT4 QAT，训推共用内核
- **适用**：要把模型压到 4bit 还要保交付质量

## 四、KV Cache 量化（长上下文真正的瓶颈）

**为什么难**：权重分布固定，KV 是每个请求实时生成的动态激活；不同 batch、不同句子、甚至不同注意力头之间分布差异巨大。

**2026 年的前沿**：
- **TurboQuant**（Google Research，ICLR 2026）：PolarQuant（随机旋转量化）+ QJL（Johnson-Lindenstrauss 零开销压缩），KV 压到 **3bit**，内存压缩 **6×+**，H100 上推理加速最高 **8×**，**无需训练或微调**
- **常规做法**：KV Cache FP8（vLLM/SGLang 原生支持，`--kv-cache-dtype fp8`），基本无损
- **端侧**：FP8 与 INT4 动态量化并用，突破显存带宽瓶颈

**GLM-5 的做法**：推理侧 **FP8 rollout** 降低单 token 延迟，缩短长轨迹完成时间——在 RL 里这直接决定单位时间能采多少条轨迹。

## 五、量化对 RL 训练的影响（容易被忽略）

GLM-5 的 slime 架构里，推理引擎用 **FP8 + MTP**，训练引擎高精度：
- 生成侧快 → 单位时间轨迹多 → RL 样本吞吐高
- 但**生成策略与训练策略必须严格对齐**（TITO 网关保留精确 token ID）
- → **量化误差会污染重要性采样比率** r_t = π_θ/π_rollout。这是"量化影响 RL 稳定性"的真实机理

## 六、实操选型决策树

```
目标是什么？
├─ 只是想跑起来看看
│   └─ 用官方 FP8 权重 + vLLM/SGLang 默认参数（KV 用 FP8）
├─ 显存不够，要压到单机
│   ├─ 8×H100 80G → FP8 744B 勉强（745GB > 640GB，需 8×H200 141G 或更多卡）
│   └─ 消费级卡 → 放弃 744B，选 30B 以下模型
├─ 要私有化交付给客户
│   ├─ 精度优先 → BF16 + 张量并行
│   └─ 成本优先 → FP8 + KV Cache FP8（先测业务指标，别只看 perplexity）
└─ 要自己训/微调
    ├─ 有 Hopper 卡 → FP8 混合精度（TE）
    └─ 没有 → BF16 + ZeRO/FSDP，别硬上 FP8
```

## 七、评估量化效果的正确姿势（血泪）

1. **别只看 perplexity** —— 业务指标（代码通过率、JSON 合规率、指令遵循）才是真指标
2. **分层测**：短上下文 / 长上下文（128K）/ 多轮 Agent，三段都要测
3. **必须做"变更测试"**：量化前后同一批 prompt 跑，diff 出**具体哪些 case 退化**，不是看平均分
4. **KV 量化和权重量化分开验证** —— 混在一起测，出问题定位不了

## 八、诚实的边界

- GLM-5 技术报告**没有公开** FP8 训练的完整 scale 策略、精度损失控制细节、KV cache 量化方案
- 本文件里"GLM 的实践"部分是**工程侧确认**（README/部署文档/报告片段），不是完整复现方案
- 想真正复现 FP8 训练 744B，需要 8×H200 级别资源，**本机（无独显）不可能**
- TurboQuant 是 2026-03 的 ICLR 论文，**代码/内核可用性未验证**
