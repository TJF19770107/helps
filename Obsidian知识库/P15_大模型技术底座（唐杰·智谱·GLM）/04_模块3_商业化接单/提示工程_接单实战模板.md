# 提示工程 · 接单实战模板

> 对应智谱 Academy 第 1 门课「从几种经典 Prompt 到 Prompt 工程」。
> 这里给的是**能直接抄进项目的东西**，不是概念科普。

## 一、六个层次（客户听得懂的版本）

| 层 | 做法 | 什么时候用 |
|---|---|---|
| L1 裸问 | 直接提问 | 一次性、低要求 |
| L2 角色+任务 | "你是X，帮我做Y" | 90% 的日常场景 |
| L3 结构化约束 | 加输出格式、字数、禁用词 | 要交付物时**必用** |
| L4 Few-shot | 给 2-5 个范例 | 风格/格式要求高时 |
| L5 CoT + 自检 | 要求先思考再答 + 自查一遍 | 复杂推理 |
| L6 多轮编排 | 拆分 → 生成 → 评审 → 返修 | 生产环境**必用** |

> **接单报价的锚**：客户要 L2 的效果，收 L3 的钱，交 L5-L6 的货 —— 这叫"降本增效"。
> 反过来（要 L6 效果收 L2 钱）就是亏。

## 二、通用六段式 Prompt 骨架（可直接复用）

```
【角色】你是____，服务对象是____。
【任务】把____变成____。
【输入】____（附：数据说明/边界）
【约束】
  - 必须：____
  - 禁止：____
  - 字数/格式：____
【输出格式】
  （给 schema 或示例）
【自检】输出前检查：①是否满足全部约束 ②有没有编造 ③格式是否合法
```

**为什么加"自检"**：这是 L5→L6 的分水岭，实测能显著降低格式错误率。

## 三、五个高频场景模板

### 模板 1：文案生成（接单最高频）
```
【角色】你是资深小红书/抖音文案策划，服务对象是中小商家。
【任务】为「<产品>」写 3 条不同切入点的种草文案。
【约束】每条 80-120 字；必须含 1 个具体使用场景；不得使用"最好/第一/绝对"等违禁词；不得编造功效。
【输出】表格：序号 | 切入点 | 正文 | 配图建议
【自检】检查违禁词、字数、是否出现无法验证的承诺。
```

### 模板 2：客服问答（知识库场景）
```
【角色】你是「<公司>」的客服，只回答与本公司产品相关的问题。
【知识】以下是从知识库检索到的片段：
<context>
{retrieved_chunks}
</context>
【规则】
1. 只能用 <context> 里的信息回答，找不到就答"这个问题我需要转人工确认"
2. 不得推测、不得补充 context 里没有的数字或政策
3. 回答控制在 80 字内，语气礼貌不油腻
【输出】JSON：{"answer": "...", "confidence": "high|low", "need_human": true|false}
```
> **关键**：`confidence` + `need_human` 两个字段是**降幻觉的工程手段**，不是装饰。

### 模板 3：结构化抽取（数据类接单）
```
【任务】从以下合同文本中抽取字段，输出严格 JSON。
【Schema】
{"party_a": "", "party_b": "", "amount": 0, "currency": "CNY",
 "start_date": "YYYY-MM-DD", "end_date": "YYYY-MM-DD", "penalty": ""}
【规则】找不到的字段填 null，不要猜；金额只留数字；日期统一 YYYY-MM-DD。
【输出】只输出 JSON，不要任何解释文字。
【自检】检查：JSON 可解析？字段齐全？有没有编造？
```

### 模板 4：方案/提案（接单前的敲门砖）
用唐杰 Final Project 的四问结构，非常好用：
```
【Problem】客户要解决的具体问题是什么？（一句话）
【Motivation】为什么值得做？（量化损失/机会）
【Method】我们怎么做？（分几步，每步交付什么）
【Results & analysis】怎么验收？成功/失败怎么判定？
```
> 这四个问题来自清华那门课 Final Project 的评审标准（slide 原话），**用它写提案，专业度立刻不一样**。

### 模板 5：Agent 任务分解
```
【目标】<终态描述>
【可用工具】<工具清单 + 各自能力边界>
【约束】最多 N 步；每步必须产出可验证的结果；失败要报告而不是重试同一动作
【输出】
  步骤1: 动作 | 输入 | 预期结果 | 验证方式
  步骤2: ...
【终止条件】满足____或达到 N 步
```

## 四、降幻觉五招（接单必须会）

| 招 | 做法 | 效果 |
|---|---|---|
| 1. 引用约束 | "只能基于给定资料回答" | 最有效 |
| 2. 强制弃权 | 给"我不知道/需转人工"出口 | 防止硬编 |
| 3. 结构化输出 | JSON + schema 校验 | 格式错立刻暴露 |
| 4. 二次校验 | 另一个模型实例当评审 | 抓事实错误 |
| 5. 温度调低 | temperature 0-0.3（抽取类） | 减少随机性 |

> 月之暗面的原话很清醒：*"幻觉无法彻底根除，幻觉本质是模型创造力的同源产物。"*
> → 所以正确姿势是**架构上做事后校验**，不是指望 prompt 消灭它。

## 五、参数怎么设（实测建议）

| 场景 | temperature | top_p | 说明 |
|---|---|---|---|
| 结构化抽取 | 0 - 0.2 | 0.9 | 要稳定 |
| 客服问答 | 0.1 - 0.3 | 0.9 | 要稳但别太死 |
| 文案创意 | 0.7 - 0.9 | 0.95 | 要发散 |
| 代码生成 | 0.1 - 0.3 | 0.95 | 要准 |

**GLM-5 系列特别注意**（官方 README）：
- `reasoning_effort` 只有 `low / high / max` 三档，默认 `max`
- 聊天场景要显式传 `clear_thinking=true`
- 跑 benchmark 复现保持默认 `max`

## 六、交付时怎么证明"提示工程有效"

**不要给客户看 prompt**，给他看这张表：

| 版本 | 通过率 | 平均字数 | 格式错误率 | 人工返修率 |
|---|---|---|---|---|
| v0 裸问 | 62% | 187 | 23% | 41% |
| v1 加约束 | 78% | 142 | 6% | 18% |
| v2 加 few-shot | 86% | 138 | 2% | 9% |
| v3 加自检 loop | **91%** | 136 | **0%** | **4%** |

（数字为结构示例，实际要用自己测的）

> 这张表就是"把 prompt 工程卖成服务"的证据链。

## 七、常见坑

1. **在系统提示里写"你是最好的助手"** —— 无意义，浪费 token
2. **一次给 20 条约束** —— 模型会漏，**分两轮**（先结构后细节）
3. **用中文写 JSON schema 又要求输出英文键** —— 容易混，schema 直接用代码块给
4. **不设 max_tokens** —— 长输出会被截断，客户以为模型坏了
5. **改 prompt 不记录版本** —— 出问题无法回滚，**必须 v0/v1/v2 存文件**
